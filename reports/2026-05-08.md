## 确认 Bug（bug_confirmed）

### riscv-isa-manual / PR-2661 / XiangShan — privilege_escape
mseccfg.MML/MMWP/RLB 被硬连线为只读零，Smepmp 扩展完全失效。PMP checker 没有 MML 真值表，M-mode 无条件通过所有 PMP 检查——即使 MML=1 应限制 M-mode 访问。这构成了硬件级特权边界逃逸。

### riscv-isa-manual / PR-2782 / QEMU — privilege_escape
Zicfiss SSPUSH 在 QEMU TCG 中以顺序一致性实现（store → ssp update 在同一翻译块内原子完成），但真实 RISC-V 硬件（RVWMO）下两者是 relaxed ordering。MTTCG 模式下其他 vCPU 可观察到比真实硬件更强的内存序，掩盖了 CFI shadow-stack 竞态条件，使 shadow-stack 绕过漏洞在模拟测试中无法暴露。

### riscv-fast-interrupt / PR-730 / OpenSBI — data_corruption
M-mode trap handler 在保存 CSR 之前先调整 sp（`_trap_handler` line 519）。在 SP 调整和 mscratch 恢复之间的 38 条指令窗口中，如果发生同步异常，mscratch 不指向有效的 sbi_scratch，导致不可恢复的陷阱状态损坏。同时 OpenSBI 显式清零 menvcfg.DTE（line 141），禁用硬件双陷阱保护，使得 M-mode trap handler 完全暴露在嵌套异常的损坏风险中。

### riscv-isa-manual / PR-2769 / FreeBSD — data_corruption
FreeBSD 未定义 SSTATUS_UXL 宏。`exception.S` 中 `csrw sstatus, t0` 在每次 trap return 时原样回写 UXL bits [33:32]，不做任何验证。`cpu_fork` 通过 `bcopy` 将父进程的 tf_sstatus（含 UXL）完整复制给子进程。若 M-mode firmware 设置了非法 UXL 值，该值会通过 fork/context-switch/signal-delivery 在整个进程树中传播，导致指令宽度误判。

### riscv-fast-interrupt / PR-700 / FreeBSD — data_corruption
struct pcb 无 pcb_xsp 字段。`cpu_switch`、`cpu_throw`、`savectx` 均不保存/恢复 xsp CSR。若 Smip 使能，线程在 deschedule/resume 后 xsp 与 sp 不匹配，`cspspop` 将从错误的 shadow-stack 位置弹出。`sendsig` 会覆盖硬件预保存的 x10-x15 区域。`cpu_fork` 不复制任何 shadow-stack 状态。bhyve 的 vmm_switch 也不交换 xsp CSR——guest 的 Smip 状态完全丢失。

### riscv-iopmp / PR-134 / XiangShan — privilege_escape
HWCFG2 的 field bit position 与更新后的 spec 不一致：chk_x/peis/pees/prient_prog 被初始化到 HWCFG0（offset 0x0008）而非 HWCFG2（offset 0x0010）。软件读取 HWCFG2 做 capability discovery 时得到全零，误认为 instruction-fetch-check 和 per-entry-suppression 不被支持——即使硬件实际实现了这些功能。IOPMP 权限模型被静默破坏。

### riscv-isa-manual / PR-2494 / Linux — data_corruption
KVM 在 `sbi_fwft_set()` 路径中直接 `csr_write(CSR_HENVCFG, ...)` 修改 henvcfg.PMM，但没有后续 `HFENCE.GVMA`。当 vsatp.MODE=Bare 且 hgatp.MODE 为 sv48x4/sv57x4 时，G-stage TLB 中的陈旧条目可能将仅在高位掩码不同的 GPA 别名到同一物理页，造成 guest 数据损坏。

### riscv-isa-manual / PR-2571 / QEMU — info_leak
scountinhibit 访问谓词未检查 menvcfg.CDE。按 Smcdeleg spec，当 CDE=0 时 scountinhibit 必须 raise illegal-instruction。当前仅检查 ext_ssccfg/ext_smcdeleg 存在性，S-mode 可在 M-mode 未委托计数器控制的情况下读写 scountinhibit，泄漏 M-mode 计数器状态。

### riscv-isa-manual / PR-2571 / XiangShan — function_loss
scountinhibit CSR（0x120）在 CSRs.scala 中定义了但无 CSRModule 实现，S-mode 访问直接触发 illegal-instruction trap。menvcfg.CDE（bit 60）完全缺失于 EnvCfg bundle。源码中有显式 TODO 标注 Sscounterenw 不支持。

### riscv-isa-manual / PR-2637 / QEMU — function_loss
`zcmt()` CSR 谓词和 `cm_jalt` TCG helper 将 JVT/Zcmt 门控在 smstateen0 bit 2。但 spec PR #2637 已移除了这个 spurious 依赖——bit 2 不应门控 JVT 访问。当 mstateen0/sstateen0/hstateen0 的 bit 2 为 0 时，QEMU 错误地 raise illegal-instruction，造成 Zcmt guest 功能丧失。

### riscv-isa-manual / PR-2597 / Linux — race_condition
Zicfiss validate callback 未检查 RISCV_ISA_EXT_ZAAMO。若硬件宣称支持 Zicfiss 但缺失 Zaamo（且无 'A' 扩展），内核仍枚举 Zicfiss 为可用，使能 shadow stack 但其 `ssamoswap.d` 指令发出非原子内存访问。并发 store 可破坏 shadow-stack token，CFI 保护失效。

### integrated-matrix-extension / PR-2 / Linux — data_corruption
`ptrace.c:invalid_ptrace_v_csr` 将 reserved mask 计算为 `~(VTYPE_VSEW | VTYPE_VLMUL | VTYPE_VMA | VTYPE_VTA) = ~0xFF`，拒绝 bits 63:8 的所有位。Zvvm 的 lambda[2:0]（bits 62:60）、altfmt_A（bit 9）、altfmt_B（bit 10）均在拒绝范围内。任何 ptrace SETREGSET 或 CRIU checkpoint/restore 在 Zvvm 进程上返回 -EINVAL——内核显式的 field knowledge 主动破坏 Zvvm 兼容性。

### riscv-isa-manual / PR-2660 / FreeBSD — info_leak
mcyclecfg/minstretcfg 在 context switch 中完全不被处理：`cpu_switch`/`cpu_throw` 只保存 GPR 和 FPE，struct pcb 无对应字段，encoding.h 无 CSR 定义（mcyclecfg=0x321, minstretcfg=0x322 均缺失）。线程设置的 `___INH` bits 跨 context switch 持久化，可选择性抑制后续线程的 cycle/instret 计数，泄漏计时信息。

### riscv-fast-interrupt / PR-629 / FreeBSD — info_leak
bhyve 的 APLIC MMIO 模拟在 sourcecfg write path 无条件存储 guest 写入的所有 32 bits，不屏蔽 bits 31:30（ACLIC 的 RO IE/IP mirror）。read path 直接返回软件存储值，不从实际中断状态（`irq->state`）合成。恶意 guest 可写入任意值到 RO 字段，且读取到 stale/fake 中断状态。

### riscv-iopmp / PR-186 / XiangShan — function_loss
RegHwcfg0 Chisel Bundle 完全缺失 no_err_rec 字段。Bit 23 被 md_entry_num[6] 占用而非 no_err_rec。error capture record 寄存器（ERR_INFO、ERR_REQADDR 等）完全未实现。软件无法通过 HWCFG0 发现 error recording 支持状态。

### riscv-isa-manual / PR-2605 / FreeBSD — info_leak
FreeBSD 检测到 Sscofpmf 后完全不管理 HPM counter 状态：`cpu_switch` 不保存/恢复 hpmcounter3-31 和 mhpmevent3-31，scounteren 保持为零阻塞合法访问，无 LCOFI handler。若 M-mode firmware 配置了 mcounteren 授予 S-mode HPM 访问，29 个 counter CSR 携带前一线程的陈旧值进入下一线程——跨线程信息泄漏。LCOFI（cause=13）将使内核 panic。

## 潜在风险（potential_risk）

### 特权逃逸类（privilege_escape）

**riscv-elf-psabi-doc / PR-429 / Linux**
FDPIC signal delivery 未检查 FDPIC_FUNCPTRS personality，未解引用 function descriptor 提取 entry PC 和 gp。信号处理器用 raw code address 作为 sepc，gp 未设置——处理器执行时 GOT 相对访问指向任意内存。

**riscv-elf-psabi-doc / PR-499 / FreeBSD**
纯 capability ABI（YLEN >= 129bit）下，所有 context switch（`cpu_switch`/`cpu_throw`/`savectx`）、trapframe、signal frame 均只保存 XLEN=64bit。`sd`/`ld` 指令在 save 时静默丢弃 capability metadata（bounds/permissions/seal/tag），在 restore 时从 raw address 构造无界 capability。整个内核的 capability 单调性不变量被破坏。

**riscv-fast-interrupt / PR-730 / XiangShan**
CLIC 双陷阱处理缺失：`TrapEntryMNEvent` 将第二个 trap 的 PC 写入 mnepc 但不检查是否为双陷阱上下文。mtval2 在双陷阱时从不写入，handler 无法发现原始 trap 原因。NMI handler 中所有后续 trap 被静默丢弃（NMIE=0 门控），无日志、无升级。

**riscv-isa-manual / PR-2599 / Linux**
KVM G-stage PTE walker 不知道 Svnapot：每级迭代用 level-derived page_size（4 KiB），TLB flush range 同样受限。若出现 NAPOT 64 KiB PTE，只 flush/写保护 4 KiB，剩余 60 KiB 保留可写/有效 TLB 条目——guest 可继续访问 hypervisor 意图保护的 GPA。

**riscv-isa-manual / PR-2661 / XiangShan**（已在 bug_confirmed 中详述）

### 数据损坏类（data_corruption）

**riscv-fast-interrupt / PR-700 / Linux**
trap entry 顺序为 "adjust sp → save GPRs"，但 Smip spec 要求 "save GPRs → adjust sp → cspspush"。无 cspspush 指令。若 Smip 硬件存在，硬件预保存的 x10-x15 在错误栈上。

**riscv-fast-interrupt / PR-730 / Linux**
sp 在所有寄存器保存前调整（`addi sp, sp, -(PT_SIZE_ON_STACK)` 在 REG_S 之前）。CSR_SCRATCH 被清零后到实际 exception dispatch 之间存在窗口——递归 trap 被检测到但 xepc 指向窗口内 kernel 地址而非 user 指令，sret 回 kernel 地址以 user privilege 执行。

**riscv-isa-manual / PR-2501 / FreeBSD + Linux**
CBIE override chain：M-mode firmware 可设置 menvcfg.CBIE=01 将 CBO.INVAL 从 invalidate 降级为 flush。Linux 内核无条件执行 CBO.INVAL 而不验证 menvcfg.CBIE——安全敏感的缓存擦除（如 crypto key wipe）将静默回写敏感数据。KVM 无条件设 henvcfg.CBIE=0x3 但不检查 menvcfg 实际允许值。

**riscv-p-spec / PR-189 / XiangShan**
P-ext REV（full-XLEN bit-reverse）在 BitmanipDecode 表中无条目，ALU datapath 无对应操作，MiscResultSelect 无第 5 项——软件使用 REV 将触发 illegal-instruction DoS。

**riscv-p-spec / PR-196 / QEMU**
PM4ADD 系列指令无 decode 条目。若未来实现，`get_gpr` 对 RV64 上 2-lane 操作只对 lane 0 做 sign-extend，lane 1 保留 raw bits。`gen_set_gpr` 在 RV32 上对 unsigned result 错误地 sign-extend。

### 信息泄漏类（info_leak）

**riscv-isa-manual / PR-1541 / QEMU**
KVM 加速下 ACLINT SWI write path raise MSIP 通过 KVM 注入硬件 mip，但 QEMU 的 env->mip 不同步更新——ACLINT SWI read handler 读到 stale mip.MSIP。

**riscv-isa-manual / PR-2660 / Linux + XiangShan**
Linux: struct thread_struct 无 mcyclecfg/minstretcfg 字段，`__switch_to` 不保存/恢复这些 CSR。CSR 定义完全缺失。XiangShan: EventInhibitBundle 将 MINH/SINH/UINH/VSINH/VUINH 无条件定义为 RW()，无 WARL 门控——未实现的 privilege mode 对应 bit 仍可写。

**riscv-isa-manual / PR-2494 / FreeBSD**
bhyve 的 `HFENCE.GVMA` 在 henvcfg 写入之前执行。struct hypcsr 无 senvcfg 字段，不跨 VM entry/exit 保存/恢复。HSTATUS_HUPMM 未定义。

### 拒绝服务类（denial_of_service）

**riscv-iopmp / PR-175 / XiangShan**
wired interrupt 和 MSI 生成未做互斥——两者同时触发导致重复中断传递。Ctrl FSM 无 MSI write transaction 相关状态。ERR_INFO.msi_werr 的 write-1-clear handler 被注释掉，且无硬件逻辑驱动该位。msi_en 信号连接到 Ctrl 但从未被引用。

**riscv-isa-manual / PR-2604 / Linux**
`__cmpwait()` 中 WRS.NTO 内联汇编无 `_ASM_EXTABLE` 条目。若 firmware 设 mstatus.TW=1，WRS.NTO 超时 raise illegal-instruction 导致 `fixup_exception()` 返回 false → `die()` → panic（在 IRQ 上下文中为 `panic("Fatal exception in interrupt")`）。调用路径包括 qspinlock/osq_lock 热路径。

### 功能丧失类（function_loss）

**riscv-isa-manual / PR-1922 / Linux**
Zabhlrsc 扩展 ID 缺失于 riscv_isa_ext_id enum，KVM ISA allowlist 无对应条目。CHERI 依赖 Zabhlrsc 做 capability atomics——无此扩展 guest 无法使用 byte/halfword LR/SC。

**riscv-isa-manual / PR-2539 / Linux**
PMU raw event 只验证 bit-range format，不查询 SBI firmware 或硬件实际是否实现该 event encoding。无实现的 event 被 WARL silently map 到 event 0（零计数），内核将常量零当作有效性能数据传递到 perf core。

**riscv-isa-manual / PR-2978 / FreeBSD + OpenSBI + QEMU**
FreeBSD `ENTER_USER_ACCESS` 对 sstatus.SUM 做 `csrs` 后无 WARL readback——若硬件错误地将 SUM 硬连线为只读零，所有 copyin/copyout 失败。OpenSBI MPRV/MXR set 后无验证读——若硬连线为零，unprivileged load/store 以 M-mode 特权静默执行。QEMU WARL write-mask 无条件包含 SIE/SPIE/MPRV/SUM/MXR/TVM/TSR/TW，但未按 spec 要求在对应 privilege mode 缺失时设为只读零——guest 可读写本应为零的位。

**riscv-fast-interrupt / PR-630 / QEMU**
Smtp tpush 尚未实现。未来实现的关键安全要求：external interrupt 时 xtopei（minor identity）写入 a1，xtopi（major identity）写入 a0——旧 spec 反了二者的寄存器分配。

### 竞态条件类（race_condition）

**riscv-isa-manual / PR-1541 / OpenSBI**
`sbi_ipi_send()` 用 `__ATOMIC_RELAXED` 在 scratch ipi_type 上做跨 hart 共享内存通信，无 release/acquire 语义。`wmb()`（fence ow,ow）只排序 MMIO store，不保证 scratch store 在 MSIP MMIO write 到达前对 remote hart 可见。若 remote hart 的 MSIP 中断先于 ipi_type store 到达，`sbi_ipi_process()` 读到 ipi_type=0 丢弃 IPI。

**riscv-isa-manual / PR-2575 / OpenSBI**
CSR_MSECCFGH（0x757）无条件定义，无 `__riscv_xlen==32` 守卫。HSM non-retentive suspend 不保存/恢复 CSR_MSECCFG——SSEED/USEED/RLB/MML/MMWP 配置在 suspend/resume 后丢失，运行时 S-mode 修改被静默丢弃。

## 值得关注的跨 spec 模式

### 1. Smip / Smrnmi 对 trap entry 的冲击（riscv-fast-interrupt PR-700, 730, 630）
多个 spec PR 对 Smip 规范进行了修订（cspspush/cspspop 的时序、shadow-stack pointer 管理、双陷阱保护依赖），但 **Linux、FreeBSD、OpenSBI、XiangShan 四个实现均无 Smip 感知**。共同问题：
- trap entry 仍为 "先调 sp 再保存寄存器"，不满足 Smip 的 "先保存寄存器再调 sp" 顺序
- xsp 在 context switch、fork、signal delivery、VM world-switch 中完全不被管理
- OpenSBI 显式禁用了 DTE（双陷阱使能）但非 Smrnmi 硬件上仍无法安全处理嵌套异常
- **结论**：Smip 一旦在硬件上落地，所有实现的 M/S-mode 软件栈都需要同步改造

### 2. CSR 门控与 smstateen/menvcfg 的 spec 修正（riscv-isa-manual PR-2571, 2637, 1541, 2660）
涉及多个 CSR（scountinhibit、JVT、mcyclecfg/minstretcfg）的门控条件在 spec 中被修正或新增，但实现侧存在滞后：
- QEMU 仍按旧 spec 用 smstateen bit 2 门控 JVT（该依赖已被移除）
- XiangShan 完全缺失 menvcfg.CDE、scountinhibit、mcyclecfg filter
- FreeBSD 缺失 mcyclecfg/minstretcfg 的 CSR 定义和 context-switch 路径
- **结论**：CSR 访问控制的 spec 修订正在密集发生，各实现的 CSR module 和 context-switch 代码是高风险区域

### 3. CHERI / capability 对内核 ABI 的根本性改变（riscv-elf-psabi-doc PR-429, 499; riscv-isa-manual PR-1922）
FDPIC 和 pure-capability ABI 要求内核在 signal delivery、context switch、ptrace 中维护 YLEN 宽度的 capability 寄存器，但当前 XLEN=64bit 的 trapframe/PCB 结构无法容纳。Zabhlrsc 缺失又使 CHERI 必需依赖断裂。**所有触及 trapframe/PCB/信号栈的内核代码都需要 width-agnostic 重构才能支持 CHERI**。

### 4. IOPMP spec 升级暴露硬件 RTL 滞后的系统性风险（riscv-iopmp PR-134, 175, 186）
三个 IOPMP PR 揭示了 XiangShan RTL 与最新 spec 在三个维度上的差距：
- HWCFG 字段位布局变更（PR-134）
- MSI 传递通路全链路缺失（PR-175）
- capability discovery 字段遗漏（PR-186）
这些问题在 spec 演进中很常见，但 IOPMP 作为系统级安全组件，其 capability misreporting 的后果是权限模型的静默绕过。
