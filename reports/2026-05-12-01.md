## 确认 Bug

### 1. riscv-isa-manual / PR-2922 / XiangShan
- **后果**: denial_of_service
- **描述**: XiangShan 在 ISA 字符串中声明了 Ziccrse 扩展支持，但整个微架构完全没有实现 RsrvEventual 相关的 PMA 属性 —— PMAConfigEntry、PMPRespBundle、pma_check() 等所有 PMA 通路均缺少 reservability 字段。当软件使用 LR/SC 同步原语时，硬件无法提供 forward progress 保证，在缓存压力下会导致无限 livelock。SoC 默认配置中 coherent-cacheable 主存区域也未设置 RsrvEventual。

### 2. riscv-isa-manual / PR-2996 / XiangShan
- **后果**: function_loss
- **描述**: Zawrs 扩展的 WRS.NTO/WRS.STO 指令被解码为 CSR 类型但执行阶段为零操作（no-op）。ROB 中仅有 hasWFI 阻塞状态机，没有 hasWRS 寄存器、WRS 入队触发器、WRS 唤醒条件。CfCtrl 缺少 isWrsNto/isWrsSto 谓词，blockCommit 不包含 WRS 阻塞。软件使用 WRS 的轮询循环将变成忙等待，彻底丧失 Zawrs 的节能目的。WRS 指令的 trap 逻辑和解码表定义正确。

### 3. riscv-profiles / PR-219 / FreeBSD
- **后果**: info_leak
- **描述**: bhyve VMM 在每次 VM exit 时无条件捕获 stval CSR（csr_read(stval)）并存储到 vm_exit.stval，无论 scause 类型。当 scause 为 BREAKPOINT 时，ebreak 触发的断点并不保证 stval 包含有效值（Sstvala 扩展明确排除了 ebreak），stval 可能携带上一次异常的残留硬件 CSR 状态。该值通过 VM_RUN ioctl 的 copyout 直接传递给用户态 bhyve 进程，构成内核信息泄露。原生内核 trap handler 正确使用 sepc 而非 stval。

### 4. riscv-rpmi / PR-158 / OpenSBI
- **后果**: privilege_escape
- **描述**: OpenSBI 作为 RPMI TEE framework 在 sbi_hart_smepmp_map_range()/unmap_range() 中修改 PMP CSR（pmp_set/pmp_disable）用于 TEE 内存 parcel 操作（MPXY 通道），但未执行 SFENCE.VMA 同步。RISC-V 规范要求在 PMP CSR 写入后必须执行 SFENCE.VMA 才能确保 PMP 权限变化被地址翻译缓存感知。同样的问题出现在 eswin_eic7700 平台专用 pmp_unconfigure() 和 sbi_hart_pmp_unconfigure() 中。mret 返回 S-mode 后，旧 PMP 权限可能仍被 TLB 缓存使用，导致 REE 访问刚撤销的 TEE 内存区域。

### 5. riscv-security-model / PR-111 / FreeBSD
- **后果**: info_leak
- **描述**: FreeBSD/riscv 内核不支持 Svukte 扩展（地址无关的 fault 延迟），且 VIRT_IS_VALID() 宏允许 U-mode 触发的 kernel 地址 page fault 进入 pmap_fault() 路径。pmap_fault() 存在至少四条不同耗时的执行路径（无效 L2 PTE、无效 L3 PTE、权限失败、A/D bit 更新+sfence.vma），使 U-mode 攻击者可通过 rdtime 测量 timing 差异推断 kernel 地址的 PTE 有效性，实现 KASLR 绕过。identcpu.c 缺少 Svukte 检测，locore.S 完全未配置 menvcfg，riscvreg.h 缺少 MENVCFG_* 宏定义。

### 6. riscv-server-platform / PR-102 / QEMU
- **后果**: function_loss
- **描述**: QEMU virt 机器的 RIMT ACPI 表生成存在两个 bug：(1) build_rimt_id_mapping() 中 "Destination Device ID Base" 字段错误写入了 source_id_base 而非 0；(2) build_rimt() 中 system IOMMU 路径的 num_ids 存在 off-by-one —— 计算为 `0xffff - s->pci_iommu_bdf` 覆盖 65535 个 ID，但 PCI Requester ID 共 65536 个（0-0xffff），最后一个 ID 被遗漏。导致 Guest OS 无法正确发现和配置 IOMMU，DMA 隔离和 device assignment 失效。

### 7. riscv-server-soc / PR-96 / FreeBSD
- **后果**: privilege_escape
- **描述**: FreeBSD IOMMU 驱动存在多处 TLB invalidation 功能缺陷：(a) SMMUv3 无条件使用 CMD_CFGI_STE_RANGE 而未检查 SMMU_FEATURE_RANGE_INV；(b) 无条件设置 tlbi.leaf=true 而未检查 IDR3.BBML；(c) Intel DMAR QI 路径无条件设置 DW/DR 而未检查 DMAP_CAP_DRD/DWD；(d) AMD IOMMU 驱动完全未发出 INVALIDATE_IOTLB_PAGES 命令刷新设备 IOTLB。上述问题可能导致设备通过过时映射访问已被释放/重分配的物理页面。

### 8. riscv-smmtt / PR-265 / XiangShan
- **后果**: info_leak
- **描述**: XiangShan RTL 在 MachineLevel 的 VSEIP 计算中使用 hgeip.asUInt(hstatusVGEIN.asUInt) 作为直接位索引，但 HstatusVgeinField 的 WLRL 未定义 legalRange（isLegal 恒返回 true），任何 6-bit 值（0-63）都可写入。配置中 vgeinWidth=6 但 geilen=7，超出范围的 VGEIN（8-63）在 hgeip/hgeie 数组中进行越界位索引，读取零填充位或未定义状态，导致 VSEIP 信号错误。CSRPermitModule 的 stopei bounds check 是正确的，但不防护此处的 hgeip 位提取路径。

### 9. riscv-svvptc / PR-134 / QEMU
- **后果**: function_loss
- **描述**: QEMU 的 riscv_cpu_reset_hold() 仅在 ext_smepmp 活跃时清零 mseccfg。但 mseccfg 也因 ext_zkr、ext_smmpm、ext_zicfilp 而存在。如果这些扩展启用但 smepmp 未启用，mseccfg 在 reset 时保留旧值，违反规范要求的 MML/MMWP/RLB reset=0 以及 USEED/SSEED 必须有定义 reset 值。have_mseccfg() 未检查 ext_zicfilp 但 mseccfg_needed() 检查了，存在不一致。

## 潜在风险

### 1. riscv-isa-manual / PR-2840 / OpenSBI
- **后果**: function_loss
- **描述**: mstatus_init() 仅在检测到 SMAIA 或 SMCSRIND 时设置 mstateen0[60]（SVSLCT，控制 S-mode 对 siselect/sireg* 的访问），但未在检测到 Smcdeleg 时设置。规范规定 Smcdeleg 依赖 Sscsrind，而 Sscsrind 的 CSR 访问由 mstateen0[60] 门控。如果 DT 列出 Smcdeleg 但缺少 Smcsrind，CDE 被启用而 mstateen0[60]=0，S-mode 访问委托计数器时收到 illegal-instruction 异常。Ssccfg（Smcdeleg 的 S-mode 对应扩展）也无运行时初始化。

### 2. riscv-isa-manual / PR-2974 / Linux
- **后果**: denial_of_service
- **描述**: M-mode Linux (CONFIG_RISCV_M_MODE) 在 _start_kernel 和 secondary_start_sbi 中使用 csrw CSR_IP, zero（即 csrw mip, zero）来清除中断 pending 位。但规范规定 MEIP、MTIP、MSIP 在 mip 中是只读的，写零无效 —— 必须通过平台特定机制清除（mtimecmp 写入清 MTIP、内存映射 MSIP 寄存器清 MSIP、平台中断控制器清 MEIP）。虽然先行写入 mie=0 屏蔽了中断，但一旦后续启用，残留 pending 会立即触发中断风暴。

### 3. riscv-isa-manual / PR-2974 / OpenSBI
- **后果**: denial_of_service
- **描述**: OpenSBI 在 sbi_ipi_init() 无条件 csr_set(CSR_MIE, MIP_MSIP)、sbi_hsm_hart_wait() 无条件 csr_set(CSR_MIE, MIP_MSIP|MIP_MEIP)、sbi_irqchip_init() 无条件 csr_set(CSR_MIE, MIP_MEIP)。规范规定若对应中断永远不能 pending，则 mie 位为 read-only zero。在单 hart 系统或通过 MEI 交付 IPI 的平台上，这些写入静默失败，导致 IPI/WFI 唤醒机制失效。SiFive TMC0 和 Andes AE350 的 suspend 路径也有相同模式。

### 4. riscv-server-platform / PR-101 / Linux
- **后果**: data_corruption
- **描述**: Linux 内核假设 SMP 中所有 hart ISA 同质（使用全局 riscv_isa bitmap 交集），但 RVA 规范放宽了此要求。KVM vCPU 在 kvm_arch_vcpu_create() 中缓存创建 CPU 的 ISA 特征，迁移到异构 hart 时 kvm_arch_vcpu_load() 无目标 hart ISA 验证，直接写入可能不支持的 CSR bits。KVM host FP/vector save 使用全局 ISA 交集判断，可能在拥有该扩展的 hart 上跳过了状态保存。spinlock 选择、VDSO hwprobe、PMM probe 均假设 hart 同质性。

### 5. riscv-server-soc / PR-118 / QEMU
- **后果**: function_loss
- **描述**: QEMU 的 IMSIC MMIO 写处理同步设置 pending 位并立即 raise 中断线（在 MMIO 写返回之前）。由于 QEMU 在 BQL 下串行化所有设备操作，设备 MSI 写入 IMSIC 总是对后续 DMA 读取可见，隐式提供了规范有意删除的 load-acquire 排序。在 QEMU 上开发的 Guest 驱动如果依赖 MSI 作为读屏障，将在真实硬件上失败。这是仿真保真度差距，非代码正确性 bug。

### 6. riscv-smmtt / PR-265 / FreeBSD
- **后果**: info_leak
- **描述**: FreeBSD bhyve 在 VM entry/exit 路径中无条件使用 guest hstatus（含 VGEIN 字段），未验证 VGEIN 是否在合法范围内。规范更新删除了对无效 VGEIN/SIDN 的明确 fail-safe 行为（SEIP=0、siselect/sireg 非法指令异常）。hideleg 无条件委托 IRQ_EXTERNAL_HYPERVISOR，hie 无条件启用 VSEIE/SGEIE，bhyve 无 CSR 模拟路径处理 siselect/sireg/stopei 访问 —— 完全依赖硬件陷阱，但陷阱行为现在是"建议"而非保证。

### 7. riscv-spec-barrier / PR-3 / FreeBSD
- **后果**: info_leak
- **描述**: FreeBSD/riscv copyinout.S 中的 copyout/copyin/copyinstr 在地址边界检查（bgeu 比较 VM_MAXUSER_ADDRESS）后直接进入 ENTER_USER_ACCESS（设置 SSTATUS_SUM），中间无任何 speculation barrier。当边界检查分支被误预测时，CPU 可能在 SUM=1 下投机执行越界或 kernel 地址的 load/store，通过 microarchitectural side channel（cache timing）泄露 kernel 内存（Spectre-v1 模式）。sendsig() 和 sys_sigreturn() 也存在无 barrier 的用户态状态注入。

### 8. riscv-spec-barrier / PR-38 / FreeBSD
- **后果**: info_leak
- **描述**: FreeBSD/riscv 的 pmap_activate_sw() 在上下文切换时写入 satp（ASID 当前硬编码为 0），仅跟 sfence_vma()，无 fence.hpd 清除页表 walker 预测结构。bhyve 的 vmmops_run() 在 VM 切换时使用 hfence.gvma() 但同样缺少 fence.hpd，前一个 VM 的页表预测可能被投机用于当前 VM 的地址翻译，构成跨 VM 瞬态执行信息泄露。hstatus.VTSR 未设置，hypervisor 无法拦截 guest 内 SRET 以插入 fence.hpd。

### 9. riscv-svvptc / PR-134 / OpenSBI
- **后果**: function_loss
- **描述**: sbi_hart_pmp_unconfigure() 禁用所有非固件 PMP entries 后不调用 sbi_hart_pmp_fence()。domain context 切换中 configure() 的返回值被丢弃 —— 若失败，PMP 保护完全失效而代码继续执行到 mret。mstatus_init() 在 HSM non-retentive suspend/resume 期间清零 mstatus（含 TW/TVM/TSR），S-mode 设置的虚拟化 trap bits 永久丢失。sbi_hart_smepmp_configure() 中 MML 先于共享区域编程设置，存在瞬时未定义保护窗口。

### 10. riscv-trace-spec / PR-216 / XiangShan
- **后果**: info_leak
- **描述**: XiangShan TraceCoreInterface 的 FromEncoder bundle 仅含 enable 和 stall，无 debug-mode halted 或 inhibit[1:0] 侧带信号。规范要求 debug mode 下 trace 记录必须被抑制，但 CtrlBlock 从未将 CSR 块的 debugMode 状态路由到 trace 基础设施。外部 encoder 无法区分"hart idle"与"hart 处于 debug mode 需要抑制记录"。security monitor 也无法通过 inhibit=10 信号注入 trace 抑制事件。

### 11. riscv-trace-spec / PR-276 / XiangShan
- **后果**: info_leak
- **描述**: XiangShan TraceCoreInterface.FromEncoder 仅提供 2-bit encoder→core 通道（enable/stall），外部 encoder 独立生成 Standard Support Packet。core 无法读取或验证 encoder 通告的功能标志（implicit_return、branch_predictor、resync_disabled）、协议版本、buffer sizing 参数。若 encoder 支持包声称 implicit_return=1 而 core 实际输出显式返回类型，trace 解码器将跳过返回栈验证产生错误指令轨迹。encoder 可通过 enable+stall 无限阻塞 ROB commit 而不被 core 察觉。

## 跨 Spec 模式

### CSR 访问控制与状态机同步（PMP/CSR 写入后缺少 fence）
多个 Spec 和 target 中出现同一模式：M-mode 固件写入安全关键 CSR（PMP、mseccfg、msdcfg、mstatus）后缺少 SFENCE.VMA 或等效同步，导致旧权限/配置被 TLB 或地址翻译缓存继续使用。

| PR | Target | 具体问题 |
|----|--------|---------|
| rpmi/158 | OpenSBI | PMP CSR map_range/unmap_range/unconfigure 无 SFENCE.VMA |
| svvptc/134 | OpenSBI | PMP unconfigure 无 fence；mstatus 在 HSM resume 时破坏 TW/TVM/TSR |
| svvptc/134 | QEMU | mseccfg reset 仅覆盖 ext_smepmp 路径 |
| isa-manual/2840 | OpenSBI | mstateen0[60] 未在 Smcdeleg 检测时设置 |
