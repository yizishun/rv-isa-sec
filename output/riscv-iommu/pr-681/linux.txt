PR #681  target=linux  overall=potential_risk
Spec: iotval2[1] was incorrectly set from SADE instead of is_implicit_write on implicit guest page faults; the kernel could misinterpret read implicit accesses as writes, corrupting guest page dirty tracking (marking pages dirty on reads or failing to mark them dirty on writes) in KVM/virtualized IOMMU contexts
Violation: The Linux kernel IOMMU fault handler reads iotval2 bit 1 from an implicit guest page fault record (G-stage page fault during two-stage translation) and interprets it as the implicit access write/read indicator, but the hardware set bit 1 based on SADE (S/VS-stage access/dirty exception flag) instead of the actual implicit access type, causing the kernel to misclassify a read access as a write or vice versa.
Consequence: data_corruption
Pattern: drivers/iommu/riscv/iommu.c reads iotval2 and extracts bit 1 to determine read vs write for implicit guest page faults; any future fault handling code that uses iotval2[1] to update guest page dirty bits or perform write-specific recovery on implicit faults would be affected

[potential_risk] drivers/iommu/riscv/iommu.c:520-525  riscv_iommu_fault
  The 'Placeholder for future fault handling implementation' comment on line 520 actively invites future code to be added here. When future guest page fault handling code is implemented (for causes 20-23: FAULT_VS), a developer unaware of the hardware behavior described in the RISC-V IOMMU spec could extract iotval2[1] assuming it indicates the implicit access type (read=0, write=1). In reality, when SADE (S/VS-stage Access/Dirty Exception) is enabled (set at line 1516 via RISCV_IOMMU_DC_TC_SADE), the hardware may report S/VS-stage A/D exceptions as guest page faults where iotval2[1] reflects the exception type (A-bit vs D-bit) rather than the original transaction's read/write direction. No comment or warning currently documents this pitfall in the code.
