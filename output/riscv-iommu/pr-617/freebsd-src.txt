PR #617  target=freebsd-src  overall=potential_risk
Spec: When iohgatp.MODE is Bare (no second-stage translation), msiptp.MODE must be Off; failing to enforce this in bhyve's DDT/DC programming allows a guest VM's MSI interrupts to be routed through stale or host-owned GSCID context, enabling VM escape via MSI interrupt redirection
Violation: In a future FreeBSD RISC-V bhype IOMMU driver, when software sets DC.iohgatp.MODE to Bare (disabling second-stage address translation because the guest runs with direct physical access or identity mapping) but leaves DC.msiptp.MODE != Off, the IOMMU will attempt MSI page-table walks with no valid GSCID context, causing MSI translations to be resolved in an undefined or stale VM address space
Consequence: privilege_escape
Pattern: iohgatp.*MODE.*Bare|msiptp.*MODE|DDT.*DC.*iohgatp|DDT.*DC.*msiptp|device_context.*iohgatp|device_context.*msiptp
------------------------------------------------------------

[compliant] sys/dev/iommu/iommu.h:145-150  iommu_domain
  The IOMMU_DOMAIN_IDMAP flag at line 147 shows the framework already understands identity-mapped domains (where DC.iohgatp.MODE would logically be Bare). In an x86 context this flag is safe because VT-d context entries don't have an independent MSI-PT mode — the translation enable affects all request types uniformly. However, a RISC-V IOMMU driver that maps this flag to DC.iohgatp.MODE=Bare must additionally enforce DC.msiptp.MODE=Off. The flag itself is correctly defined; the compliance gap is that no RISC-V IOMMU driver exists to misuse it.
