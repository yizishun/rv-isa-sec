PR #694  target=qemu  overall=bug_confirmed
Spec: IOMMU iohgatp.MODE uses shared encoding 8 for both Sv32x4 and Sv39x4, disambiguated by fctl.GXL; stale value 1 for Sv32x4 or missing GXL check causes G-stage walks to misinterpret page table format, leading to wrong SPA translations for DMA
Violation:
  QEMU's IOMMU emulation defines IOHGATP_Sv32x4 as 1 (the old hgatp-style
  value) instead of 8, OR uses MODE=8 exclusively for Sv39x4 without checking
  fctl.GXL to disambiguate between Sv32x4 (GXL=1) and Sv39x4 (GXL=0)
Consequence: data_corruption
Pattern:
  IOHGATP_Sv32x4|iohgatp.*MODE.*==.*1|Sv32x4.*=.*1|MODE.*8.*Sv39|gxl.*MODE|fct
  l.*gxl.*iohgatp
------------------------------------------------------------
[bug_confirmed] hw/riscv/riscv-iommu.c:785-789  riscv_iommu_validate_device_ctx
  Line 786 compares fsc_mode against RISCV_IOMMU_CAP_SV32 (BIT_ULL(8)=256)
  instead of RISCV_IOMMU_DC_FSC_IOSATP_MODE_SV32 (=8). The condition 'fsc_mode
  == RISCV_IOMMU_CAP_SV32' is always false, making the SXL=1 first-stage SV32
  capability check dead code. Any fsc_mode value (including unsupported modes)
  passes validation when SXL=1. The validate_process_ctx() function (line 853)
  correctly uses RISCV_IOMMU_DC_FSC_IOSATP_MODE_SV32 for the same check.

[potential_risk] hw/riscv/riscv-iommu.c:747-757  riscv_iommu_validate_device_ctx
  validate_device_ctx() validates only BARE-mode interactions with T2GPA and
  MSIPTP but does NOT validate whether the G-stage (IOHGATP) mode value
  (8/9/10) is supported by s->cap hardware capabilities or within valid range.
  By contrast, first-stage (FSC) mode validation is performed at lines
  759-808. G-stage mode validation is deferred to the actual page-table walk
  in riscv_iommu_spa_fetch() and pdt_memory_read(), which catch unsupported
