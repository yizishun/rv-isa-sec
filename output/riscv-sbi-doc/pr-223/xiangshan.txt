PR #223  target=xiangshan  overall=compliant
Spec: Hardware NMI routing must forward all unrecognized/local NMI sources to M-mode firmware so the SSE unknown NMI event can be injected to S-mode; dropping or maskable-routing of unknown NMI causes constitutes a function loss where S-mode is never notified of the event
Violation:
  In XiangShan RTL, when the processor receives an NMI signal from an
  unrecognized/local NMI source (mnmi CSR or external pin) and the M-mode trap
  handler either (a) fails to correctly identify and forward the unknown NMI
  via the SSE mechanism to S-mode, or (b) S-mode CSR state (e.g., sstatus.SIE,
  sie) can suppress delivery of the SSE software interrupt that carries the
  unknown NMI event, or (c) the hardware NMI prioritization logic incorrectly
  routes the unknown NMI as maskable rather than non-maskable, causing it to
  be lost or deferred under normal interrupt masking
Consequence: function_loss
Pattern:
  Look for hardware NMI routing logic where (1) the NMI signal classification
  tree has an incomplete case/switch statement that drops unrecognized NMI
  cause encodings instead of forwarding them to the SSE handler as unknown,
  (2) the software interrupt (SSI) used for SSE injection is gated on
  sstatus.SIE or sie CSR bits allowing S-mode to unintentionally block the SSE
  notification, (3) the mnmi/mcause NMI cause field is compared against a
  fixed whitelist without a fallback 'unknown' bucket, or (4) the per-hart
  local event state is stored in a shared multi-hart structure without per-
  hart isolation in the CSR module or CLINT equivalent
