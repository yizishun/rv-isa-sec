PR #136  target=linux  overall=bug_confirmed
Spec: IDE stream Insecure transition asynchronously force-clears RP IDE keys from Enabled/Programmed state bypassing set_stop gate; kernel VMM must poll key status before issuing DMA or plaintext guest data traverses the PCIe link
Violation: In the Linux kernel (acting as CoVE-IO host supervisor domain manager / VMM), DMA operations are issued on a PCIe IDE stream whose Root Port IDE keys have been asynchronously cleared by an 'IDE stream Insecure' transition, without the kernel first re-verifying key state via sbi_covt_rp_ide_key_status()
Consequence: info_leak
Pattern: Stale IDE key state cached by VMM; DMA proceeds on IDE stream after asynchronous Insecure transition force-clears RP keys from Enabled state, bypassing the set_stop→clear gate
------------------------------------------------------------
[bug_confirmed] drivers/pci/ide.c:687-707  pci_ide_stream_enable
  pci_ide_stream_enable() performs a one-shot PCI_IDE_SEL_STS_STATE check at enable time (lines 701-703), then caches 'enable=1' in the settings descriptor. After enable returns success, there is no mechanism to re-verify that IDE RP keys remain in the Secure state before issuing subsequent DMA. The kernel-doc at line 681-682 explicitly acknowledges this gap: 'the state may go insecure at any point after returning 0' and delegates recovery to asynchronous error reporting (AER). In the CoVE-IO threat model, the Secure-IO Manager can asynchronously force-clear RP IDE keys via an 'IDE stream Insecure' transition, and DMA that arrives between the key-clear and AER processing will leak plaintext on a stream believed to be encrypted. The spec-required sbi_covt_rp_ide_key_status() gate before DMA issuance is entirely absent from this kernel tree.

[potential_risk] drivers/crypto/ccp/sev-dev-tsm.c:56-69  stream_enable
  The SEV-TIO TSM driver's stream_enable() calls pci_ide_stream_enable() on both the Root Port and the Endpoint, but never installs a re-verification gate for subsequent DMA operations. After both enables succeed, the driver assumes the stream remains Secure indefinitely. If the platform TSM (acting as CoVE-IO Secure-IO Manager) asynchronously revokes the IDE stream keys, the RP hardware will clear them but the kernel's in-memory state (settings->enable == 1) will remain stale. Subsequent DMA on this stream will proceed through the IOMMU with the kernel believing the stream is still IDE-protected.

[potential_risk] drivers/pci/ide.c:596-634  pci_ide_stream_setup
  pci_ide_stream_setup() programs the stream_id into the SEL_CTL register (line 632: set_ide_sel_ctl with enable=false) before key programming, with the comment at lines 628-631 noting 'Setup control register early for devices that expect stream_id is set during key programming.' However, the stream_id is written unconditionally without any prior key-status verification. In a CoVE-IO scenario, if keys were asynchronously cleared between a previous teardown and this setup, writing the stream_id into SEL_CTL could interact with stale/broken key state. The setup flow has no sbi_covt_rp_ide_key_status() gate before writing stream configuration registers.

[compliant] drivers/pci/ide.c:364-385  pci_ide_stream_release
  pci_ide_stream_release() implements proper reverse-order teardown: disable RP before EP, teardown RP before EP. This ensures the stream is fully quiesced before freeing resources. The disable-teardown-unregister-free sequence is correct for normal stream destruction.
