PR #825  target=linux  overall=potential_risk
Spec: Fast interrupts (sfie/mfie) bypass the global interrupt-enable bits (sie/mie) when IPRIO < FITHRESHOLD, breaking the kernel invariant that sie=0 guarantees no interrupt delivery
Violation: The kernel disables S-mode interrupts (sstatus.sie=0) to enter a critical section, but sipreemptcfg.sfie remains 1 and mipreemptcfg.fithresh is configured such that a pending interrupt has IPRIO < FITHRESHOLD. The fast interrupt fires despite sie=0, preempting the kernel critical section. Additionally, when the kernel writes sfie=0 to disable fast interrupts, the hardware silently clears sie=0 as a side-effect, potentially leaving interrupts disabled after the kernel expected to re-enable them.
Consequence: race_condition
Pattern: csr[cw].*sstatus.*sie|csr[cw].*sipreemptcfg|__disable_irq|local_irq_disable|arch_local_irq_disable

  arch_local_irq_disable() clears only sstatus.SIE (csr_clear CSR_STATUS, SR_IE). It does not write sipreemptcfg.sfie=0. [potential_risk] arch/riscv/include/asm/irqflags.h:49-52  arch_local_irq_restore
  arch_local_irq_restore() only restores sstatus.SIE. If the kernel ever added SMNIP support and wrote sfie=0 before a critical section (to prevent fast-interrupt preemption), the hardware would silently clear sie=0 as a RISC-V spec side-effect. On restore, re-setting sie would leave sfie still at 0 — fast interrupts would remain disabled, potentially causing missed interrupts and denial of service. This code path is currently safe only because the kernel never touches sfie.
