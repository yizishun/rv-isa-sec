PR #730  target=qemu  overall=compliant
Spec: Nested exception during Smip interrupt trap entry must preserve original xepc/mnepc value pointing to the first trap; overwriting with the second exception's PC destroys the guest's ability to resume the original interrupt handler, causing unrecoverable state loss
Violation: When QEMU's trap delivery logic overwrites xepc/mnepc with the PC of a synchronous exception that fires during Smip interrupt trap side effects, instead of preserving the original trap's exception PC as required by the spec
Consequence: denial_of_service
Pattern: riscv_cpu_do_interrupt.*set_field.*sepc|riscv_cpu_do_interrupt.*env->mepc|riscv_cpu_do_interrupt.*env->mnepc
------------------------------------------------------------

No re-entrancy risk: riscv_cpu_do_interrupt is called once per trap synchronously from the TCG execution loop; QEMU's single-threaded vCPU model prevents any concurrent modification of env->pc between function entry and this assignment.

[compliant] hw/riscv/riscv-iommu.c:753-757  riscv_iommu_validate_device_ctx
  New validation check is a security hardening, not a vulnerability. When second-stage translation is BARE (no address translation) but MSI translation mode is not OFF, the IOMMU now rejects the device context as invalid. This prevents undefined runtime behavior where MSI PTE page-table walks would occur without a valid translation regime, which could lead to guest-observable misbehavior or information leaks via fault queues.

[potential_risk] hw/riscv/riscv-iommu.c:739-745  riscv_iommu_validate_device_ctx
  The existing MSI mode validation (lines 739-744) only runs when CAP_MSI_FLAT is set. The new check (lines 753-756) runs unconditionally regardless of MSI capability flags. There is a gap: if CAP_MSI_MRIF is set but CAP_MSI_FLAT is not, MSI MRIF mode can be configured, and the unconditional check still catches BARE+GATP mismatch. However, the unconditional check uses MSIPTP_MODE_OFF comparison which only differentiates OFF vs non-OFF — it doesn't validate MRIF-specific modes (there is no MSIPTP_MODE_MRIF defined in the bits header, only OFF=0 and FLAT=1). If MRIF mode uses a different MSIPTP_MODE encoding, it wouldn't be caught by the mode-range check at lines 741-742. This is a spec-compliance gap rather than an exploitable bug: a misconfigured MRIF device context would have undefined behavior at runtime.
