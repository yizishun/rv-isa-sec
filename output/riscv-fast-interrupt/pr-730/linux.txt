PR #730  target=linux  overall=potential_risk
Spec: Smip context-save faults set xepc to the original trap PC (not the fault PC), so unless the kernel's entry code preserves the ordering guarantee (registers-before-sp) and verifies double-trap support, a mid-save exception corrupts resumed state
Violation: Linux kernel trap entry/exit code on RISC-V executes the Smip context save/restore sequence (saving registers then adjusting sp) but either (a) reorders register saves after the stack pointer adjustment, or (b) fails to handle the case where a synchronous exception during save leaves xepc pointing to the original trap rather than the faulting instruction, causing resumption at a stale context and potential double-execution or register corruption on the return path
Consequence: data_corruption
Pattern: sp adjustment before full register save in trap entry; assumption that mid-save faults are unrecoverable without checking double-trap capability; missing misa.Smip or double-trap feature test before emitting Smip-style save sequences
------------------------------------------------------------

  new_vmalloc_check macro handles vmalloc page faults during trap entry by doing sret (line 85) to retry the faulting instruction. On Smip hardware where save sequence reordering matters, this re-execution is blind: it does not check whether preceding instructions in the save sequence (like csrrc CSR_STATUS at line 183) have side effects that make re-execution non-idempotent.
