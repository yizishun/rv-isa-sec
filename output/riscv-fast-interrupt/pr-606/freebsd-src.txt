PR #606  target=freebsd-src  overall=bug_confirmed
Spec: FreeBSD's RISC-V trap dispatch and INTC driver assume legacy CLINT-mode interrupt delivery where timer (STI), software (SSI), and external (SEI) interrupts arrive with distinct scause codes; ACLIC mode unification collapses all interrupts to SEI scause=9, causing timer and IPI interrupts to be silently redirected to the external interrupt handler chain, hanging the scheduler tick and SMP coordination
Violation: FreeBSD's intc.c (INTC_NIRQS=16, legacy CLINT-mode controller) and the trap dispatchers do_trap_supervisor/do_trap_user dispatch interrupts by reading frame->tf_scause & SCAUSE_CODE to identify the major interrupt source (1=SSI, 5=STI, 9=SEI). When ACLIC mode is active (eidelivery CSR set), all major interrupts—timer, software, and external—are forwarded to ACLIC and arrive through a single scause code (9, supervisor external interrupt). The intc_intr() handler at intc.c:276 would map every interrupt to scause code 9 and forward it to the external interrupt handler chain, silently discarding timer and IPI interrupts. Conversely, sbi_ipi.c:sbi_ipi_intr() at sbi_ipi.c:106 clears SIP_SSIP directly via csr_clear(sip, SIP_SSIP), which is meaningless in ACLIC mode where the SSIP bit no longer drives interrupt delivery. No code path in FreeBSD's RISC-V port checks eidelivery or ACLIC state before assuming legacy interrupt semantics.
Consequence: denial_of_service
Pattern: tf_scause.*SCAUSE_CODE|csr_clear.*sip.*SIP_SSIP|csr_.*sip|intc_intr|frame->tf_scause & SCAUSE_CODE|sbi_ipi_intr|SSIP|STIP

[potential_risk] sys/riscv/riscv/intc.c:199-209  intc_enable_intr
  intc_enable_intr() uses csr_set(sie, 1ul << irq) and intc_disable_intr() uses csr_clear(sie, 1ul << irq) to control interrupt delivery. Under AIA/ACLIC, the sie CSR bits no longer gate interrupt delivery—interrupt routing is managed by the ACLIC's IDC (interrupt delivery control) registers instead. Manipulating sie.SSIE/sie.STIE/sie.SEIE has no effect on actual interrupt delivery in AIA mode, leaving interrupts potentially uncontrollable.

[bug_confirmed] sys/riscv/riscv/sbi_ipi.c:96-126  sbi_ipi_intr
  sbi_ipi_intr() at line 106 calls csr_clear(sip, SIP_SSIP) to clear the software interrupt pending bit. In AIA/ACLIC mode, the SIP_SSIP bit no longer drives interrupt delivery—the ACLIC manages pending state internally. Clearing SIP_SSIP via csr_clear is a no-op that does not clear the actual interrupt source, potentially causing a tight loop of spurious interrupt re-delivery. Furthermore, the sbi_ipi driver registers itself on IRQ_SOFTWARE_SUPERVISOR (IRQ 1 in intc's isrcs[]), but on ACLIC systems with eidelivery set, the intc_intr() handler would route all interrupts to isrcs[9] (SEIP), so sbi_ipi_intr() would never be called at all.
