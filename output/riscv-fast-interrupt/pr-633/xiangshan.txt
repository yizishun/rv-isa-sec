PR #633  target=xiangshan  overall=compliant
Spec: Operator precedence bug in CLIC preemption formula (PR #633): iprio[i] & NIPPRIO_MASK >= xithreshold evaluates as iprio[i] & (NIPPRIO_MASK >= xithreshold) in HDL, turning xithreshold into a no-op and allowing unconditional preemption from any non-zero priority interrupt
Violation: In XiangShan RTL, any CLIC/IMSIC preemption threshold comparator that directly transcribes the old spec formula 'iprio[i] & NIPPRIO_MASK >= xithreshold' into Chisel/Verilog with HDL-native operator precedence will produce: iprio[i] & (NIPPRIO_MASK >= xithreshold). Since NIPPRIO_MASK is a wide constant (e.g., 0xFF for 8-bit priority) and xithreshold is a CSR-programmed small value, (NIPPRIO_MASK >= xithreshold) is a constant true, reducing the preemption condition to 'iprio[i] != 0' — any non-zero-priority pending interrupt preempts the current handler regardless of the threshold CSR value. Specifically in XiangShan's InterruptFilter, the IpriosSort/minSelect infrastructure at lines 162-189 performs priority comparison (prioNum <= comparison) but feeds into external IMSIC hardware (marked 'Todo: IMSIC' at CSRAIA.scala:197). If that external IMSIC threshold comparator uses the buggy precedence, the xithreshold CSR becomes non-functional for preemption gating.
Consequence: privilege_escape
Pattern: xithreshold.*>|>=|threshold.*prio|preempt.*threshold|nipprio.*mask.*threshold|prio.*>=.*threshold|priority.*>=.*thresh
