PR #735  target=freebsd-src  overall=potential_risk
Spec: Ssip sipopret unconditionally sets SUM during register restore; a user-controlled invalid ssp causes a page fault while SUM=1, tripping FreeBSD's KASSERT(SUM==0) in do_trap_supervisor() and panicking the kernel from unprivileged userspace
Violation: During Ssip fast interrupt pop (sipopret), sstatus.SUM is unconditionally set before loading GPRs from the interrupted context's stack. If the interrupted context's ssp points to an unmapped page (e.g., a user process deliberately sets sp to an invalid address then triggers a fast interrupt via a tight timer loop), the `lw`/`ld` during sipopret takes a synchronous page fault. The trap handler in do_trap_supervisor() enters with SUM=1, violating the KASSERT at sys/riscv/riscv/trap.c:315, causing a kernel panic even though the faulting condition (bad user stack pointer) should at worst kill the offending process.
Consequence: denial_of_service
Pattern: sipopret.*SUM|ssp.*unmapped.*fast.interrupt|sstatus.*SUM.*assert.*trap|tf_sstatus.*SUM
------------------------------------------------------------
[potential_risk] sys/riscv/riscv/trap.c:306-317  do_trap_supervisor
  KASSERT at line 315 requires SUM==0 on entry to do_trap_supervisor(). If Smip fast interrupt support is added, sipopret sets SUM to access the interruptee's shadow-stack (ssp). A page fault during sipopret (e.g., user process sets sp to unmapped address, then a fast timer interrupt fires) would enter do_trap_supervisor() with SUM=1, triggering this KASSERT and causing a kernel panic (DoS) instead of a graceful SIGBUS/SIGSEGV to the offending process. The KASSERT needs to be relaxed or a special fault-recovery path added for sipopret faults.
  | KASSERT((csr_read(sstatus) & (SSTATUS_SUM)) == 0,
  |     ("Came from S mode with SUM enabled"));

[potential_risk] sys/riscv/riscv/trap.c:379-397  do_trap_user
  Analogous KASSERT on SUM==0 in do_trap_user() at line 396. While sipopret faults would reach do_trap_supervisor() (not do_trap_user()), any Smip fast-interrupt return path that involves user-mode transitions could trigger this assert as well, representing a secondary DoS surface.
  | KASSERT((csr_read(sstatus) & (SSTATUS_SUM)) == 0,
  |     ("Came from U mode with SUM enabled"));

[compliant] sys/riscv/riscv/exception.S:105-109  save_registers
  Current save_registers macro for supervisor-mode exceptions (mode=1) explicitly clears SUM via `csrc sstatus, t0` at line 107-108. This is correct for the standard (non-Smip) interrupt model and ensures traps into do_trap_supervisor() enter with SUM=0. However, if Smip sipopret is added, the SUM set by sipopret would already be active before save_registers runs, and the page fault taken during sipopret's load phase would occur in the window between SUM being set and save_registers clearing it, making this clearing mechanism insufficient to protect against the sipopret-fault scenario.
  | li    t0, SSTATUS_SUM
  | carc   sstatus, t0

[potential_risk] sys/riscv/riscv/exception.S:219-225  cpu_exception_handler_supervisor
  The supervisor exception handler uses `sret` for return. When Smip is implemented, this path may need to be altered to use `sipopret` (for fast interrupt pop) or `mnreti` (for nested fast interrupts). The current `sret`-only path has no awareness of ssp/Smip state and would not correctly resume a sipopret sequence that faulted mid-pop. The Smip spec requires sipopret to be restartable, meaning the trap handler must not blindly use sret for sipopret faults.
  | ENTRY(cpu_exception_handler_supervisor)
  |     save_registers 1
  |     mv    a0, sp
  |     call  _C_LABEL(do_trap_supervisor)
  |     load_registers 1
  |     sret
