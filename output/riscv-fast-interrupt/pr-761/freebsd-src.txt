Spec: Off-by-one in ACLIC xiselect iprio/sourcecfg range: spec previously allowed 257 entries (0x1000–0x1100) but only 256 defined; FreeBSD has no ACLIC code yet, but future CLIC driver or bhyve VMM emulation using the old upper bound would read/write beyond the register table at xiselect=0x1100
Violation: FreeBSD kernel or bhype VMM code implementing ACLIC (Smidctrl) indirect CSR access using the old, erroneous xiselect range 0x1000–0x1100 (inclusive upper bound) would reference one past the valid acliciprio/aclicsourcecfg table (256 entries, xiselect 0x1000–0x10FF), causing out-of-bounds register access or incorrect illegal-instruction traps on xireg4–xireg6 at the boundary value 0x1100
Consequence: data_corruption
Pattern: xiselect bounds check with 0x1100 as inclusive upper limit instead of 0x10FF; off-by-one in ACLIC indirect CSR select range validation

[compliant] N/A — feature absent from entire FreeBSD source tree:0-0  N/A
  FreeBSD kernel and bhyve VMM contain zero implementation of ACLIC (Smidctrl/Ssidctrl) indirect CSR access. No code path exists that validates xiselect ranges for acliciprio or aclicsourcecfg table lookups — the entire Smidctrl/Ssidctrl feature (indirect CSR access via xiselect/xireg to hart-local APLIC domain registers) is unimplemented. Therefore the off-by-one xiselect bounds check (0x1100 as inclusive upper limit instead of 0x10FF) cannot exist in this codebase. The vulnerability pattern described in the spec — xiselect bounds check with 0x1100 as inclusive upper limit causing out-of-bounds register access or incorrect illegal-instruction traps on xireg4–xireg6 — has no code to manifest in.
