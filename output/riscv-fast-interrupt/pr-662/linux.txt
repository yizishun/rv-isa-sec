PR #662  target=linux  overall=bug_confirmed
Spec: eidelivery CSR becomes read-only under Smidctrl/Ssidctrl plus extension rename Smaclic→Smidctrl breaks kernel feature probing; silent write drops risk interrupt delivery misconfiguration across context-switch/resume paths
Violation: Linux kernel writes to eidelivery CSR expecting to configure or dynamically change the interrupt delivery mode (e.g., during suspend/resume, kexec, CPU hotplug, or KVM virtual IRQCHIP context switch), but when Smidctrl/Ssidctrl is present, eidelivery is read-only fixed to 0x20000000; the write is silently ignored, and the kernel proceeds with a mismatched assumption about whether interrupts are delivered via MSI (1), PLIC/APLIC direct (0x40000000), or ACLIC (0x20000000) semantics.
Consequence: denial_of_service
Pattern: csr_write.*eidelivery|eidelivery.*csr_write|write.*EIDELIVERY|EIDELIVERY.*write|smaclic|ssaclic|smidctrl|ssidctrl|riscv_isa_extension.*aclic

[bug_confirmed] arch/riscv/kvm/aia_imsic.c:458-464  imsic_vsfile_local_rw
  KVM VCPU context-switch path: when a guest writes to VS-level eidelivery via imsic_vsfile_local_rw(), the kernel writes the guest-provided value directly to hardware via imsic_vs_csr_write(IMSIC_EIDELIVERY, ...). On ACLIC hardware with Ssaclic/Smidctrl, VS-level eidelivery is read-only. The hardware ignores the write, but KVM caches the guest's write and subsequent reads return the cached value, creating a divergence between what the guest sees through KVM and what the hardware actually enforces. This is a virtualization escape vector: a guest can believe it configured MSI delivery mode while the hardware is in ACLIC delivery mode.
