PR #732  target=xiangshan  overall=compliant
Spec: Spec clarifies xithreshold must NOT be raised on synchronous exceptions (only on interrupts), but xpistatus.pithreshold must still be captured on all traps; M-mode double traps must preserve pithreshold. Incorrect CSR microarch update on exception entry corrupts threshold lineage across nested traps, causing wrong interrupt priority threshold after xRET unwind, enabling lower-priority interrupt injection into higher-privilege handler context.
Violation: In XiangShan RTL, when a synchronous exception trap is taken (e.g., page fault, illegal instruction), if the CSR module incorrectly sets xithreshold to the exception's IPRIO level—treating exceptions identically to interrupts—the hardware violates the spec rule that 'synchronous exceptions do not modify the value of xithreshold.' Additionally, if the trap-entry microcode fails to capture the current xithreshold into xpistatus.pithreshold on exception entry (as now required: the write to pithreshold occurs for ALL traps, not just interrupts), a subsequent xRET will restore a stale/wrong threshold value when unwinding through nested trap contexts. Further, if an M-mode double trap inadvertantly overwrites xpistatus.pithreshold—violating the new rule that it remains unchanged—the original threshold lineage from the pre-double-trap context is permanently lost, causing incorrect threshold restoration after xRET unwinds past the double-trap boundary.
Consequence: privilege_escape
Pattern: trap_entry.*xithreshold.*IPRIO|exception.*ithreshold_write|double_trap.*pithreshold|synchronous_exception.*ithreshold|CSR_xithreshold_exception_update
