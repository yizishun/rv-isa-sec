PR #819  target=xiangshan  overall=potential_risk
Spec: Missing mstateen0.ACLIC gate on seivt CSR allows S-mode to read/write the supervisor external interrupt vector table even when M-mode has explicitly disabled ACLIC- controlled CSRs, bypassing the state-enable access-control hierarchy.
Violation: In the XiangShan CSR access-control module (likely CSR.scala or a StateEnable checker), when mstateen0.ACLIC (bit 53) is 0 and S-mode executes a CSR read/write to seivt, the hardware permits the access instead of raising an illegal-instruction exception — because seivt was omitted from the whitelist of CSRs gated by the ACLIC bit, while only sivt is checked.
Consequence: privilege_escape
Pattern: mstateen0.*ACLIC|stateen.*ACLIC|isAccessControlled.*seivt|seivt.*mstateen|CSR.*0x[0-9a-fA-F]+.*seivt
------------------------------------------------------------
[potential_risk] src/main/scala/xiangshan/backend/fu/NewCSR/StateEnBundle.scala:27-38  Mstateen0Bundle
  The Mstateen0Bundle does NOT define an ACLIC bit (bit 53). The entire ACLIC feature for gating interrupt-file CSR access is not yet implemented in this version of the RTL. The existing stateen bits cover SE0(63), ENVCFG(62), CSRIND(60), AIA(59), IMSIC(58), CONTEXT(57), P1P13(56), and C(0), with bits 55-48 entirely unallocated. When ACLIC is added in the future, the whitelist-based access-control pattern means any new CSR not explicitly added to the gating check will be silently accessible.

[potential_risk] src/main/scala/xiangshan/backend/fu/NewCSR/CSRPermitModule.scala:288-291  MLevelPermitModule
  The access-control logic uses a whitelist pattern: access is blocked ONLY if a CSR explicitly matches a gated category. The final OR-reduce at line 290-291 combines all individual gating checks. Any CSR not matching these checks is permitted by default. This pattern is inherently fragile—adding a new stateen bit (e.g., ACLIC) requires also adding explicit CSR-address-match logic for every CSR it should gate. Omitting even one CSR creates a privilege-escalation path. This is exactly the vulnerability class the security spec warns about for seivt.
