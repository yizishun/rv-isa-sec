PR #819  target=linux  overall=potential_risk
Spec: seivt was missing from mstateen0.ACLIC access-control gating, so clearing mstateen0.ACLIC did not disable external interrupt vectoring for S-mode guests, breaking the hypervisor invariant that mstateen0.ACLIC=0 fully disables ACLIC
Violation: Hypervisor (e.g., KVM in HS-mode) clears mstateen0.ACLIC (bit 53) to disable ACLIC for a guest VS-mode vCPU, expecting that all ACLIC-dependent CSRs are inaccessible. Hardware built to the pre-fix spec does not trap guest access to seivt when mstateen0.ACLIC=0, allowing the guest to read/write the external interrupt vector table address while sivt, steivt, and snivt are correctly blocked. This inconsistent gating means the hypervisor's assumption that clearing one bit disables the entire ACLIC feature for the guest is violated.
Consequence: privilege_escape
Pattern: CSR_SEIVT CSR_SIVT mstateen0 ACLIC kvm_riscv_vcpu kvm_arch_vcpu kvm_riscv_switch

[potential_risk] arch/riscv/kvm/vcpu.c:564-572  kvm_riscv_vcpu_setup_config
  hstateen0 configuration during VCPU setup enables only AIA-related bits (58-60), HSENVCFG (62), and SSTATEEN0 (63) — no ACLIC bit (53). If the hypervisor intends to expose ACLIC to the guest, it has no mechanism to set or clear the ACLIC control bit. Conversely, if the hypervisor wants to explicitly disable ACLIC for a guest by clearing bit 53, it cannot do so through the kernel's hstateen0 framework. On pre-fix hardware, clearing all unused hstateen0 bits would leave bit 53 at its hardware-default value, which may or may not disable ACLIC — but either way seivt is not properly gated.
