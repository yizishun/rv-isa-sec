PR #718  target=opensbi  overall=potential_risk
Spec: Smnip trap entry must set mithreshold to IPRIO (max priority) not iprio[i] (specific interrupt priority) to ensure all interrupts are masked during M-mode ISR execution, preventing interrupt-induced race conditions during firmware critical sections (PMP reconfig, domain switch, HSM state transitions)
Violation: In OpenSBI, when the M-mode CLIC trap handler takes an interrupt i and writes mithreshold with iprio[i] (the specific interrupt's priority) instead of IPRIO (the maximum supported priority level), higher-priority interrupts remain unmasked during M-mode interrupt processing, violating the spec-mandated blanket masking of all interrupts on trap entry.
Consequence: race_condition
Pattern: pattern: CSR write to mithreshold/mintthresh in M-mode trap entry that sources the value from the triggering interrupt's priority (iprio[i], TOPI priority field, or equivalent) rather than the architectural IPRIO constant; also grep for any masking of iprio[i] with non-maximum bounds before writing mithreshold

  The M-mode AIA interrupt handler reads CSR_MTOPI but shifts away the IPRIO field (low 8 bits, TOPI_IPRIO_MASK) and only extracts the IID. It never writes the mithreshold CSR. Under Smnip hardware, the hardware automatically sets xithreshold = iprio_of_interrupt on trap entry (ACLIC spec §Trap behavior), which masks equal-or-lower-priority interrupts but leaves higher-priority interrupts unmasked. OpenSBI currently runs with MIE=0 during M-mode trap processing, so no preemption is possible regardless of threshold. However, if OpenSBI were ever to enable MIE during M-mode IRQ processing (e.g., for nested interrupt handling), higher-priority interrupts would preempt the handler, potentially corrupting shared M-mode state.
