PR #668  target=freebsd-src  overall=bug_confirmed
Spec: Latent: using raw iprio[i] instead of spec-mandated IPRIO (xtopi-reported value) for threshold comparison could unmask interrupts that should be disabled when iprio[i] > 255 or iprio[i]=0, but FreeBSD's hardcoded priority-1/zero-threshold avoids triggering this semantic gap
Violation: FreeBSD kernel code that reads raw interrupt priority configuration (iprio[i]) directly from APLIC_TARGET or source priority registers and compares it against the hart's xithreshold value bypasses the IPRIO mapping mandated by the spec. Specifically: (1) iprio[i] > 255 is not capped to IPRIO=255, causing threshold comparisons with values exceeding the 8-bit threshold register width; (2) iprio[i]=0 is treated uniformly as the lowest priority, ignoring the platform-defined default-priority semantics (IPRIO=0 for interrupts pinned higher than machine external, IPRIO=255 otherwise). In FreeBSD, this is currently latent because all interrupt sources are programmed with priority=1 and threshold=0, but any future dynamic-priority or threshold-based interrupt masking code would be affected.
Consequence: denial_of_service
Pattern: iprio[i].*xithreshold|APLIC_TARGET.*PRIO|sourcecfg.*threshold|(raw.*priority.*threshold)|(unsigned long|uint32_t).*target.*>>.*PRIO_SHIFT
