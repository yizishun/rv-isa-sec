PR #700  target=freebsd-src  overall=bug_confirmed
Spec: Smip reorders cspspush after GPR save: x10-x15 now land on the interrupted context's kernel stack; FreeBSD's cpu_switch and signal-delivery must treat that stack region as a hardware-written trapframe extension or risk register corruption on thread resume
Violation: In the FreeBSD kernel, if a thread is context-switched out after CLIC trap entry saves x10-x15 on the interrupted thread's kernel stack (before cspspush), and the kernel later resumes that thread via cpu_switch() without having preserved both (a) the xsp CSR value in struct pcb and (b) the integrity of the stack region holding the hardware-saved x10-x15—for instance, if the kernel stack is partially reclaimed during swapout, or if the signal-delivery path overwrites those stack slots while setting up a sigframe trampoline—then cspspop followed by hardware register restore loads corrupted GPRs from the wrong stack location
Consequence: data_corruption
Pattern: cspspush|cspspop|xsp|smip|cpu_switch.*stack|savectx.*x\d\d|sigframe.*sp|pcb_regs
------------------------------------------------------------
[bug_confirmed] sys/riscv/include/pcb.h:42-54  struct pcb
  struct pcb has no pcb_xsp field. The per-thread saved context block stores pcb_ra, pcb_sp, pcb_gp, pcb_tp, pcb_s[12], pcb_x[32][2], pcb_fcsr, pcb_fpflags, pcb_onfault — but no shadow stack pointer. Without this field, no context-switch path (cpu_switch, cpu_throw, savectx) can preserve the xsp CSR across thread deschedule/resume. If Smip were active, a thread switched out after cspspush would resume with a stale xsp from the incoming thread's prior execution, creating a mismatched (sp, xsp) pair.

[bug_confirmed] sys/riscv/vmm/vmm_switch.S:67-84  vmm_switch
  vmm_switch CSR swap sequence uses csrrw to atomically exchange host↔guest sstatus, hstatus, scounteren, sscratch, stvec, and sets sepc — but does not swap xsp or any Smip CSR.
