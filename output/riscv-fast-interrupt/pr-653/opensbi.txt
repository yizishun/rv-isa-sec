PR #653  target=opensbi  overall=bug_confirmed
Spec: Smip makes interrupt-entry context push automatic (hardware saves x10-x15 + adjusts SP before handler fetch); returning with mret instead of ipopxret leaks the auto-pushed stack frame and leaves x10-x15 unrestored, corrupting the preempted context on return to S-mode
Violation: OpenSBI M-mode trap handler returns from interrupts using mret without first restoring the x10-x15 registers and stack frame that Smip hardware automatically pushed on interrupt entry; the handler is also unaware that only interrupts (not exceptions) receive this auto-save, so a unified trap path assumes an incorrect stack layout for synchronous exceptions
Consequence: data_corruption
Pattern: mret used as interrupt return instead of ipopxret when Smip is implemented; trap handler entry that does not distinguish interrupt vs exception for expected stack frame layout; manual CSR save/restore of mepc/mstatus that conflicts with hardware-preserved values during tail-chaining
------------------------------------------------------------
[bug_confirmed] /home/yzs/riscv/opensbi/firmware/fw_base.S:690-690  _trap_handler
  mret is used unconditionally as the interrupt return instruction. When the Smip extension is implemented, M-mode interrupt handlers MUST use mipopret (ipopxret) to return from interrupts, because mipopret is the only instruction that (a) restores the hardware-auto-saved x10-x15 registers from the stack, (b) adjusts sp to destroy the hardware-created frame, and (c) conditionally swaps the stack pointer. Using mret skips all stack-frame teardown and register restore that Smip hardware performed on entry, causing register corruption (x10-x15 hold stale/zero values) and stack corruption (sp is misaligned and leaking frames).

  | 	TRAP_SAVE_GENERAL_REGS_EXCEPT_SP_T0
  | 	...
  | 	mret

[potential_risk] /home/yzs/riscv/opensbi/firmware/fw_base.S:393-401  _start_warm (trap setup path)
  CSR_MTVEC is set to a single unified trap handler (_trap_handler or _trap_handler_hyp) without Smip detection. The code loads the handler address via `lla a4, _trap_handler` and writes it directly to CSR_MTVEC. Since the label is 8-byte aligned, mtvec.MODE=0 (Direct mode). The Smip spec explicitly states: 'As this extension modifies interrupt trap behavior but not the behaviour of synchronous exception traps, it should only be used in interrupt handling modes that provide separate entry points for interrupt and synchronous exception traps. Specifically, mtvec.mode = 0 (direct) is incompatible.' A platform implementing Smip would need mtvec.MODE=1 (Vectored) with separate handler vectors for interrupts vs exceptions, because the hardware auto-save only occurs on interrupts, not on synchronous exceptions.

[potential_risk] /home/yzs/riscv/opensbi/firmware/fw_base.S:545-577  TRAP_SAVE_GENERAL_REGS_EXCEPT_SP_T0 (macro)
  This macro unconditionally saves all general-purpose registers including x10-x15 (a0-a5) to the software trap frame, for both interrupts and synchronous exceptions. Under Smip, hardware has already auto-saved x10-x15 to the interrupted context's stack on interrupt entry (aclic.adoc lines 1478-1481). The macro does not distinguish interrupt from exception, so for Smip interrupts the software save is redundant at best but creates a conflicting stack layout: the software trap frame has x10-x15 at the software-managed SP offset, while the hardware frame has them at the interrupted context's SP minus the hardware frame. If the C handler modifies the software-saved copies, those modifications are lost because mipopret restores from the hardware frame. Conversely, if mret is used (as currently), the hardware-saved registers are ignored and only software-saved values are restored—both paths produce inconsistency.
  | REG_S	a0, SBI_TRAP_REGS_OFFSET(a0)(sp)
  | REG_S	a1, SBI_TRAP_REGS_OFFSET(a1)(sp)
  | REG_S	a2, SBI_TRAP_REGS_OFFSET(a2)(sp)
  | REG_S	a3, SBI_TRAP_REGS_OFFSET(a3)(sp)
  | REG_S	a4, SBI_TRAP_REGS_OFFSET(a4)(sp)
  | REG_S	a5, SBI_TRAP_REGS_OFFSET(a5)(sp)

[potential_risk] /home/yzs/riscv/opensbi/firmware/fw_base.S:647-660  TRAP_RESTORE_MEPC_MSTATUS (macro)
  This macro unconditionally writes software-saved values to CSR_MSTATUS and CSR_MEPC via csrw before returning. Under Smip tail-chaining (aclic.adoc lines 1531-1540), the hardware may abort an in-progress mipopret and start processing a new interrupt, during which 'xepc, xpistatus remain unchanged'—they preserve the values from the first interrupt. By performing explicit csrw to MSTATUS and MEPC from the software trap frame, this macro overwrites the hardware's preserved epc/pistatus, destroying the correct return target for tail-chained interrupts. This would cause tail-chained interrupts to return to the wrong PC and with incorrect privilege state.
  | REG_L	t0, SBI_TRAP_REGS_OFFSET(mstatus)(a0)
  | csrw	CSR_MSTATUS, t0
  | REG_L	t0, SBI_TRAP_REGS_OFFSET(mepc)(a0)
  | csrw	CSR_MEPC, t0
