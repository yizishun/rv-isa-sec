PR #714  target=qemu  overall=potential_risk
Spec: Missing mstateen0 bit 53 (ACLIC) definition and access gating in QEMU emulation undermines Smstateen-based isolation of ACLIC CSRs from S-mode
Violation: QEMU does not define SMSTATEEN0_ACLIC at bit 53 in cpu_bits.h, does not include it in write_mstateen0's wr_mask, and has no smstateen_acc_ok check gating S-mode access to acliciprio/aclicsourcecfg CSRs. Consequently: (1) mstateen0 bit 53 is always read-as-zero/write-ignored (WARL-zero), so M-mode cannot grant S-mode access to ACLIC CSRs; (2) if ACLIC CSRs are emulated, S-mode access is either unconditionally allowed (missing trap) or unconditionally denied (breaking M-mode delegation).
Consequence: privilege_escape
Pattern: SMSTATEEN0_ACLIC.*(?:1ULL << 53)|mstateen0.*wr_mask.*53|smstateen_acc_ok.*aclic|acliciprio.*smstateen|aclicsourcecfg.*smstateen
------------------------------------------------------------
[potential_risk] target/riscv/cpu_bits.h:355-365  N/A (macro definitions)
  SMSTATEEN0_ACLIC bit 53 is not defined in cpu_bits.h. The ACLIC fast-interrupt spec (aclic.adoc:656) requires bit 53 of mstateen0 to control S-mode access to acliciprio/aclicsourcecfg CSRs when both Smstateen and ACLIC extensions are implemented. Currently QEMU does not emulate ACLIC CSRs, so bit 53 is implicitly read-as-zero/write-ignored (correct for no-ACLIC). However, if ACLIC CSR support is added in the future without also adding this bit, S-mode access to ACLIC CSRs would either be unconditionally allowed (privilege escape) or unconditionally denied (breaking M-mode delegation).
  | #define SMSTATEEN0_CS       (1ULL << 0)
  | #define SMSTATEEN0_FCSR     (1ULL << 1)
  | #define SMSTATEEN0_JVT      (1ULL << 2)
  | #define SMSTATEEN0_CTR      (1ULL << 54)
  | #define SMSTATEEN0_P1P13    (1ULL << 56)
  | ...no SMSTATEEN0_ACLIC at bit 53...

[potential_risk] target/riscv/csr.c:3459-3493  write_mstateen0
  write_mstateen0's wr_mask does not include SMSTATEEN0_ACLIC (bit 53). This is consistent with the missing define in cpu_bits.h. If ACLIC CSRs are later added, this function would fail to gate bit 53 writability, meaning even if bit 53 were defined, M-mode writes to bit 53 would be silently ignored (WARL-zero). Conditional inclusion (e.g., based on a future ext_smaclic property) would be needed, following the existing pattern for ext_ssaia gating SMSTATEEN0_AIA/IMSIC.

  |     wr_mask |= SMSTATEEN0_FCSR;
  | }
  | // missing: conditional wr_mask |= SMSTATEEN0_ACLIC

[compliant] target/riscv/csr.c:48-77  smstateen_acc_ok
  smstateen_acc_ok() is a generic gate function that checks env->mstateen[index] & bit. It correctly handles M-mode bypass, virt/hypervisor layering, and user-mode sstateen checks. No functional issue with this function itself — it would work correctly if SMSTATEEN0_ACLIC were defined and passed as the bit argument. The gap is that no code path calls smstateen_acc_ok(env, 0, SMSTATEEN0_ACLIC) for ACLIC CSR access gating.

[compliant] target/riscv/cpu_bits.h:355-365  N/A (macro definitions)
  QEMU currently does not implement any ACLIC CSRs (acliciprio, aclicsourcecfg, spistatus, sithreshold, sivt, seivt). Absent ACLIC emulation, the base Smstateen spec (smstateen.adoc line 138-140) is satisfied: bits controlling unimplemented state must be read-only zero, and bit 53 falls within the WPRI range (bits 3-53) per the base mstateen0 wavedrom layout. The current behavior — where bit 53 is implicitly ROZ because no write mask includes it — is technically spec-compliant for a non-ACLIC hart.

  | // bits 3-53 are WPRI in base spec; no ACLIC CSR support exists in QEMU
