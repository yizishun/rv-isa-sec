PR #781  target=linux  overall=potential_risk
Spec: Any CSR write to stvec without corresponding guarantee that the target page has S-mode execute permission via PMP/Smepmp creates a trap-loop DoS: the next interrupt/exception vector fetch faults on instruction access, which itself faults, crashing the kernel.
Violation: The kernel places the S-mode trap vector page (stvec) at a physical address where PMP/Smepmp does not grant S-mode execute permission — either during boot cpuidle (head.S PMPCFG write with X=0 at that region), through a context switch that changes stvec (KVM), or when M-mode firmware shares a CLIC vector table via xivt/xeivt without ensuring S-mode X permission on the shared table.
Consequence: denial_of_service
Pattern: csrw CSR_STVEC, <reg> | csr_write(CSR_STVEC, | csr_write(CSR_TVEC, | csr_write(CSR_VSTVEC,
------------------------------------------------------------

[potential_risk] arch/riscv/kvm/vcpu.c:607-607  kvm_arch_vcpu_load
  Writes CSR_VSTVEC from csr->vstvec, which is guest-owned CSR state saved at vcpu_put:675 via csr_read(CSR_VSTVEC). The host does NOT validate the guest's vstvec value before writing it to the hardware CSR. If a malicious guest sets vstvec.MODE=11 (CLIC/Smivt interrupt vector table mode), the hardware will switch to CLIC interrupt vectoring in VS-mode. While this does not directly violate the stvec/PMP spec (vstvec controls VS-mode, not host S-mode), the host has no CLIC-aware scause parsing at the trap exit path (line 856 reads CSR_SCAUSE without CLIC decoding), creating a guest-to-host confusion risk. However, this is primarily a KVM guest isolation issue, not a direct PMP-execute violation on the host stvec.
  | csr_write(CSR_VSTVEC, csr->vstvec);

[potential_risk] arch/riscv/include/asm/csr.h:321-321  
  CSR_STVEC (0x105) is defined but the CLIC/Smivt CSR constants CSR_SIVT (0x107) and CSR_SEIVT (0x108) are NOT defined anywhere in the kernel. Per the CLIC spec (aclic.adoc:1198-1202), these are the S-mode interrupt vector table base registers required for CLIC IVT mode (stvec.MODE=11). Without these definitions, the kernel structurally cannot validate or configure CLIC shared vector tables. If M-mode firmware shares a CLIC vector table via xivt/xeivt without S-mode X permission on the table memory, the kernel has no mechanism to detect or remediate this. The kernel is blind to CLIC vector table permission state.
  | #define CSR_STVEC 0x105
