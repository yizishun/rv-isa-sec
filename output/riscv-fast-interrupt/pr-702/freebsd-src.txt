PR #702  target=freebsd-src  overall=bug_confirmed
Spec: Ssip adds supervisor-level ssp architectural state invisible to the register file; FreeBSD's context switch and bhyve VM-entry paths lack awareness of ssp.SP/PUSH/PPUSH, risking stack corruption when scheduling across threads or vCPUs that use scspspush/scspspop/sipopret
Violation: FreeBSD context-switch path (swtch.S) or bhyve VM-entry/VM-exit does not save/restore the per-hart ssp architectural state (ssp.SP, ssp.PUSH, ssp.PPUSH), causing a thread or vCPU to inherit stale shadow-stack-pointer state from the previously scheduled entity that had executed scspspush/scspspop/sipopret.
Consequence: data_corruption
Pattern: ssp\.(SP|PUSH|PPUSH)|scspspush|scspspop|sipopret|Ssip|CSR_SSCRATCH|ENABLE_SMCSPS|ENABLE_SSCSPS
------------------------------------------------------------
[bug_confirmed] sys/riscv/riscv/swtch.S:258-358  cpu_switch
  cpu_switch saves/restores ra, sp, s0-s11, and FPU state to PCB but does not save/restore the sspcs CSR (0x149). When a thread that has executed scspspush/scspspop/sipopret is preempted, the sspcs.SP, sspcs.PUSH, and sspcs.PPUSH fields are not saved. The next thread inherits the stale sspcs state directly from hardware, causing thread A's sspcs.SP (the saved supervisor stack pointer) to be used when thread B executes sipopret or scspspop.

  |   sd sp, (PCB_SP)(x13)
  |   /* ... no csrr sspcs / sd to PCB */
  |   /* ... no ld from PCB / csrw sspcs on restore */
