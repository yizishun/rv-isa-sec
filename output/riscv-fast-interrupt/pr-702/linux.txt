PR #702  target=linux  overall=compliant
Spec: Ssip/Sscsps introduces per-hart ssp.SP/ssp.PUSH/ssp.PPUSH state that the kernel must context-switch; failure to do so corrupts kernel stack usage across tasks sharing a hart
Violation: Linux kernel context switch (__switch_to) or trap return path fails to save/restore the per-hart ssp architectural state (ssp.SP, ssp.PUSH, ssp.PPUSH) when the Ssip/Sscsps extension is enabled, causing one task's conditional-stack-swap state to be applied to another task's kernel stack on the same hart
Consequence: data_corruption
Pattern: ssp\.(SP|PUSH|PPUSH)|scspspush|scspspop|sipopret|Ssip|Sscsps|__switch_to.*sst|context.*switch.*sst
------------------------------------------------------------
[compliant] arch/riscv/kernel/entry.S:421-471  __switch_to
  The __switch_to function does not directly save/restore CSR_SSP (the user-mode Zicfiss shadow stack pointer CSR at 0x011). This is compliant because CSR_SSP is saved to per-task thread_info on kernel entry via save_userssp (line 184) and will be restored from the incoming task's thread_info on kernel exit via restore_userssp (line 280). The context switch swaps tp to point to the next task's thread_info, which carries the next task's user_shdw_stk. ENVCFG (with SSE bit) is also switched via __switch_to_envcfg before __switch_to is called. No Ssip/Sscsps supervisor-mode CSRs exist in this kernel, so there is nothing to save/restore.

  |   REG_S ra,  TASK_THREAD_RA_RA(a3)
  |   ...
  |   scs_save_current
  |   ...
  |   move tp, a1
  |   scs_load_current
  |   ret

[compliant] arch/riscv/kernel/entry.S:99-110  save_userssp
  The save_userssp macro correctly saves CSR_SSP (user shadow stack pointer) to TASK_TI_USER_SSP(tp) — which is current->thread_info.user_cfi_state.user_shdw_stk — and simultaneously zeros CSR_SSP via csrrw for sanitization. It uses ALTERNATIVE patching gated on RISCV_ISA_EXT_ZICFISS, so it only executes on harts with Zicfiss support. When the previous mode is S-mode (kernel-to-kernel exception), it skips the save because CSR_SSP is already sanitized.
  | csrrw \tmp, CSR_SSP, x0;
  | REG_S \tmp, TASK_TI_USER_SSP(tp);

[compliant] arch/riscv/kernel/entry.S:112-123  restore_userssp
  The restore_userssp macro correctly restores CSR_SSP from TASK_TI_USER_SSP(tp) — which after a context switch points to the next task's user_shdw_stk. It only executes when returning to U-mode. The CSR write is ungated by any fence; per the RISC-V spec, CSR writes are not speculative and take effect immediately, so no fence is needed before sret.
  | REG_L \tmp, TASK_TI_USER_SSP(tp);
  | csrw CSR_SSP, \tmp;

[potential_risk] arch/riscv/kvm/vcpu_switch.S:198-219  __kvm_riscv_switch_to
  KVM VCPU context switch (__kvm_riscv_switch_to and __kvm_riscv_nacl_switch_to) saves/restores sstatus, stvec, sscratch, sepc via SAVE_HOST_AND_RESTORE_GUEST_CSRS and SAVE_GUEST_AND_RESTORE_HOST_CSRS macros, but does NOT save/restore CSR_SSP (0x011). If a guest OS enables Zicfiss for its user processes, the guest's CSR_SSP value would leak to the host or vice-versa across VM exits, causing cross-VM shadow stack corruption. However, Ssip/Sscsps (supervisor shadow stack) CSRs are not implemented, so this gap only affects user-mode Zicfiss virtualization if the guest supports it.

  | sret
  | .Lkvm_switch_return:
  | SAVE_GUEST_GPRS
  | SAVE_GUEST_AND_RESTORE_HOST_CSRS
