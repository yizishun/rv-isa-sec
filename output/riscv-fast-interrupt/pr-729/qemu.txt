PR #729  target=qemu  overall=potential_risk
Spec: IVT mode trap entry must atomically clear the interrupt-pending bit when vectoring; failure to do so causes infinite re-delivery loop (DoS) after mret/sret
Violation: In QEMU's emulation of smehv IVT (Interrupt Vector Table) mode: when the CPU takes an interrupt trap in IVT mode, it fetches the handler address from VTBASE + XLEN/8 × exccode, sets PC to that address — but does NOT clear the corresponding interrupt-pending bit in mip/sip or the IMSIC eistate. After the handler executes mret/sret, riscv_cpu_interrupt() re-evaluates and finds the same pending bit still set, causing immediate re-delivery of the same interrupt in an infinite loop.
Consequence: denial_of_service
Pattern: IVT/hardware-vectored trap entry path that fetches handler address from VTBASE/mivt/sivt and sets PC but lacks a preceding or concurrent write to clear the pending bit (mip CSR or IMSIC EIP/eistate) for the interrupt being taken — search for vtbase, VTBASE, mivt, sivt alongside pc assignment without corresponding pending-bit clear
