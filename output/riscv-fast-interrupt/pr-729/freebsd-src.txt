PR #729  target=freebsd-src  overall=compliant
Spec: CLIC IVT mode cannot reliably clear mip/sip pending bits on trap entry for level-triggered interrupts; FreeBSD dispatch logic that re-examines pending-bit state after hardware vectored entry risks infinite re-trap storm before PLIC acknowledgment, halting the hart
Violation: FreeBSD's RISC-V hart runs in CLIC IVT (Interrupt Vector Table) mode with a level-sensitive external interrupt source (e.g., PLIC-wired IRQ). Hardware vectors to the handler via VTBASE lookup and *attempts* to clear the interrupt-pending bit in mip/sip per the new spec, but cannot do so because the device still physically asserts the level line. After the FreeBSD handler returns (mret) or when the kernel's dispatch loop polls mip/sip/mnxti pending bits, the still-set bit triggers immediate re-trapping into the same handler. This forms a tight re-trap loop where the handler is invoked indefinitely before it ever reaches the PLIC claim/complete register write or the inthand_add()/intr_event_handle() stage that would deassert the source.
Consequence: denial_of_service
Pattern: RISC-V CLIC/IVT-mode interrupt paths where: (a) the trap entry path or dispatch loop in sys/riscv/riscv/intr_machdep.c or sys/riscv/riscv/trap.c polls mip/sip/mnxti pending bits as a loop condition; (b) no software masking (PLIC threshold/IE or mie CSR bits) occurs at the handler prologue before the pending-bit is (re)examined; (c) the pattern of 'csrr mie / csrr mip / csrrw sip' near a bnez loop or XINTR dispatch without prior PLIC claim. Look for mcause polling loops that assume pending-bit auto-clear on entry.
