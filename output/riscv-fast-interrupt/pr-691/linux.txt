PR #691  target=linux  overall=compliant
Spec: Removal of cspspush/cspspop from ipush/ipopxret means kernel must not rely on hardware stack-swap for interrupt isolation; interrupt frames always land on the interrupted context's stack
Violation: Kernel configures xsp as a dedicated interrupt stack (via MSECCFG.Smip enable) expecting hardware to cspspush/cspspop on interrupt entry/exit, but with cspspush/cspspop removed from ipush/ipopxret, interrupt frames land on the interrupted context's stack — if that context is near stack limit, the additional frame causes overflow; if that context is user space, the frame corrupts the user stack.
Consequence: data_corruption
Pattern: CSR write to xsp|MSECCFG.*Smip|ipush|ipopxret|cspspush|cspspop
------------------------------------------------------------
[compliant] arch/riscv/include/asm/csr.h:245-250  (CSR definitions)
  Only PMM (pointer masking) bits are defined for MSECCFG. No MIPU/SIPU (Smip enable) bit definitions exist. The kernel never writes to CSR_MSECCFG (0x747) — it only defines PMP-related read fields. The Smip control bits don't even have allocated encodings in the current RISC-V spec.

[compliant] arch/riscv/kernel/entry.S:300-317  ret_from_exception
  Interrupt return uses standard sret, not sipopret/mipopret. The kernel does not rely on hardware cspspush/cspspop for stack management. Registers are saved/restored manually in handle_exception. No xspcs CSR is ever configured, so the conditional stack pointer swap path is never activated even if Smip were implemented in hardware.
