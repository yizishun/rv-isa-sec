PR #691  target=freebsd-src  overall=bug_confirmed
Spec: PR#691 removes cspspush/cspspop, making Smip hardware unconditionally push x10-x15 onto the interrupted context's own stack before the kernel's first instruction — FreeBSD's save_registers then double-adjusts sp (hardware + software), overwrites hardware-saved caller-saved with post-entry clobbered values, and sret returns without ipopxret, permanently corrupting the interrupted context and leaking register state
Violation: FreeBSD boots on RISC-V hardware implementing Smip per the post-PR#691 spec (cspspush/cspspop removed). When a CLIC fast interrupt fires in S-mode or U-mode, hardware unconditionally saves x10-x15 (6 registers, 48 bytes) onto the interrupted context's own stack and adjusts sp downward by 48 bytes before the first instruction of cpu_exception_handler at exception.S:209 executes. FreeBSD's save_registers macro at exception.S:42 then performs addi sp, sp, -(TF_SIZE) — a second sp adjustment uncoordinated with the hardware frame. The 304-byte software trapframe is allocated starting at this doubly-adjusted sp position; the hardware-saved x10-x15 sit between the original sp and the software trapframe base, inaccessible to the kernel. Software saves a0-a7 (x10-x17) into tf_a slots at exception.S:80-87, but these values reflect post-entry handler state — for S-mode interrupts, t0-t6 are already clobbered by the macro's own CSR reads of sscratch/sepc/sstatus/stval/scause. On return, load_registers restores x10-x17 from the trapframe's tf_a slots (exception.S:172-179) — handler-clobbered values instead of the original interrupted context. addi sp, sp, (TF_SIZE) at exception.S:181 undoes only the software adjustment. sret at exception.S:224/234 returns without ipopxret, so the hardware sp adjustment is never unwound. The interrupted context resumes with x10-x15 corrupted, sp offset by 48 bytes relative to pre-interrupt state, and the hardware-saved original register values leaked as stale stack data below the current sp. Because PR#691 eliminates cspspush/cspspop (no shadow stack), the hardware always collides with the kernel's own stack frame allocation — there is no longer any mechanism to separate interrupt frame from kernel frame.
Consequence: data_corruption
Pattern: addi sp, sp, -(TF_SIZE) after Smip hardware pre-push without misa.Smip gate; sret instead of ipopxret for interrupt returns; sd a0-a7 at tf_a relative to doubly-adjusted sp; load_registers restoring caller-saved from clobbered frame; fork_trampoline sscratch setup spanning Smip-displaced sp

[bug_confirmed] sys/riscv/riscv/exception.S:219-225  cpu_exception_handler_supervisor
  sret at line 224 returns from an interrupt context without using sipopret. The Smip spec requires sipopret (not sret) for interrupt returns: sipopret performs scspspop (undo stack pointer swap), restores x10-x15, adjusts sp to destroy the hardware stack frame, then executes sret. With PR#691 removing cspspush/cspspop, the hardware pre-pushes x10-x15 onto the interrupted context's own stack and adjusts sp; sret has no mechanism to unwind this. The hardware sp adjustment is never unwound, leaving the resumed context with sp offset by 48 bytes relative to pre-interrupt state.

[potential_risk] sys/riscv/riscv/exception.S:208-217  cpu_exception_handler
  The csrrw sp, sscratch, sp at line 209 atomically swaps sp with sscratch to detect user vs supervisor mode. On Smip hardware, the sp value at entry already reflects the hardware pre-push adjustment (original sp - 48). If this is a user-mode trap, the swapped sscratch value (user sp) correctly goes into sp — but the hardware pre-push was done against the user stack at [user_sp - 48]. After the swap, sp = user_sp, but the hardware already wrote x10-x15 at [user_sp - 48 .. user_sp], meaning the user stack is corrupted and the kernel cannot access those saved registers. If this is an S-mode trap, sp = 0 (sscratch), and the subsequent csrrw restores the kernel sp (with hardware adjustment), which is the supervisor path.
