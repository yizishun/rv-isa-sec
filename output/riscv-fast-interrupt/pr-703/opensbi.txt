PR #703  target=opensbi  overall=bug_confirmed
Spec: Smip/ACLIC fast interrupts require vectored mtvec (mtvec.MODE ≠ 0) because the extension diverges interrupt vs. exception entry behavior; Direct mode causes shared-entry handlers to mis-handle hardware-saved GPRs on the interrupted stack.
Violation: OpenSBI configures mtvec.MODE=0 (Direct) while the ACLIC/Smip fast-interrupt extension is active, causing M-mode interrupts and synchronous exceptions to share a single trap entry point despite the extension modifying only interrupt trap behavior (e.g., automatic GPR stack saves) and not exception trap behavior.
Consequence: data_corruption
Pattern: CSR write to mtvec with MODE field (bits 1:0) cleared to 0 (Direct mode), combined with any ACLIC/Smip enable or configuration CSR writes (e.g., miprio, mnxti, or similar ACLIC CSRs).
------------------------------------------------------------
[bug_confirmed] firmware/fw_base.S:393-401  _start_warm (trap handler setup)
  CSR_MTVEC is programmed with the address of _trap_handler (or _trap_handler_hyp), producing mtvec.MODE=0 (Direct mode). The ACLIC Smip specification explicitly states 'mtvec.mode = 0 (direct) is incompatible' with the Smip extension because Smip modifies interrupt trap behavior (auto-save x10-x15, push stack) but does not modify exception trap behavior, so shared entry points cause data corruption when hardware pushes registers onto the exception stack.

[potential_risk] firmware/fw_base.S:110-132  _start (cold boot Zkr stack guard)
  During cold boot, mtvec is temporarily set to __stack_chk_guard_done (line 112, MODE=0) and then to _start_hang (line 136, MODE=0) before the final trap handler setup. If interrupts fire during this early init phase with ACLIC/Smip active, the hardware would push x10-x15 but the handler would not expect nor restore them, causing register corruption. These are transitional but on hardware where Smip is fused on, the window exists.

[bug_confirmed] firmware/fw_base.S:672-724  _trap_handler / _trap_handler_hyp
  Both _trap_handler and _trap_handler_hyp unconditionally end with 'mret' and unconditionally save/restore all GPRs including x10-x15 via TRAP_SAVE_GENERAL_REGS_EXCEPT_SP_T0. On Smip hardware with auto-push enabled, the hardware would have already stacked x10-x15 and adjusted sp before entering the handler. The trap handler would then save already-stacked registers again, and the final mret would return without popping them — xipopret (not xret) is required to restore the hardware-saved context.
