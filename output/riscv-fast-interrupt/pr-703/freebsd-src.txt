PR #703  target=freebsd-src  overall=potential_risk
Spec: FreeBSD's cpu_exception_handler uses direct-mode stvec (mode=0) as a unified trap entry for both interrupts and exceptions in exception.S:208, which the Smip spec explicitly marks as incompatible because Smip modifies interrupt entry behavior without modifying exception entry behavior
Violation: If the Smip fast-interrupt extension is enabled on a hart running FreeBSD, the kernel writes a bare address (bit 0 = 0, direct mode) to stvec, creating a single entry point (cpu_exception_handler) shared by both interrupts and synchronous exceptions. Smip modifies interrupt trap entry behavior (e.g., selective register stacking, different save/restore semantics) but does not modify synchronous exception trap behavior. Since both trap types vector to the same handler, the Smip-altered interrupt entry state (register file, trap frame layout, or control flow) violates the assumptions in cpu_exception_handler and its save_registers/load_registers macros, which expect unmodified RISC-V trap entry semantics for all traps regardless of cause.
Consequence: data_corruption
Pattern: csrw\s+stvec,\s*\w+ where the written value has bit 0 clear AND Smip is enabled (check menvcfg/senvcfg for Smip enable bits) OR any kernel code setting stvec.mode=0 while the CLIC/Smip hardware is active
------------------------------------------------------------
[potential_risk] sys/riscv/riscv/locore.S:231-232  _alt_start / pagetables (BSP boot)
  BSP writes cpu_exception_handler to stvec with bit 0 = 0 (direct mode), creating a single entry point for both interrupts and synchronous exceptions. If the firmware (OpenSBI) or M-mode enables Smip (menvcfg/senvcfg Smip enable bits), Smip applies selective hardware register stacking for interrupts but not for synchronous exceptions. Since both trap types vector to the same handler, save_registers/load_registers in exception.S assume standard unmodified RISC-V trap entry semantics and would either double-save registers (corrupting the trapframe layout) or miss registers (leaving caller-saved state unrestored on sret), depending on which subset Smip stacks. The kernel has no Smip-awareness, no ISA string check for Smsip, and no defensive configuration.

[potential_risk] sys/riscv/riscv/exception.S:208-217  cpu_exception_handler
  The shared entry point dispatches on sscratch (user vs supervisor) but does NOT inspect scause before dispatching to save_registers. Under Smip with CLIC active, interrupt traps may have already stacked a subset of registers (x1/x5-x7/x10-x17/x28-x31 per the Smip spec) by the time this handler runs. The save_registers macro (lines 41-114) manually saves ALL of ra, tp, gp, t0-t6, s0-s11, a0-a7, which would: (a) overwrite Smip-stacked values with post-trap register contents, or (b) corrupt the trapframe if Smip-stacked registers are in a different order/offset. The load_registers macro (lines 116-182) would then restore the wrong values on sret.
  | ENTRY(cpu_exception_handler)
  | 	csrrw	sp, sscratch, sp
  | 	beqz	sp, 1f
  | 	/* User mode detected */
  | 	j	cpu_exception_handler_user
  | 1:
  | 	/* Supervisor mode detected */
  | 	csrrw	sp, sscratch, sp
  | 	j	cpu_exception_handler_supervisor
  | END(cpu_exception_handler)

[potential_risk] sys/riscv/riscv/exception.S:41-114  save_registers (macro)
  The save_registers macro manually saves all t0-t6, s0-s11, a0-a7, ra, tp, gp, sepc, sstatus, stval, scause into a struct trapframe at sp - TF_SIZE. This assumes standard RISC-V trap entry semantics where hardware saves ONLY sepc/scause/stval/sstatus (or their virtualized equivalents) and nothing else. Under Smip with selective hardware stacking, a configurable subset of GPRs may already be saved by the hardware to a different location or in a different format. The manual saves here would clobber or duplicate hardware-stacked state, making the trapframe internally inconsistent.
  | addi	sp, sp, -(TF_SIZE)
  | 	sd	ra, (TF_RA)(sp)
  | 	sd	tp, (TF_TP)(sp)
  | 	sd	gp, (TF_GP)(sp)
  | 	...
  | 	sd	t0, (TF_T + 0 * 8)(sp)
  | 	...

[potential_risk] sys/riscv/riscv/exception.S:116-182  load_registers (macro)
  The load_registers macro restores sstatus, sepc, then all GPRs from the trapframe and deallocates it with addi sp, sp, TF_SIZE. Under Smip, if selective stacking pushed some registers onto the stack before the kernel's manual save, the trapframe layout (offsets within TF_SIZE) would be misaligned with the actual stack state. The addi sp, sp, TF_SIZE at line 181 may not fully unwind the stack if Smip stacked additional state, causing stack corruption on return.
  | addi	sp, sp, (TF_SIZE)
