PR #703  target=linux  overall=potential_risk
Spec: Smip alters interrupt trap microarchitecture (GPR save) but not exception traps; if mtvec uses Direct mode (shared entry), synchronous exceptions incorrectly receive Smip treatment, corrupting kernel exception handling state
Violation: The kernel enables the Smip fast-interrupt extension (e.g., via menvcfg or siselect CSR) while mtvec.mode is set to 0 (Direct mode), causing synchronous exceptions to share the same trap entry point as interrupts. On a synchronous exception, the hardware applies Smip's GPR-saving behavior—which is designed only for interrupts—corrupting the exception handler's expected register state and stack layout.
Consequence: data_corruption
Pattern: mtvec.*mode.*0|CSR_WRITE.*mtvec.*DIRECT|menvcfg.*smip|siselect.*smip.*enable

[potential_risk] arch/riscv/kernel/entry.S:125-238  handle_exception
  The trap handler assumes standard RISC-V save/restore semantics: registers are explicitly saved to the stack (PT_RA, PT_GP, PT_T0, save_from_x6_to_x31 at lines 164-167) and CSR_SCRATCH-based kernel/user detection is used (line 131). If Smip were enabled with mtvec.mode=Direct by firmware, Smip's automatic GPR saving would conflict with the handler's explicit save sequence—the hardware would save a subset of GPRs before the handler runs, but the handler code would still execute its full save routine, leading to double-save or mismatched stack layout.

[potential_risk] arch/riscv/kernel/cpufeature.c:578-581  riscv_isa_ext (table)
  The ISA extension table has entries for smaia, smmpm, smnpm, and smstateen, but no entry for smip. This means even if hardware advertises Smip in the ISA string, the kernel would not recognize it. More critically, the kernel has no boot-time validation that menvcfg or mseccfg does not have Smip enabled—it trusts firmware to leave M-mode CSRs in a sane state. This is a blind spot: if firmware enables Smip, the kernel has no defense and no mechanism to detect the misconfiguration.
