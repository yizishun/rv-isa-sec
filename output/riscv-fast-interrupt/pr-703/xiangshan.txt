PR #703  target=xiangshan  overall=compliant
Spec: ACLIC hardware stack push on interrupt entry must be gated on mtvec.mode != 0; direct mode causes shared interrupt/exception entry point to receive unexpected sp/x-register side effects, enabling privilege escape via corrupted exception handler context
Violation: XiangShan RTL implements ACLIC/SMIP hardware stack push (automatic GPR saving on interrupt entry) but does not gate this behavior on mtvec.mode != 0 (vectored mode). When mtvec.mode = 0 (direct mode), both interrupts and synchronous exceptions share the same trap entry point at mtvec.BASE. The ACLIC hardware stack push fires on interrupt entry and modifies sp/x-registers, but the shared exception handler at the same entry point does not expect these side effects — the hardware corrupts the interrupted context that synchronous exception handlers rely on. Additionally, if the CLIC/ACLIC module's enable/configure logic does not reject writes that enable SMIP features while mtvec.mode = 0, the core enters an architecturally-incompatible state.
Consequence: privilege_escape
Pattern: mtvec.mode check missing before CLIC/ACLIC/SMIP hardware stack push; mtvec.mode === 0.U && smip_enable; clic_save_gpr without mtvec_mode_vectored gate; aclic_hwstack_push && (mtvec_mode === Direct)

[compliant] src/main/scala/xiangshan/backend/fu/NewCSR/TrapHandleModule.scala:92-101  TrapHandleModule (trap PC computation)
  XiangShan does NOT implement the ACLIC/SMIP hardware stack push extension. There is no automatic GPR saving (x10-x15) on interrupt entry, no mipopret/sipopret instruction support, and no mcspspush/mcspspop CSR logic. The core uses AIA+IMSIC for interrupt control, not ACLIC. The vulnerability condition — hardware stack push corrupting GPRs when mtvec.mode=0 (Direct mode) with shared interrupt/synchronous exception entry — cannot fire because the vulnerable code path does not exist. The existing mtvec.mode checking logic is correctly implemented for vectored-mode PC offset computation.
