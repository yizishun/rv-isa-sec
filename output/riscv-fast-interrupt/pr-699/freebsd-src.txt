PR #699  target=freebsd-src  overall=bug_confirmed
Spec: FreeBSD RISC-V port is completely unaware of CSR 0x107 (sivt) and its EHV bit; if firmware leaves EHV=1, synchronous exception vectoring redirects traps to unmapped code offsets around the single-entry handler, crashing the kernel
Violation: FreeBSD never defines, reads, or writes CSR 0x107 (sivt). If firmware or a prior boot stage leaves sivt.EHV=1, synchronous exceptions are hardware-vectored to stvec + (cause << 2). FreeBSD stvec points to a single cpu_exception_handler with no vector table padded around it, so vectored exceptions land on arbitrary instructions in the surrounding code, causing immediate undefined behavior.
Consequence: denial_of_service
Pattern: absence of csr_write(sivt, 0) or csr_clear(sivt, EHV) in locore.S or trap initialization; absence of CSR_SIVT / SIVT_EHV macro definitions in riscvreg.h or encoding.h
------------------------------------------------------------
[bug_confirmed] sys/riscv/include/encoding.h:567-576

[bug_confirmed] sys/riscv/riscv/locore.S:203-237  _start
  Boot path writes stvec (0x105) four times (lines 212, 232, 369, 387) but never writes or clears CSR 0x107 (sivt). If firmware set sivt.EHV=1, exceptions will be vectored to stvec+(cause<<2). stvec is set to cpu_exception_handler address with bit 0 = 0 (direct mode), but the EHV bit in sivt is independent — EHV=1 enables hardware vectoring even without stvec[0]=1. No csr_write or csr_clear of 0x107 at any point in the boot sequence.
  | la    t0, cpu_exception_handler
  |         csrw  stvec, t0
  | 
  |         /* Ensure sscratch is zero */
  |         li    t0, 0
  |         csrw  sscratch, t0

[bug_confirmed] sys/riscv/riscv/exception.S:208-217  cpu_exception_handler
  cpu_exception_handler is a compact single-entry dispatch routine (6 instructions). It is not a vector table — there are no padded .align entries with exception dispatch stubs at stvec+0x08, +0x10, +0x18, ... offsets. If vectored exceptions are enabled (via sivt.EHV=1), exceptions whose cause >= 1 will land on arbitrary instructions in surrounding .text (cpu_exception_handler_user at +8, or other code), causing undefined behavior.
  | ENTRY(cpu_exception_handler)
  |         csrrw  sp, sscratch, sp
  |         beqz   sp, 1f
  |         j      cpu_exception_handler_user
  | 1:
  |         csrrw  sp, sscratch, sp
  |         j      cpu_exception_handler_supervisor
  | END(cpu_exception_handler)
