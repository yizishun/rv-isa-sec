PR #29  target=qemu  overall=not_implemented
Spec: PR tightens MDB semantics from 'any preceding store' to 'the last preceding store' and broadens the second clause to prohibit load data from 'any' subsequent instruction; QEMU currently has no Zisb implementation, so a future TCG implementation that treats MDB as a trivial no-op (relying on TCG's in-order execution) could violate 'last store' ordering under async interruption, and KVM passthrough without host capability checks would silently break guest speculation defenses.
Violation:
  QEMU TCG implements Zisb MDB as a NOP (since TCG is in-order and does not
  speculate), but guest software relies on MDB to enforce 'last store'
  visibility — i.e., a load after MDB must observe the *last* (not just any)
  preceding store to the same physical address. If QEMU's sequential TCG
  execution is interrupted by an asynchronous event (e.g., a timer IRQ causing
  a longjmp out of a translation block) between two stores to the same address
  before MDB, and the load after MDB reads stale data from a cached/delayed
  earlier store, the 'last store' guarantee is violated. Additionally, on KVM-
  accelerated setups, if QEMU does not validate that the host CPU supports
  Zisb and passes MDB through as a NOP or illegal instruction, guest kernel
  speculation barriers become ineffective, leaking transient execution
  protection assumptions.
Consequence: info_leak
Pattern:
  Zisb MDB/DPB/TEB instruction decode as no-op or illegal instruction raise in
  QEMU TCG; missing MDB barrier enforcement between store queuing and load
  forwarding in TCG memory model; KVM passthrough of MDB without host feature
  check

  Zisb barrier instructions (MDB, DPB, TEB) are encoded in Zimop MOP.R/MOP.RR
  code points. When ext_zimop is enabled (default on 'max' CPU, rva22s64,
  rva23s64 profiles), these security barrier instructions silently decode as
  functional NOPs that only write 0 to x[rd] — no memory barrier, no
  speculation fence, and no TCG ordering is emitted. While the Zisb spec
  explicitly allows Zimop fallback NOP behavior for processors without
  speculative execution, QEMU does not expose a separate ext_zisb flag for
  guest software to discover that the barriers are inactive. A guest kernel
  that probes for Zisb barriers via ISA string will find no indication of
  their presence, and one that blindly emits them (relying on the 'strict
  contract' per the Zisb spec) will get NOPs with no barrier effect. On in-
  order TCG this is functionally safe, but the 'last store' guarantee
  tightened by the PR under review (PR #29: 'the last instruction that
  stores') depends on TCG translation-block atomicity, not on explicit barrier
  enforcement.
