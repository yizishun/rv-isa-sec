PR #157  target=linux  overall=compliant
Spec: TEE buffer sizes derived from COMM_REQ_REGS/COMM_RESP_REGS scale by XLEN; kernel-TEE XLEN mismatch causes shared-memory over-read/write, and STATUS-word accounting ambiguity risks 4-byte response buffer underflow
Violation: Linux kernel computes TEE_COMMUNICATE shared-memory buffer sizes as COMM_REQ_REGS*(XLEN/8) and COMM_RESP_REGS*(XLEN/8) using its own XLEN without validating that the TEE implementation expects the same XLEN width. When kernel XLEN (e.g., RV64, XLEN=8 bytes/reg) differs from the TEE's assumed XLEN (e.g., OP-TEE firmware compiled for RV32, XLEN=4 bytes/reg), the kernel writes/reads double the expected byte count in shared memory, overrunning the allocated RPMI MPXY transport buffer. Additionally, COMM_RESP_REGS is defined as 'Number of XLEN-bit values in TEE_COMMUNICATE response data' but it is ambiguous whether the mandatory STATUS word at offset 0 is counted in COMM_RESP_REGS or is additional, causing a 4-byte under-allocation if the kernel treats the formula as the total response size.
Consequence: data_corruption
Pattern: TEE_GET_ATTRIBUTES|COMM_REQ_REGS|COMM_RESP_REGS|XLEN.*TEE|tee_communicate.*size|rpmi.*tee
