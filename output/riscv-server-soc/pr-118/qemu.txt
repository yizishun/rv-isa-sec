PR #118  target=qemu  overall=potential_risk
Spec: QEMU's synchronous IMSIC MSI write handling implicitly enforces load-acquire ordering (interrupt observed before subsequent device reads) that the spec intentionally removed, masking guest driver race conditions on real hardware
Violation:
  QEMU TCG's IMSIC MMIO write handler (riscv_imsic_write) processes MSI writes
  synchronously: the pending bit is set atomically and the external interrupt
  line is raised inline before the MMIO write returns. Because QEMU's device
  model serializes all MMIO/DMA operations on the BQL (Big QEMU Lock) or per-
  device iothread, a device MSI write to IMSIC will always appear to complete
  before any subsequent DMA read from the same device, thereby implicitly
  providing the load-acquire ordering that the spec (PR #118) intentionally
  removed. Guest drivers that incorrectly rely on MSI acting as a read barrier
  will work on QEMU but fail on real RISC-V hardware.
Consequence: function_loss
Pattern:
  riscv_imsic_write.*qatomic_or.*eistate.*IMSIC_EISTATE_PENDING; synchronous
  MSI delivery without deferred/batched interrupt injection; IMSIC MMIO write
  processed inline on BQL before device DMA read completion dispatch

  QEMU's IMSIC MMIO write handler processes MSI writes synchronously on the
  BQL: the pending bit is set atomically (qatomic_or) and the external
  interrupt line is raised inline (qemu_irq_raise via riscv_imsic_update)
  before the MMIO write returns. Because QEMU serializes all device MMIO/DMA
  operations under the BQL, a device MSI write to IMSIC will always appear to
  complete before any subsequent DMA read from the same device, thereby
  implicitly providing load-acquire ordering that the RISC-V AIA spec (PR
  #118) intentionally removed. Guest drivers developed on QEMU that
  incorrectly rely on MSI acting as a read barrier will function correctly on
  QEMU but will fail on real RISC-V hardware where the device may read stale
  data after MSI delivery. This is a fidelity gap in the emulation model, not
  a code correctness bug — QEMU's synchronous device model inherently provides
  stronger ordering than real hardware.
