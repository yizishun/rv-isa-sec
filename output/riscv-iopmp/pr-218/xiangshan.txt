PR #218  target=xiangshan  overall=bug_confirmed
Spec: ChiselIOPMP NAPOT address construction hardcodes lower 2 bits as 2'b11 instead of replicating ones across bits [G-2:0] per hardware granularity G, causing incorrect NAPOT range computation when G > 2
Violation: In ChiselIOPMP's Ctrl module (IopmpChecker.scala:1238-1239), when constructing the NAPOT entry address for the NAPOTDecoder, the hardware hardcodes the lower 2 bits as 2'b11 via `Cat(io.entry.addr, 3.U(2.W))`. This assumes a fixed granularity that ignores the configurable G field. Per the spec fix: when granularity G>=2 and the mode is NAPOT, entry address bits [G-2:0] must read as all ones. The Chisel implementation does not reference any granularity register to compute the number of lower bits that should be forced to 1. If G > 2, bits beyond [1:0] that should be all-ones per the spec are left at their raw entry_addr values (which may be zero), causing the NAPOT decoder to compute an incorrectly smaller address range — start address shifted downward relative to spec, end address correspondingly smaller. This causes incorrect address matching: transactions to addresses within the spec-defined NAPOT range but outside the incorrectly-computed range will fail to match, resulting in spurious access denials (function loss / denial of service).
Consequence: denial_of_service
Pattern: Cat(io.entry.addr, 3.U(2.W)) NAPOT entry_addr construction without granularity G mask; HWCFG0 granularity field not consulted before NAPOT address decode
