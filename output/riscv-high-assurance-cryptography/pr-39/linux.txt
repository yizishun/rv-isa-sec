PR #39  target=linux  overall=potential_risk
Spec: ACES standard Off/Initial/Clean/Dirty model: kernel MUST issue ace.reset to clear crypto contexts before writing ACES=Initial, because raw CSR writes to ACES do NOT clear CC contents
Violation: In the Linux kernel, if the context switch path or execve path writes sstatus.ACES to Initial (1) or Clean (2) without first executing ace.reset, the hardware CCs retain prior cryptographic key material but are marked as clean. A subsequent process or VM can then read or use stale cryptographic state belonging to a previous security domain.
Consequence: info_leak
Pattern: sstatus.*ACES|SSTATUS_ACES|__ACES|csr_write.*ACES|ace\.reset|ace_reset|ace_clear_all

[potential_risk] arch/riscv/kernel/signal.c:1-1  N/A (signal delivery/sigreturn paths)
  The signal delivery and sigreturn paths have no ACES state preservation in the signal frame. If a process receives a signal while ACES is in Dirty state with active key material in the cryptographic coprocessor registers, those registers are not saved to the sigframe. On sigreturn, the CCs would be restored to architectural reset state (losing the keys) or, worse, could expose stale keys if ACES state transitions are mishandled during signal delivery.
