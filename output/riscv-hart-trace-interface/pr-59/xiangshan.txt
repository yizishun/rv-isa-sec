PR #59  target=xiangshan  overall=bug_confirmed
Spec: XiangShan unconditionally drives trace tval from CSR for both exceptions and interrupts; corrected spec restricts tval validity to itype=1 (exception) only, causing undefined tval output on interrupt trace packets
Violation: In CtrlBlock.scala:310, io.traceCoreInterface.toEncoder.trap.tval is unconditionally wired to io.fromCSR.traceCSR.tval without gating on itype. The CSR module (NewCSR.scala:1269-1272) always drives tval from mtval/stval/vstval regardless of whether the trap is an exception (itype=1) or interrupt (itype=2). Per the corrected spec, tval is only defined when itype=1 (exception), meaning the RTL outputs tval for interrupt trace packets where the spec declares it undefined.
Consequence: info_leak
Pattern: trap\.tval\s*:=\s*|traceCSR\.tval|toEncoder.*tval(?!.*itype)
------------------------------------------------------------
[bug_confirmed] src/main/scala/xiangshan/backend/CtrlBlock.scala:309-310  CtrlBlockImp
  Both trap.cause and trap.tval are unconditionally wired from io.fromCSR.traceCSR without gating on itype. tval is only defined per RISC-V spec when itype=Exception (1). When the trap is an interrupt (itype=2), tval carries stale mtval/stval/vstval values, leaking exception-related data into interrupt trace packets. Notably, tracePriv (line 305) is correctly gated on Itype.isTrapOrXret, demonstrating the pattern exists but was omitted for tval.
  | io.traceCoreInterface.toEncoder.trap.cause := io.fromCSR.traceCSR.cause
  | io.traceCoreInterface.toEncoder.trap.tval  := io.fromCSR.traceCSR.tval

[bug_confirmed] src/main/scala/xiangshan/backend/fu/NewCSR/NewCSR.scala:1269-1272  NewCSR
  CSR module always drives traceCSR.tval from mtval/stval/vstval via Mux1H on privilege mode, without considering whether the current trap is an exception or interrupt. When an interrupt arrives (mcause bit[XLEN-1] = 1), mtval/stval/vstval are undefined per spec but the RTL still drives them out, making stale tval visible to the trace encoder.
  | io.status.traceCSR.tval  := Mux1H(
  |   Seq(privState.isModeM, privState.isModeHS, privState.isModeVS),
  |   Seq(mtval.rdata,       stval.rdata,        vstval.rdata)
  | )

[bug_confirmed] src/main/scala/top/Top.scala:352-353  Top
  The external trace interface (io.traceCoreInterface(i).toEncoder) receives trap.cause and trap.tval directly from the core's traceInterface without any itype qualification. No downstream consumer of these signals has the semantic context to gate tval on itype=Exception, so the leak propagates to the chip boundary.
  | io.traceCoreInterface(i).toEncoder.cause := traceInterface.toEncoder.trap.cause
  | io.traceCoreInterface(i).toEncoder.tval := traceInterface.toEncoder.trap.tval

[bug_confirmed] src/main/scala/top/XSNoCTop.scala:442-443  XSNoCTop
  Same unconditional forwarding of trap.cause and trap.tval to the external trace interface in the NoC topology variant. Identical information leak as Top.scala.
  | io.traceCoreInterface.toEncoder.cause := traceInterface.toEncoder.trap.cause
  | io.traceCoreInterface.toEncoder.tval := traceInterface.toEncoder.trap.tval

[compliant] src/main/scala/xiangshan/backend/CtrlBlock.scala:305-308  CtrlBlockImp
  The tracePriv signal is correctly gated on Itype.isTrapOrXret(itype), selecting lastPriv for trap/xret blocks and currentPriv otherwise. This is the correct pattern that should also be applied to trap.tval (though with isTrap + itype==Exception, not isTrapOrXret).
  | val tracePriv = Mux(Itype.isTrapOrXret(trace.toEncoder.blocks(0).bits.tracePipe.itype),
  |   io.fromCSR.traceCSR.lastPriv,
  |   io.fromCSR.traceCSR.currentPriv
  | )
