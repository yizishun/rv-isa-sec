PR #82  target=linux  overall=compliant
Spec: hstatus.MTAG_I is hardware-deposited on trap entry and controls HLV/HSV tag-check policy; kernel must not clobber it before HLV emulation and must not leak stale values across VM boundaries
Violation: KVM restores a stale hstatus.MTAG_I (from a previous VM exit) that does not match the current trapping instruction's code-page PTE.MTAG, then executes HLV/HSV instructions via kvm_riscv_vcpu_unpriv_read(), causing HLV tag-check policy to diverge from what the guest's native execution would have produced
Consequence: info_leak
Pattern: csr_write(CSR_HSTATUS, ...) | csr_swap(CSR_HSTATUS, ...) where the written value contains an MTAG_I bit not reflecting the current trap's code page MTAG; csr_write(CSR_MSTATUS, ...) where MTAG_I is clobbered before MPRV loads/stores
------------------------------------------------------------
[potential_risk] arch/riscv/kvm/vcpu_exit.c:74-74  kvm_riscv_vcpu_unpriv_read
  csr_swap(CSR_HSTATUS, vcpu->arch.guest_context.hstatus) loads the guest hstatus verbatim, including whatever MTAG_I bits the guest context carries, before executing HLV/HSV instructions. If MTAG support is added in future silicon, this could load a stale MTAG_I from the guest context that diverges from the trapped instruction's code-page PTE.MTAG. Currently safe because the kernel defines no MTAG_I bit and no RISC-V MTE support exists in this tree.
  | old_hstatus = csr_swap(CSR_HSTATUS, vcpu->arch.guest_context.hstatus);
