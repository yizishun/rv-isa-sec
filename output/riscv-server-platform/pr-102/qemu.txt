PR #102  target=qemu  overall=bug_confirmed
Spec: FIRM_140 unconditionally requires IOMMU to be described via RIMT ACPI table; QEMU virt machine must generate a correct RIMT table for the riscv-iommu device, or guest OS will fail to discover IOMMU — breaking DMA isolation and device assignment
Violation:
  QEMU's RISC-V virt machine instantiates an IOMMU (riscv-iommu) but does not
  generate a corresponding RIMT ACPI table in the guest firmware/hardware
  description, or generates a malformed RIMT table that fails to describe the
  IOMMU device topology, base addresses, and capabilities correctly
Consequence: function_loss
Pattern:
  iommu.*rimt|RIMT|riscv_iommu.*acpi|build_rimt|acpi.*iommu|iort.*riscv
------------------------------------------------------------

[bug_confirmed] /home/yzs/riscv/qemu/hw/riscv/virt-acpi-build.c:800-811  build_rimt
  Off-by-one error in `num_ids` for the system IOMMU path. Line 808 sets
  `range->num_ids = 0xffff - s->pci_iommu_bdf`, which evaluates to `0xffff`
  (65535) when `s->pci_iommu_bdf` is 0 (its default for the system IOMMU
  case). PCI Requester IDs span 0 through 0xffff inclusive — 65536 IDs total.
  The RIMT table declares only 65535 IDs, omitting the last Requester ID
  (0xffff). This is a malformed RIMT table: an OS parsing it will believe the
  IOMMU covers IDs 0–65534 but not 65535. The correct value should be
  `0x10000` (65536), i.e., `0xffff - s->pci_iommu_bdf + 1`.
  | range->num_ids = 0xffff - s->pci_iommu_bdf;
  |         build_rimt_id_mapping(table_data, range->source_id_base,
  |                               range->num_ids, iommu_offset);
