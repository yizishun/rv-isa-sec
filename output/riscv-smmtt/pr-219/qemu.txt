PR #219  target=qemu  overall=not_implemented
Spec: Spec explicitly forbids MXR and HLVX from overriding MPT permission bits; QEMU must check raw XWR bits in isolation without mstatus.MXR influence, else execute-only MPT pages become readable when MXR=1
Violation:
  When QEMU's MPT permission check reuses or delegates to the existing page-
  table walk machinery that consults mstatus.MXR, or when the MPT lookup path
  itself checks MXR, causing a load access to an MPT-protected execute-only
  (X=1,W=0,R=0) page to be incorrectly granted read permission because MXR
  makes the page appear readable.
Consequence: privilege_escape
Pattern:
  mstatus.MXR referenced or evaluated within the MPT access-type permission
  check path (step 7 of the MPT lookup algorithm); MPT XWR check that
  considers anything beyond the raw XWR bits; code paths where
  get_physical_address or similar TLB-fill functions consult MXR without first
  checking whether MPT is active
------------------------------------------------------------
[not_implemented] target/riscv/cpu_helper.c:1537-1565  get_physical_address
  QEMU does not implement the MPT (Memory Protection Table / Smmpt) extension
  at all. The get_physical_address function (lines 1537-1565) implements the
  standard Sv39/Sv48/Sv57 page-table walk with MXR handling for virtual-memory
  PTEs only. There is no MPT lookup path, no MPT entry format parsing, no mmpt
  CSR, and no MPT-specific permission check (step 7 of the MPT lookup
  algorithm). The spec violation — mstatus.MXR being consulted during MPT
  permission checks — cannot occur because the MPT infrastructure does not
  exist. However, this means any future MPT implementation that reuses or
  delegates to the existing get_physical_address code would inherit the MXR-
  vulnerable permission check and violate the PR #219 spec requirement that
  'The MXR mechanisms or the use of HLVX instruction cannot be used to affect
  or override the interpretation of permissions encoded in memory-protection-
  table entries.'
