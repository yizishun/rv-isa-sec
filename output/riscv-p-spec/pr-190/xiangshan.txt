PR #190  target=xiangshan  overall=compliant
Spec: RV32-only ADDD/SUBD instructions reuse OP-IMM-32 opcode with funct3=0x6 and register-pair format (4-bit rd_p/rs1_p/rs2_p indices); XiangShan RV64 decoder must trap these as illegal, and any future implementation must correctly decode pair-indices from truncated register bit-fields to avoid silent register file corruption
Violation: XiangShan is an RV64 processor; ADDD/SUBD are RV32-only P-extension instructions encoded in the OP-IMM-32 (instr[6:0]=0x1B) opcode space with funct3=0x6. If the XiangShan decoder (DecodeUnit.scala:791) lacks explicit illegal-instruction trapping for OP-IMM-32 funct3=0x6 encodings, these bit patterns will fall through to the decodeDefault path. However, the register-pair format (rd_p/rs1_p/rs2_p as 4-bit indices selecting X[2*p] and X[2*p+1]) reinterprets standard RISC-V register fields: rd_p uses only instr[11:8] (vs standard instr[11:7]), rs1_p uses instr[19:16] (vs instr[19:15]), rs2_p uses instr[24:21] (vs instr[24:20]). A decoder bug that maps these pair-indices onto standard 5-bit register specifiers would read/write wrong architectural registers, silently corrupting register state. The encoding forces instr[7]=0 (the 8-bit opcode byte is exactly 0x1B), imposing a constraint on what is normally RD[0] in standard encodings — failure to validate instr[7]==0 would accept invalid encoding variants.
Consequence: data_corruption
Pattern: OP_IMM_32.*funct3.*0x6|decodeDefault.*OP-IMM-32|RS1(19,16).*RS2(24,21)|rd_p.*rs1_p.*rs2_p|register.pair.*decoder|XLEN.*gate.*OP.IMM.32|illegalInstr.*funct3

[compliant] src/main/scala/xiangshan/backend/decode/DecodeUnit.scala:842-849  DecodeUnit (register source/dest assignment)
