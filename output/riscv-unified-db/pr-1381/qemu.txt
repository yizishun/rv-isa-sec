PR #1381  target=qemu  overall=compliant
Spec: Missing Sstvecv emulation in QEMU causes stvec.MODE=1 writes to either be silently truncated (WARL mismatch vs hardware) or accepted but ignored, breaking per-interrupt-source vectored dispatch and causing guest kernel interrupt handlers to receive wrong/unexpected traps
Violation:
  QEMU TCG does not implement stvec.MODE=Vectored dispatch logic (pc =
  stvec.BASE + 4 * cause for interrupts), yet the stvec CSR WARL mask does not
  constrain MODE to 0 (Direct only), allowing a guest to write MODE=1 and
  observe incorrect interrupt vectoring — either interrupts jump to the wrong
  PC or the vectored write is silently accepted but not honored, causing the
  guest kernel's per-cause entry points to be bypassed.
Consequence: denial_of_service
Pattern:
  stvec.*MODE.*warl|stvec.*vectored|riscv_cpu_do_interrupt.*stvec|stvec.*BASE.
  *cause|VECTORED_INTERRUPTS|sstvecv|stvec_mode
------------------------------------------------------------
[compliant] target/riscv/csr.c:4153-4163  write_stvec
  write_stvec WARL mask accepts MODE values 0 (Direct) and 1 (Vectored),
  rejecting >=2 as reserved. This is correct because QEMU TCG fully implements
  vectored dispatch at cpu_helper.c:2421-2422. Every MODE=1 write that passes
  the mask is correctly honored during interrupt delivery.
  | if ((val & 3) < 2) {
  |     env->stvec = val;
  | } else {
  |     qemu_log_mask(LOG_UNIMP, "CSR_STVEC: reserved mode not supported\n");
  | }

[compliant] target/riscv/cpu_helper.c:2421-2422  riscv_cpu_do_interrupt
  S-mode interrupt dispatch correctly implements the vectored formula: pc =
  stvec.BASE (masked via >>2<<2) + (async && MODE==1 ? cause*4 : 0).
  Synchronous exceptions always use BASE regardless of MODE. This matches the
  spec requirement identically.
  | env->pc = (env->stvec >> 2 << 2) +
  |           ((async && (env->stvec & 3) == 1) ? cause * 4 : 0);

[potential_risk] target/riscv/cpu.c:244-245  riscv_cpu_extensions_init
  Sstvecd is registered in the ISA extension table but Sstvecv is not. A guest
  querying the ISA string will see Sstvecd (Direct mode support) without
  Sstvecv (Vectored mode support), yet the hardware functionally supports both
  MODE=0 and MODE=1. This could cause a guest OS to avoid using Vectored mode
  even though it works, relying on a less efficient single-entry-point
  handler. Not a security bug (no silent misrouting occurs) but could cause
  guest performance degradation.
  | ISA_EXT_DATA_ENTRY(sstvecd, PRIV_VERSION_1_12_0, has_priv_1_12),

[compliant] target/riscv/machine.c:482-482  vmstate_riscv_cpu
  stvec is included in VMStateDescription via VMSTATE_UINT64, ensuring it is
  correctly migrated across live-migration save/restore cycles.
  | VMSTATE_UINT64(env.stvec, RISCVCPU),

[potential_risk] target/riscv/csr.c:4156-4162  write_stvec
  When an unsupported MODE (>=2) is written, the write is silently dropped —
  stvec retains its previous value. The spec says stvec.MODE is WARL, so this
  is legal WARL behavior. However, the qemu_log_mask with LOG_UNIMP is
  suboptimal: for a guest that mistakenly writes MODE=2, the register silently
  retains the old value, but since MODE>=2 is architecturally reserved, the
  guest should never rely on this. Not a security issue — the guest sees its
  write clamped, which is correct WARL semantics.
  | if ((val & 3) < 2) {
  |     env->stvec = val;
