PR #1236  target=linux  overall=potential_risk
Spec: sie bits are aliases of mie; they become read-only zero when mideleg delegation is inactive, so kernel writes to sie can silently fail and cause missed interrupts
Violation:
  Kernel at S-mode writes to sie (e.g., csr_set CSR_SIE) to enable supervisor
  interrupts, but if M-mode firmware concurrently clears the corresponding
  mideleg delegation bit, the sie bit becomes read-only zero — the write
  silently fails, the kernel believes the interrupt is enabled but the hart
  never delivers it
Consequence: denial_of_service
Pattern:
  csr_set.*0x104|__enable_irq|arch_local_irq_enable|sie.*write|CSR_SIE
------------------------------------------------------------

  csr_set(CSR_IE, BIT(d->hwirq)) writes to per-source sie bits without
  verifying the write took effect. Per RISC-V priv spec, if M-mode firmware
  clears the corresponding mideleg delegation bit, the sie bit becomes read-
  only zero and the csr_set silently fails — the kernel believes the interrupt
  is enabled but the hart will never deliver it. No csr_read(CSR_IE) is
  performed after any csr_set(CSR_IE, ...) call anywhere in the kernel. This
  is the single funnel through which all timer, IPI, external, PMU, and custom
  local interrupts are enabled.
  | static void riscv_intc_irq_unmask(struct irq_data *d)
  | {
  | 	if (IS_ENABLED(CONFIG_32BIT) && d->hwirq >= BITS_PER_LONG)
  | 		csr_set(CSR_IEH, BIT(d->hwirq - BITS_PER_LONG));
  | 	else
  | 		csr_set(CSR_IE, BIT(d->hwirq));
  | }

  KVM correctly orders CSR writes: clears VSIE before HIDELEG. The comment at
  line 61-65 explicitly acknowledges the delegation-vs-enable interaction:
  'After clearing the hideleg CSR, the host kernel will receive spurious
