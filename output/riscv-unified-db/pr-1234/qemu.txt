PR #1234  target=qemu  overall=compliant
Spec: QEMU write_jvt lacks WARL masking on JVT BASE lower bits and uses RVS presence as proxy for Ssstateen, causing architecturally-zero bits to be guest-observable and potentially incorrect stateen access denial in configurations with S-mode but without Ssstateen
Violation:
  QEMU's write_jvt CSR handler stores the raw guest-written value into
  env->jvt without enforcing WARL field coercion on MODE (bits 5:0) or
  ensuring BASE lower 6 bits are architecturally read-only zero. The spec
  requires JVT.BASE lower 6 bits to be implicitly zero (the table is 64-byte
  aligned per {CSR[jvt].BASE, 6'b000000}), yet QEMU's read_jvt returns the
  unmodified raw write value, exposing bits that must be hardwired to zero.
  Additionally, QEMU's smstateen_acc_ok uses riscv_has_ext(env, RVS) as a
  proxy for implemented?(ExtensionName::Ssstateen); when S-mode exists but
  Ssstateen is not implemented, U-mode JVT access may be incorrectly denied
  because sstateen0 bits that are architecturally absent are still evaluated.
Consequence: info_leak
Pattern:
  write_jvt.*\n.*env->jvt = val
