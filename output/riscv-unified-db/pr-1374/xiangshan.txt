PR #1374  target=xiangshan  overall=compliant
Spec: Ratio comparison in VsetModule.keepVlIllegal uses specVType from decode-time vtype snapshot; stale speculative state from prior uncommitted vset can cause incorrect vill/vl computation in the rs1=x0,rd=x0 keep-vl case
Violation:
  When vsetvli/vsetvl with rs1=x0, rd=x0 (keep-vl) executes while another
  uncommitted vset instruction is in-flight, the specVType carried in the
  uop's vpu bundle (sourced from VTypeGen.io.vtype at decode time) reflects
  the speculative vtype that may already incorporate the effect of the prior
  in-flight vset, rather than the true architectural old vtype. Specifically
  in Vsetu.scala:113-114, `oldVt` from `io.in.oldVt` (VSet.scala:104-105,
  sourced from `in.ctrl.vpu.get.specVType`) is used to compute `log2OldRatio =
  oldVt.vlmul - oldVt.vsew`. If this specVType is stale or reflects a younger
  speculative vtype update, the ratio comparison `log2NewRatio =/=
  log2OldRatio` may produce a false match (ratios appear equal when they are
  not) or a false mismatch. A false match means the hardware fails to set
  vill=1/vl=0 when the LMUL/SEW ratio actually changed, causing subsequent
  vector instructions to execute with an invalid vl and incorrect vtype
  configuration. This condition requires: (1) a prior vset instruction in the
  pipeline that modified vtype but has not yet committed, AND (2) a subsequent
  keep-vl vsetvli/vsetvl that changes LMUL/SEW such that the ratio differs
  from the true architectural ratio but matches the speculative ratio.
Consequence: data_corruption
Pattern:
  oldVt\.(vlmul|vsew)|specVType|log2OldRatio|log2NewRatio|keepVlIllegal.*oldVt
  |in\.ctrl\.vpu\.get\.specVType
