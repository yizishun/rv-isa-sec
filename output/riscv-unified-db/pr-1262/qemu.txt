PR #1262  target=qemu  overall=compliant
Spec: vsetvli/vsetvl with rs1==x0 architecturally encodes 'set vl=VLMAX' (not 'read GPR[0]==0 as AVL'); incorrect TCG translation would set vl=0, silently disabling all subsequent vector ops and violating guest kernel/supervisor vector ISA assumptions
Violation:
  When QEMU TCG translates vsetvli/vsetvl with rs1==x0 by reading the
  architectural zero from GPR x0 (value 0) and passing it as AVL to the vsetvl
  helper, instead of treating rs1==x0 as the special architectural encoding
  for 'vl=VLMAX'. This causes helper_vsetvl() to compute vl=0 (since 0 <=
  vlmax), silently disabling all subsequent vector instructions.
Consequence: denial_of_service
Pattern:
  do_vsetvl.*rs1.*==.*0.*(?!tcg_constant_tl|RV_VLEN_MAX)|helper_vsetvl.*\bs1\b
  .*\bvlmax\b|vsetvl.*rs1.*x0.*!vlmax
------------------------------------------------------------

[potential_risk] target/riscv/vector_helper.c:111-117  HELPER(vsetvl)
  When rvv_vl_half_avl=true and rs1==x0, the TCG translator passes
  s1=RV_VLEN_MAX (1024) instead of ~0 (max uint). For VLMAX values in range
  (512, 1024), s1=1024 falls into the 's1 < 2*vlmax' half_avl branch,
  producing vl=512 instead of vl=VLMAX (spec requires vl=VLMAX when rs1==x0).
  Example: vlen=1024, sew=8, lmul=4 gives VLMAX=512 (OK); vlen=1024, sew=8,
  lmul=8 gives VLMAX=1024 → vl=1024 (OK border case). But vlen=800, sew=8,
  lmul=4 gives VLMAX=400 — wait, 400 < 512 so 2*VLMAX=800 < 1024, hitting else
  → vl=400. The half_avl misbehavior requires VLMAX in (512, 1024) which needs
  vlen>512. With default vlen=128 or 256 this cannot trigger. Mitigated by
  rvv_vl_half_avl defaulting to false.
  | if (s1 <= vlmax) {
  |         vl = s1;
  |     } else if (s1 < 2 * vlmax && cpu->cfg.rvv_vl_half_avl) {
  |         vl = (s1 + 1) >> 1;
  |     } else {
  |         vl = vlmax;
  |     }
