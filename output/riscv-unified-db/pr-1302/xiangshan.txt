PR #1302  target=xiangshan  overall=potential_risk
Spec: mseccfg CSR unconditionally present in hardware CSR map despite spec requiring it exist only when at least one of Zkr/Smmpm/Zicfilp/Smepmp is implemented; software probing for extension support via CSR trap behavior will incorrectly detect mseccfg capability
Violation:
  In XiangShan RTL, mseccfg (0x747) and mseccfgh (0x757) are unconditionally
  instantiated as CSRModules and always present in the csrRwMap, regardless of
  which extensions are configured. Per the updated spec, mseccfg must exist if
  and only if Sm >= 1.12 AND at least one of {Zkr, Smmpm, Zicfilp, Smepmp} is
  implemented. When XiangShan is synthesized with none of these extensions
  enabled, any M-mode CSR access to 0x747/0x757 will succeed (reading back
  zero-filled RO fields) instead of raising an illegal instruction exception
  as required. The noCSRIllegal check at NewCSR.scala:1021 will never flag
  this address as invalid because mseccfg is an unconditional key in csrRwMap.
Consequence: info_leak
Pattern:
  mseccfg.*CSRModule|CSRModule\("Mseccfg"|csrRwMap.*mseccfg|machineLevelCSRMod
  s.*mseccfg|noCSRIllegal.*mseccfg|setAddr\(CSRs\.mseccfg\)

[potential_risk] src/main/scala/xiangshan/backend/fu/NewCSR/MachineLevel.scala:319-327  mseccfg (CSRModule instantiation)
  mseccfg CSRModule is unconditionally instantiated in the MachineLevel scope
  (line 319) and unconditionally added to machineLevelCSRMods (line 462). Per
  spec norm:mseccfg_presence (machine.adoc:2335), mseccfg 'exists if any
  extension that adds a field to mseccfg is implemented. Otherwise, it is
  reserved.' The current default XiangShan config includes 'smmpm' in
  ISAExtensions (Parameters.scala:297), so mseccfg correctly exists for that
  config. However, the RTL has NO conditional gating mechanism — if a
  configuration removes smmpm (and doesn't add zkr/smepmp/zicfilp), mseccfg
  would still be present and accessible, violating the 'otherwise reserved'
  rule. This is a parameterization robustness gap.
