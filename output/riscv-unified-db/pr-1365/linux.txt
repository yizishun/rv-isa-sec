PR #1365  target=linux  overall=not_implemented
Spec: Ssube allows U-mode big-endian via sstatus.UBE but S-mode kernel accesses to user memory always use little-endian, creating an inherent endianness mismatch that the kernel is not architected to handle.
Violation:
  Kernel accesses user-space memory (via
  copy_from_user/copy_to_user/put_user/get_user or signal frame setup)
  expecting little-endian byte order, while the user process runs with
  sstatus.UBE=1 and interprets that same memory as big-endian. Since S-mode
  data accesses are unaffected by UBE, the kernel and user process disagree on
  byte order of shared data structures.
Consequence: data_corruption
Pattern:
  copy_(from|to)_user|put_user|get_user|setup_sigframe|ptrace_(getregs|setregs
  )|__access_remote_vm
------------------------------------------------------------

[not_implemented] arch/riscv/include/asm/uaccess.h:59-62  __enable_user_access / __disable_user_access
  The user memory access enable/disable macros only manipulate SR_SUM
  (Supervisor User Memory access). When SR_SUM is set, S-mode load/store
  instructions can access user pages, but these accesses follow S-mode
  endianness (SBE), NOT U-mode endianness (UBE). If a user process runs with
  sstatus.UBE=1 (big-endian), the kernel's loads/stores via these paths will
  produce byte-swapped data because the kernel sees little-endian while user-
  space sees big-endian. There is no byte-swap logic in any user-access path.
  | #define __enable_user_access()           \
  |     __asm__ __volatile__ ("csrs sstatus, %0" : : "r" (SR_SUM) : "memory")
  | #define __disable_user_access()          \
  |     __asm__ __volatile__ ("csrc sstatus, %0" : : "r" (SR_SUM) : "memory")

[not_implemented] arch/riscv/kernel/entry.S:183-301  handle_exception / ret_from_exception
  The trap entry path saves all of sstatus into pt_regs->status (line 190) and
  restores it on return (line 301). Since sstatus is fully round-tripped
  through pt_regs, any UBE bit set by hardware or previously configured would
  survive traps and context switches. However, the trap entry also clears
  SR_SUM | SR_FS_VS | SR_ELP from sstatus (line 183) but does NOT clear or
  mask the UBE bit. If a hardware implementation makes UBE writable from
  U-mode (via some mechanism), the UBE value set by user-space would persist
  into the kernel's view of sstatus. While this does not affect S-mode
  accesses, it means the kernel has no sanitization of the UBE bit on trap
  entry.
  | csrrc s1, CSR_STATUS, t0    // clears SUM|FS|VS|ELP, but NOT UBE
  | ...
  | REG_S s1, PT_STATUS(sp)     // save to pt_regs
  | ...
  | csrw CSR_STATUS, a0         // restore full sstatus including UBE

[not_implemented] arch/riscv/include/uapi/asm/byteorder.h:1-10  (byteorder selection)
  The byteorder header unconditionally selects little-endian via '#include
  <linux/byteorder/little_endian.h>'. There is no conditional logic to support
  runtime or compile-time big-endian user-space. All __swab functions,
  le_to_cpu, be_to_cpu macros are resolved at compile time for a little-endian
  kernel, with no awareness that user-space might be big-endian.
