PR #1276  target=freebsd-src  overall=potential_risk
Spec: FreeBSD's FPU management relies solely on mstatus.FS for FP access gating, ignoring the state-enable CSR chain (mstateen0/sstateen0/hstateen0) that Zfinx+Smstateen systems require per the updated check_f_ok — kernel FPU save/restore would trap with illegal-instruction on such hardware
Violation:
  FreeBSD kernel FPU save/restore in swtch.S
  (__fpe_state_save/__fpe_state_load macros) and fpe.c
  (fpe_enable/fpe_store/fpe_restore) sets sstatus.FS to enable F-register
  access, but on a Zfinx+Smstateen system the state-enable CSRs
  (mstateen0.FCSR, sstateen0.FCSR) are the actual gate for FP instruction
  legality — not mstatus.FS. Since FreeBSD has zero awareness of the state-
  enable CSR chain (no mention of mstateen0/sstateen0 anywhere in sys/riscv),
  if these CSRs power up with FCSR=0 on such hardware, every kernel-side FPU
  access (frcsr, fscsr, fsd, fld) would raise an illegal-instruction
  exception, panicking the kernel during context switch or fpe_init at boot.
Consequence: denial_of_service
Pattern:
  csrs sstatus, SSTATUS_FS_INITIAL without preceding csr-set of mstateen0.FCSR
  or sstateen0.FCSR; direct f-register access (frcsr/fscsr/fsd/fld) without
  stateen CSR audit

[not_implemented] sys/riscv/include/riscvreg.h:67-72  
  The RISC-V register definitions header defines SSTATUS_FS_* constants but
  has zero definitions for mstateen0, sstateen0, hstateen0 CSRs or their bit
  fields (FCSR, C, JVT, CTR, etc.). This absence means no kernel code can
  reference the stateen CSR chain — the entire Smstateen/Ssstateen extension
  is unknown to FreeBSD's RISC-V port.
