PR #1245  target=qemu  overall=compliant
Spec: QEMU TCG vector load emulation may leak data through destination vector register elements written past the faulting index before a memory exception is delivered, violating guest kernel expectations about observable architectural state after page faults
Violation:
  In QEMU TCG, vector load instructions (vle*.v, vlse*.v, vluxei*.v,
  vloxei*.v) are translated into host code that iterates over vector elements.
  When a guest page fault or access fault occurs at element index N during
  this iteration, QEMU's generated host code may have already written loaded
  data to destination vector register elements at indices > N before the
  exception is delivered. If QEMU does not precisely match the hardware's
  policy for VECTOR_LOAD_PAST_TRAP (whether elements past the trap index are
  clobbered or preserved), the guest exception handler will observe vector
  register state that differs from real silicon. Conversely, if QEMU preserves
  elements past the trap (the safe default for TCG) but the guest kernel was
  tested on hardware that clobbers them, guest software may incorrectly rely
  on QEMU's 'cleaner' state and leak sensitive kernel data across privilege
  boundaries after an mmap'd page fault on vector loads.
Consequence: info_leak
Pattern:
  TCG vector load helper that writes to vreg before or without checking for
  memory access faults per element; gen_helper_vle_v or similar helpers that
  batch-write destination vector registers independently of trap delivery
  order; missing post-trap vector register element restoration in
  HELPER(vle*_v) implementations in target/riscv/vector_helper.c

[potential_risk] target/riscv/insn32.decode:399-402  decode (vlxei8_v through vlxei64_v)
  Ordered (vloxei*) and unordered (vluxei*) indexed loads are decoded
  identically to the same vlxei*_v helpers. The funct3 bit pattern '0-1'
  accepts both variants (line 399). The spec distinguishes these: unordered
  loads allow arbitrary element access order, while ordered loads must access
  elements in element order. QEMU translates both to the same
  vext_ldst_index() helper which accesses elements in sequential order. While
  this is functionally correct (sequential order satisfies both ordered and

  software bugs that depend on specific memory ordering behavior of unordered
