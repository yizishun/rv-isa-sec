PR #1240  target=xiangshan  overall=compliant
Spec: AMO aq/rl ordering bits are wildcarded in decode and never enforced in the pipeline FSM, causing multi-hart memory ordering violations when Zaamo-spec-compliant software relies on acquire/release semantics for synchronization
Violation:
  XiangShan AtomicsUnit ignores aq/rl bits (inst[26:25]) entirely — the decode
  table uses wildcard '??' for these bits in LR/SC/AMO BitPat patterns, and
  the AtomicsUnit FSM never inspects or enforces acquire/release ordering
  semantics. No memory fence is injected for .aq, .rl, or .aqrl annotated
  atomics. Under Zaamo/Zabha/Zacas, if the spec mandates differentiated aq/rl
  behavior, XiangShan treats all AMOs identically, violating the memory
  consistency model.
Consequence: race_condition
Pattern:
  aq.*rl|acquire|release|inst\(26,25\)|FUNCT7.*aq|MemoryOrder|AQRL|BitPat.*\?\
  ?.*0101111
