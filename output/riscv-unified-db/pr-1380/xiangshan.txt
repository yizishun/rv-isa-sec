PR #1380  target=xiangshan  overall=bug_confirmed
Spec: Smepmp extension definition activates mseccfg CSR dependency but XiangShan hardwires MML/MMWP/RLB as RO=0 with no MML truth table in the PMP checker — M-mode unconditional memory access pass-through persists even when software configures Smepmp lockdown, creating a privilege-escalation gap where trusted-execution-environment isolation is silently absent in hardware.
Violation:
  When XiangShan RTL instantiates mseccfg (MachineLevel.scala:319-327) and the
  CSR module unconditionally decodes mseccfg without checking the misa.Smepmp
  extension bit, the hardware exposes MML/MMWP/RLB fields (bits 0-2) as RO=0.
  If software writes mseccfg expecting Smepmp-compliant behavior, the write is
  silently dropped at CSR write-back (wen asserted but reg hardwired via RO),
  and the PMP checker at PMP.scala:424 continues granting M-mode unconditional
  pass-through (passThrough = mode > 1.U) with no MML qualifier and no MML
  truth table in pmp_check (PMP.scala:404-412). The result: hardware allows
  M-mode to access all physical memory while software believes Smepmp
  restrictions are active.
Consequence: privilege_escape
Pattern:
  (mseccfg.*(MML|MMWP|RLB).*RO|mseccfg\.regOut.*(0|1|2)|pmp_match_res.*passThr
  ough.*mode.*>.*1|pmp_check.*cfg\.r.*cfg\.w.*cfg\.x(?!.*mml|.*priv|.*mode))

[bug_confirmed] src/main/scala/xiangshan/backend/fu/PMP.scala:404-412  pmp_check
  pmp_check performs simple permission bit matching (cfg.r/cfg.w/cfg.x)
  without any awareness of privilege mode or mseccfg.MML. When MML=1, the PMP
  cfg bits encode different semantics per the truth table (e.g., LRWX=0010
  with L=0 means 'M-mode Read/Write, S/U Read-only' for shared data). The
  current checker treats cfg.r/w/x literally regardless of MML, so it would
  incorrectly allow S/U-mode writes to a shared-data region that should be
  read-only for S/U, or incorrectly deny M-mode access to an M-mode-only rule
  where M-mode should be enforced.
  | def pmp_check(cmd: UInt, cfg: PMPConfig) = {
  |   val resp = Wire(new PMPRespBundle)
  |   resp.ld := TlbCmd.isRead(cmd) && !TlbCmd.isAmo(cmd) && !cfg.r
  |   resp.st := (TlbCmd.isWrite(cmd) || TlbCmd.isAmo(cmd)) && !cfg.w
  |   resp.instr := TlbCmd.isExec(cmd) && !cfg.x
  |   resp.mmio := false.B

  unlocked entries for M-mode. When MML=1 per Smepmp spec, the L bit semantics
  change: L=0 means S/U-mode-only (enforced on S/U, denied on M) and L=1 means
  M-mode-only. The current ignore logic treats L=0 entries as 'always bypass
  for M-mode' which is correct only for the pre-Smepmp baseline. With MML=1,
  M-mode should instead be denied by L=0 entries (S/U-mode-only rules deny
  M-mode). The ignore expression must be conditioned on !mseccfg.MML.
  | pmpEntries.zip(pmpDefault +: pmpEntries.take(num-1)).zipWithIndex.foreach{ case ((pmp, last_pmp), i) =>

  |   val cur = WireInit(pmp)
