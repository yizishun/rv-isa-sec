PR #1380  target=linux  overall=bug_confirmed
Spec: Kernel writes PMP configs assuming classic L-bit semantics without checking mseccfg.MML, so Smepmp-enabled firmware can redefine PMP encoding under the kernel's feet causing boot failure or privilege boundary collapse
Violation:
  Linux kernel writes PMP configuration registers (e.g., head.S:239-240) and
  any future KVM PMP emulation code without first checking mseccfg.MML state.
  When Smepmp MML=1, the pmpcfg encoding table is redefined — the kernel's
  existing L=0, R/W/X=1 NAPOT rule no longer grants S-mode all-access but
  becomes M-mode-only, potentially leaving S-mode with no usable memory
  mappings and crashing the kernel at boot or during KVM guest entry.
Consequence: denial_of_service
Pattern:
  csrw\s+CSR_PMPCFG|write_pmpcfg|pmpcfg.*write|pmp_set|__kvm_riscv.*pmp
------------------------------------------------------------
[bug_confirmed] arch/riscv/kernel/head.S:237-240  _start_kernel
  When CONFIG_RISCV_M_MODE=y, the kernel writes PMPCFG0 with encoding
  (PMP_A_NAPOT | PMP_R | PMP_W | PMP_X) = L=0, R=1, W=1, X=1, A=NAPOT without
  checking mseccfg.MML. The Smepmp spec redefines the pmpcfg encoding table
  when MML=1: L=0,R/W/X=1 becomes an S/U-mode-only rule that is denied
  (access-fault) to M-mode, while granting full R/W/X access only to S/U mode.
  If BootROM sets mseccfg.MML=1 before handing off to the kernel, this csrw at
  line 240 immediately denies M-mode access to all memory — the next
  instruction fetch faults and the kernel crashes at boot. The kernel's csr.h
  (lines 246-249) defines only MSECCFG_PMM bits; MSECCFG_MML (bit 0) is not
  defined, and no Smepmp-aware code exists anywhere in arch/riscv/.
  | li a0, -1
  | csrw CSR_PMPADDR0, a0
  | li a0, (PMP_A_NAPOT | PMP_R | PMP_W | PMP_X)
  | csrw CSR_PMPCFG0, a0
  References:
    - riscv-isa-manual/src/priv/smepmp.adoc:44-66
      "The physical memory protection rules when mseccfg.MML is set to 1:
      Row L=0,R=1,W=1,X=1 → M Mode: Access Exception, S/U Mode:
      Read/Write/Execute region"
    - riscv-isa-manual/src/priv/machine.adoc:2437-2438
      "An S/U-mode-only rule is enforced on Supervisor and User modes and
      denied on Machine mode."
    - riscv-isa-manual/src/priv/machine.adoc:2422-2423
      "This is a sticky bit, meaning that once set it cannot be unset
      until a PMP reset."

[bug_confirmed] arch/riscv/include/asm/csr.h:245-249  N/A (header definitions)
  The mseccfg bit definitions are incomplete: only MSECCFG_PMM and PMLEN
  variants are defined (lines 246-249). The Smepmp extension requires
  MSECCFG_MML (bit 0), MSECCFG_MMWP (bit 1), and MSECCFG_RLB (bit 2)
  definitions — none exist here. This absence means kernel code has no way to
  detect SMEPMP MML state before writing PMP configuration registers,
  contributing directly to the boot-crash vulnerability in head.S.
  | /* mseccfg bits */
  | #define MSECCFG_PMM			ENVCFG_PMM
  | #define MSECCFG_PMM_PMLEN_0		ENVCFG_PMM_PMLEN_0
  | #define MSECCFG_PMM_PMLEN_7		ENVCFG_PMM_PMLEN_7
  | #define MSECCFG_PMM_PMLEN_16		ENVCFG_PMM_PMLEN_16
  References:
    - riscv-isa-manual/src/priv/images/wavedrom/mseccfg.edn:1-16
      "mseccfg register layout: bit 0 = MML, bit 1 = MMWP, bit 2 = RLB"
    - riscv-isa-manual/src/priv/machine.adoc:2387-2389
      "The Smepmp extension adds the RLB, MMWP, and the MML fields in
      mseccfg."

[not_implemented] arch/riscv/kvm:0-0  N/A (KVM subsystem)
  KVM on RISC-V has no PMP emulation or mseccfg virtualization code. While
  this means no current Smepmp/PMP KVM vulnerability exists, it also means
  that if KVM PMP emulation is added in the future, it must respect the Smepmp
  MML redefined encoding table for correct guest behavior. The KVM subsystem
  grep returns zero matches for 'pmp', 'PMP', 'mseccfg', or 'MSECCFG'.
  | (no PMP or mseccfg handling in arch/riscv/kvm/)
