PR #1281  target=qemu  overall=compliant
Spec: vsetvli must zero vl when setting vtype.VILL on illegal vtype encoding — failure leaks stale vl from prior valid vector context across privilege domains or VM exits
Violation:
  QEMU's vsetvli/vsetivli/vsetvl implementation sets CSR vtype.VILL=1 for an
  illegal vtype encoding but fails to also zero CSR vl.VALUE in the same
  operation, leaving the architectural vl register holding a stale value from
  a prior valid vector configuration
Consequence: info_leak
Pattern:
  vsetvli.*VILL|vtype.*vill.*vl|set_vill|helper_vsetvl.*vl|vsetvl.*invalid.*vt
  ype

[potential_risk] target/riscv/cpu.c:784-784  riscv_cpu_reset_hold
  CPU reset sets env->vill = true without explicitly zeroing env->vl. On cold
  boot, env->vl is zero due to g_malloc0 initialization of the CPU object.
  However, on warm reset, env->vl retains its prior value, creating a
  potential info leak: a guest reading the vl CSR before executing any vsetvl
  instruction can observe a stale vector length from before reset. The spec
  (vector-common.adoc:670) recommends vl be set to zero at reset. env->vtype
  is also not zeroed, creating a similar issue for non-VILL vtype bits.
  | env->vill = true;
