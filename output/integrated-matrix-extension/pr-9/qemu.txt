PR #9  target=qemu  overall=compliant
Spec: Six integrated-matrix multiply-accumulate instructions hardwire vm=1 (masking reserved); QEMU's existing require_vm() helper is too permissive and would allow vm=0 to generate untested masked-execution TCG code, creating a divergence between emulated and real-hardware behavior that a malicious guest could exploit for emulation detection or to trigger bugs in the unvalidated masked code path
Violation: In QEMU TCG, when implementing the integrated-matrix multiply-accumulate instructions (vmmacc, vwmmacc, vqwmmacc, vfmmacc, vfwmmacc, vfqwmmacc), the translator accepts vm=0 in the encoding and generates a masked-execution code path. Since these instructions have vm hardwired to 1 in the spec, QEMU's existing require_vm(vm, vd) helper (which returns true for vm=0,v!=0) would incorrectly permit masked matrix multiply-accumulate — creating a TCG execution path that never exists in real hardware and has therefore never been validated against physical silicon behavior.
Consequence: function_loss
Pattern: trans_rvv.c.inc translator functions for matrix multiply-accumulate that call require_vm() (allows vm=0 with vd!=0) instead of explicitly rejecting vm==0; OR encoding diagrams in insn32/insn16 decode tables where the vm bit is not hardwired to 1
