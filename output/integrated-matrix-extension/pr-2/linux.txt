PR #2  target=linux  overall=bug_confirmed
Spec: New vtype CSR fields (lambda[2:0], altfmt_A/B) introduced by IME are implicit architected state that must be context-switched; failure to save/restore them permits cross-process matrix computation corruption via vtype pollution
Violation: Linux kernel context switch saves/restores vtype CSR without preserving the lambda[2:0] (bits [XLEN-2:XLEN-4]), altfmt_A (bit 9), or altfmt_B (bit 10) fields newly defined by the Integrated Matrix extension, allowing one process's matrix tile geometry or signedness/format configuration to leak into another process
Consequence: data_corruption
Pattern: __state_to_v_state|__v_state_to_state|vstate_ctrl.*vtype|vtype.*save|vtype.*restore
------------------------------------------------------------

[potential_risk] arch/riscv/include/asm/vector.h:167-194  __vstate_csr_restore
  Restores vtype via 'vsetvl x0, %2, %1' where %1 is src->vtype (the full saved value). [bug_confirmed] arch/riscv/kernel/ptrace.c:148-152  invalid_ptrace_v_csr
  ACTIVELY REJECTS Zvvm vtype bits. The 'reserved' mask is computed as ~(VTYPE_VSEW | VTYPE_VLMUL | VTYPE_VMA | VTYPE_VTA) = ~0xFF, which rejects ANY bits outside the standard V fields (bits 63:8). Zvvm's lambda[2:0] (bits 62:60), altfmt_A (bit 9), and altfmt_B (bit 10) all fall in this rejected range. Any ptrace SETREGSET or CRIU checkpoint/restore of a Zvvm-using process will fail with -EINVAL. This is a concrete, demonstrable semantic gap where the kernel's explicit field knowledge actively breaks Zvvm compatibility.
