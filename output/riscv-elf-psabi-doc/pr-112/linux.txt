PR #112  target=linux  overall=compliant
Spec: If kernel and userspace disagree on the padded size/alignment of non-power-of-two atomic types (e.g., a 24-bit atomic struct padded to 32 bits per psABI), the kernel may read stale bytes, write to wrong offsets, or trigger spurious alignment faults when accessing userspace atomics via futex or ptrace, causing silent data corruption in synchronization primitives shared across the kernel-user boundary.
Violation: Linux kernel reads or writes a userspace atomic variable (e.g., via futex(2), ptrace(2), or a shared-memory ABI structure) using a size or alignment that differs from what the userspace compiler produced under this psABI rule — specifically, when the kernel treats an atomic type at its unpadded size/alignment while userspace has promoted it to the next power-of-two width and alignment.
Consequence: data_corruption
Pattern: kernel access to userspace atomic<T> or _Atomic(T) where sizeof(T) is not a power of two, or where natural alignment differs from the psABI-promoted alignment; futex word access, UAPI struct members declared with __u32/__u64 but used as atomics in userspace, and vDSO atomics on non-power-of-two types.

[potential_risk] kernel/futex/futex.h:77-80  futex_size
  futex_size() computes `1 << (flags & FLAGS_SIZE_MASK)`, yielding 1, 2, 4, or 8 bytes. If the futex_flags_valid() gate at line 91 were removed to enable non-32-bit futexes, the RISC-V arch code would need corresponding support: (a) 8-bit futexes would need .b-suffix AMOs (requires Zabha extension, not universally available on RISC-V); (b) 16-bit futexes would need .h-suffix AMOs (also Zabha); (c) 64-bit futexes on RV64 would need .d-suffix AMOs (requires Zaamo, usually present). Without Zabha, the current AMO-based arch_futex_atomic_op_inuser() and the LR/SC-based futex_atomic_cmpxchg_inatomic() would fail to compile or would silently produce wrong code. This is a potential risk only if the 32-bit-only gate is removed without RISC-V arch review.
