PR #501  target=freebsd-src  overall=potential_risk
Spec: FreeBSD's unwind.c already uses sizeof(uintptr_t) (=PTRSZ) for frame-record offsets, making it spec-compliant, but riscvreg.h's XLEN_BYTES macro (XLEN/8) is a latent hazard: any future kernel code or ILP32 ABI support that uses XLEN_BYTES instead of sizeof(void*) for user-stack frame records would produce wrong offsets, enabling controlled stack-walk hijack and potential privilege escalation via crafted ILP32 binaries.
Violation: FreeBSD kernel code (unwinder, signal delivery, kdb) computes frame-record offsets using XLEN_BYTES instead of sizeof(uintptr_t) when FreeBSD gains ILP32 or mixed-XLEN ABI support — on RV64ILP32, XLEN=64 but PTRSZ=32, causing the kernel to read return addresses and saved frame pointers at wrong offsets (fp-16/-8 instead of fp-8/-4), dereferencing garbage as control-flow targets.
Consequence: privilege_escape
Pattern: XLEN_BYTES|XLEN\b.*\bframe|\bfp\b.*\bXLEN in riscv/ tree combined with stack frame access
------------------------------------------------------------
