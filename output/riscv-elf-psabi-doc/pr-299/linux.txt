PR #299  target=linux  overall=bug_confirmed
Spec: Kernel has zero EF_RISCV_RVE awareness; loads LP64E binaries with full 31-GPR semantics, exposing register state in ptrace/signals/coredumps that the LP64E ABI declares non-participating temporaries (x16-x31)
Violation: Linux kernel loads an LP64E ELF binary (ELFCLASS64 + EF_RISCV_RVE) but elf_check_arch() in arch/riscv/include/asm/elf.h does not inspect EF_RISCV_RVE, so the kernel applies full LP64 register semantics: all 31 GPRs are saved/restored in signal frames (restore_sigcontext/setup_sigframe in signal.c), exposed via ptrace (user_regs_struct in ptrace.h), included in core dumps (ELF_CORE_COPY_REGS), and context-switched (save_from_x6_to_x31/restore_from_x6_to_x31 + __switch_to s2-s11 save/restore). The LP64E ABI declares x16-x31 do not participate in the calling convention (all are temporaries), so the kernel exposes register state that userspace components compiled for LP64E do not expect to be preserved nor meaningful.
Consequence: info_leak
Pattern: elf_check_arch.*EM_RISCV && !(flags & EF_RISCV_RVE)
------------------------------------------------------------

  elf_check_arch() is the sole gatekeeper for native ELF binary loading. It checks e_machine==EM_RISCV and EI_CLASS==ELF_CLASS but does NOT inspect e_flags for EF_RISCV_RVE. An LP64E ELF binary (ELFCLASS64 + EF_RISCV_RVE) passes this check and is loaded with full 31-GPR register semantics, even though the RV64E spec declares only x0-x15 exist and x16-x31 are reserved. EF_RISCV_RVE is not even defined in this kernel tree (git grep returns zero results in include/). This is the root cause: the kernel has zero awareness of RV64E.

  |                    ((x)->e_ident[EI_CLASS] == ELF_CLASS))

[bug_confirmed] arch/riscv/kernel/entry.S:421-470  __switch_to
  __switch_to (the context-switch path) saves and restores callee-saved registers s0-s11 (x8-x9, x18-x27) into thread_struct. Of these, s2-s11 (x18-x27) are reserved/do-not-exist in the RV64E LP64E ABI. When context-switching between processes, the kernel unconditionally saves and restores these registers for ALL processes, including LP64E ones. Any kernel-internal data that happened to be in those registers (stale values from prior system calls, interrupt handlers, or other processes) is preserved and restored, creating a cross-process info_leak channel. Additionally, s2-s11 are saved on every exception entry via save_from_x6_to_x31 (asm.h:141-150).

[bug_confirmed] arch/riscv/include/asm/asm.h:128-185  save_from_x6_to_x31 / restore_from_x6_to_x31
  The save_from_x6_to_x31 and restore_from_x6_to_x31 macros are used on every exception entry/return (handle_exception, ret_from_exception, handle_kernel_stack_overflow). They unconditionally save and restore all GPRs x6 through x31 into pt_regs on the stack. For an LP64E process, this saves registers x16-x31 which the spec declares reserved/do-not-exist. [potential_risk] arch/riscv/include/asm/ptrace.h:15-56  pt_regs
  struct pt_regs is the kernel's in-memory representation of saved register state. It includes all 31 GPRs. While this is required for kernel operation even with LP64E userspace (the kernel itself still needs the full register file), the fact that pt_regs is directly exposed to userspace via sigcontext.restore_sigcontext/setup_sigcontext (the comment at ptrace.h:24 says 'struct user_regs_struct must form a prefix of struct pt_regs') means the kernel's internal register state layout IS the ABI. This architectural coupling means the full 31-GPR layout cannot change without breaking userspace ABI, even if LP64E were properly supported.
