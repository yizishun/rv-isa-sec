PR #470  target=linux  overall=compliant
Spec: On RISC-V big-endian (BE) systems, instructions remain little-endian regardless of data endianness; the kernel's signal trampoline, vDSO, and code-patching paths must emit LE-encoded instruction bytes into what is otherwise BE data memory, and failure to decouple the two results in corrupted instructions being executed by userspace
Violation: Kernel writes raw instruction bytes to userspace-accessible memory (e.g., sigreturn trampoline on stack, vDSO code pages, uprobes xol slot) but uses the target process's data endianness instead of the architectural requirement that all RISC-V instructions are always little-endian, causing the bytes to be byte-swapped relative to correct instruction encoding
Consequence: denial_of_service
Pattern: arch/riscv/**/signal.c or arch/riscv/**/vdso/* or arch/riscv/**/probes/* where __kernel_rt_sigreturn[] or equivalent instruction-byte arrays are written to memory using store instructions that assume data-endianness—check for memcpy() or word stores of instruction immediates without an explicit LE-encode assertion

[potential_risk] arch/riscv/kernel/probes/uprobes.c:175-178  arch_uprobe_copy_ixol
  The ebreak insertion on line 177 uses '*(uprobe_opcode_t *)dst = __BUG_INSN_32' (0x00100073) — a native-endian u32 store. Currently harmless because RISC-V has no big-endian support, making native-endian == little-endian by definition. If CONFIG_CPU_BIG_ENDIAN were ever enabled on RISC-V, this u32 store would write bytes {0x00,0x10,0x00,0x73} in memory-order, which is NOT the correct LE instruction encoding {0x73,0x00,0x10,0x00}. The same pattern exists in patch_insn_write() → copy_to_kernel_nofault() for kernel text, and in kprobes.c:28-33 which writes __BUG_INSN_32 via patch_text_nosync(). These would all need LE-explicit stores (e.g., put_unaligned_le32() or __BUG_INSN_32_LE) if big-endian support is added.
