PR #498  target=linux  overall=potential_risk
Spec: Loading a pure-capability RVY binary without kernel CHERI support silently strips all capability-enforced spatial/permission safety, giving the binary unrestricted memory access equivalent to privilege escape
Violation: Linux kernel ELF loader accepts bins with EF_RISCV_RVY in e_flags without explicit support, then executes a pure-capability (CHERI) binary as a regular RISC-V process — no capability register init, no bounds enforcement, and no capability-aware signal/context-switch handling.
Consequence: privilege_escape
Pattern: elf_check_arch.*e_flags.*EF_RISCV|ELF_HWCAP.*riscv|NT_RISCV|compat_elf_check_arch.*riscv|arch_check_elf.*e_flags
------------------------------------------------------------
[potential_risk] arch/riscv/include/asm/elf.h:37-38  elf_check_arch
  elf_check_arch checks only e_machine==EM_RISCV and EI_CLASS; it performs zero validation on e_flags. If EF_RISCV_RVY is allocated for CHERI pure-capability binaries, the kernel will silently accept and attempt to execute them as regular RISC-V processes with no capability register init, no bounds enforcement, and no capability-aware context-switch or signal-frame handling.
  | #define elf_check_arch(x) (((x)->e_machine == EM_RISCV) && \
  |                    ((x)->e_ident[EI_CLASS] == ELF_CLASS))

[potential_risk] arch/riscv/kernel/process.c:119-124  compat_elf_check_arch
  compat_elf_check_arch has the same gap: it validates e_machine and EI_CLASS but never inspects e_flags. A 32-bit CHERI RVY binary (ELFCLASS32 + EM_RISCV + EF_RISCV_RVY) would pass this check on a compat-enabled kernel.
  | bool compat_elf_check_arch(Elf32_Ehdr *hdr)

  |         return compat_mode_supported &&
  |                hdr->e_machine == EM_RISCV &&

  | }

[potential_risk] arch/riscv/include/asm/elf.h:1-156  (no arch_check_elf override)
  RISC-V does not define arch_check_elf() or arch_elf_pt_proc(), falling through to the fs/binfmt_elf.c default stubs that always return 0. The generic ELF loader calls arch_check_elf() at fs/binfmt_elf.c:1004 as the final gate before committing the load, but RISC-V does not use it to reject unrecognized e_flags.

[potential_risk] arch/riscv/include/uapi/asm/elf.h:1-101  (no EF_RISCV definitions)
  The kernel has zero EF_RISCV_* flag definitions. There is no constant EF_RISCV_RVY, no EF_RISCV_FLOAT_ABI checks, and no EF_RISCV_RVC check. The kernel is entirely agnostic to the RISC-V ELF e_flags field, which means any newly allocated flag (like EF_RISCV_RVY for CHERI) will be silently ignored rather than rejected.
  | /* uapi/asm/elf.h defines only relocation types (R_RISCV_*).
  |  * No EF_RISCV_* e_flags constants exist anywhere in the kernel tree. */
