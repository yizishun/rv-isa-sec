PR #1879  target=qemu  overall=bug_confirmed
Spec: Smepmp field rename MMWP→MMAP at bit 1 — QEMU still uses the deprecated proposal-era name MSECCFG_MMWP; functionally benign today but risks missing future MMAP-specific spec tightening
Violation: QEMU hardcodes the pre-ratification field name 'MMWP' (Machine-Mode Whitelist Policy) at pmp.h:45 (MSECCFG_MMWP = 1 << 1) while the integrated spec renames it to 'MMAP' (Machine-Mode Allowlist Policy). The bit position and sticky semantics are unchanged, so current enforcement is functionally correct. However, if the ratified spec later adds MMAP-specific WARL constraints, access-fault side-effects, or discovery requirements beyond what the MMWP name implied, QEMU's stale identifier and any MMWP-gated code paths would fail to enforce the new MMAP semantics.
Consequence: privilege_escape
Pattern: MSECCFG_MMWP|mseccfg\.MMWP|MMWP_ISSET|MSECCFG_MMWP_ISSET
------------------------------------------------------------

[bug_confirmed] target/riscv/machine.c:426-504  vmstate_riscv_cpu
  env.mseccfg is NOT included in vmstate_riscv_cpu or any subsection (vmstate_pmp only migrates pmp_entry_t array, not mseccfg). On live migration, the destination QEMU instance will receive mseccfg=0 (default/reset value), silently dropping the MMWP/MMAP allowlist policy, MML lockdown, and RLB bits. This means: (1) if MMWP/MMAP was set on the source, M-mode accesses will incorrectly succeed without PMP rules on the destination; (2) if MML was set, PMP entry lock bits lose their lockdown effect. This is a privilege-escalation window during and after live migration until the guest OS re-programs mseccfg.
