PR #1879  target=qemu  overall=bug_confirmed
Spec: Smepmp spec renames MMWP→MMAP at mseccfg bit 1 and mandates mseccfg.MML/MMAP/RLB reset to 0; QEMU must match this bit-exact, enforce sticky-bit write semantics for MML/MMAP, and enforce RLB lock-on-L behavior to prevent guest M-mode from downgrading PMP isolation after lockdown.
Violation:
  QEMU reset logic for mseccfg CSR does not clear bits MML(0), MMAP(1), and
  RLB(2) to 0 on hart reset, OR QEMU still references the old field name MMWP
  at bit 1 instead of the renamed MMAP, OR QEMU fails to enforce that MML and
  MMAP are sticky bits (writable-1-to-0 ignored until reset), allowing guest
  M-mode to clear them after lockdown and silently bypass Smepmp memory access
  restrictions.
Consequence: privilege_escape
Pattern:
  mseccfg.*reset|mseccfg.*MMWP|mseccfg.*MMAP|mseccfg.*sticky|mseccfg.*warl.*MM
  L|mseccfg.*warl.*RLB|pmpcfg.*lock.*mseccfg|pmp_is_smepmp|sempmp_locked
------------------------------------------------------------

[compliant] target/riscv/pmp.c:686-695  mseccfg_csr_write
  Sticky-bit semantics for MML and MMWP are correctly implemented. The pattern
  'val |= (env->mseccfg & mask)' ORs in the current values of MML and MMWP,
  preventing a write of 0 to clear these bits once set. This matches the spec:
  MML and MMWP are sticky bits that cannot be unset until PMP reset
  (norm:mseccfg_mmwp_op_warl, norm:mseccfg_mml_sticky). When Smepmp is not
  implemented, MML, MMWP, and RLB are all forced to 0 via 'val &= ~(mask)'.
  TLB flush is correctly triggered when MMWP/MML actually change.
  | if (riscv_cpu_cfg(env)->ext_smepmp) {
  |     /* Sticky bits */
  |     val |= (env->mseccfg & mask);
  |     if ((val ^ env->mseccfg) & mask) {
  |         tlb_flush(env_cpu(env));
  |     }
  | } else {
  |     mask |= MSECCFG_RLB;
  |     val &= ~(mask);
  | }

[bug_confirmed] target/riscv/machine.c:426-504  vmstate_riscv_cpu
  mseccfg CSR state is NOT included in the VMStateDescription for migration.
  Neither the main vmstate_riscv_cpu fields nor any subsection (vmstate_pmp,
  vmstate_envcfg, etc.) saves env.mseccfg. On live migration, if Smepmp is
  enabled and mseccfg has been configured (e.g., MML=1, MMWP=1), the
  destination VM boots with mseccfg=0 (the reset value). This silently drops
  M-mode lockdown: PMP rules revert to non-Smepmp semantics, and guest memory
  protections are defeated. This is a confirmed migration completeness bug.

[potential_risk] target/riscv/pmp.c:698-700  mseccfg_csr_write
  The Zicfilp MLPE passthrough line 'val |= (val & MSECCFG_MLPE)' is a logical
  no-op (ORing val with a subset of itself). While functionally harmless (the
  MLPE bit from the guest write passes through unchanged, which is the
  intended behavior), the code is misleading — it appears to be dead code or a
  vestige of a different intended pattern. This creates confusion about
  whether MLPE requires sticky-bit treatment (it does not — per spec it resets
  to 0 but is freely writable).
