PR #2901  target=linux  overall=compliant
Spec: Zisb barriers (TEB/MDB/DPB) are Zimop-encoded unprivileged instructions that silently become NOPs on hardware lacking Zisb but implementing Zimop; kernel relies on them for in-domain Spectre-V1 mitigation without ISA-extension guards, creating a silent information-leak vulnerability on non-Zisb hardware.
Violation: The Linux kernel emits a Zisb barrier instruction (TEB, MDB, or DPB) in a security-critical speculation boundary (e.g., bounds-check-then-access pattern in syscall handlers, seccomp filter evaluation, or eBPF JIT output) on a CPU that implements Zimop but not Zisb, treating the barrier as effective when it becomes a silent NOP. Speculative execution then crosses the barrier and leaks kernel data through a cache-based side channel observable by userspace.
Consequence: info_leak
Pattern: kernel code uses TEB, MDB, or DPB (or a macro expanding to them) without a preceding riscv_isa_extension_available() / RISCV_ISA_EXT_ZISB guard or fallback to architected speculation-barrier sequences (e.g., fence-based or CSR-based barriers). Search for '.insn' or '.word' encodings in the Zimop major opcode space alongside security-sensitive arrays indexed by user-controlled values.

[potential_risk] arch/riscv/net/bpf_jit_comp64.c:1920-1922  emit_insn (BPF JIT emission)
  BPF_ST|BPF_NOSPEC ('speculation barrier' eBPF instruction) is compiled to a no-op in the RISC-V BPF JIT (both 64-bit and 32-bit). While this does not explicitly emit Zisb barrier instructions (and thus doesn't trigger the silent-NOP-on-Zimop vulnerability directly), it means eBPF seccomp filters and eBPF programs loaded by unprivileged users cannot add speculation barriers on RISC-V. The data-masking approach in array_index_nospec() still applies in the kernel's own bounds-check paths, but eBPF programs performing their own bounds checks have no speculation barrier available.
