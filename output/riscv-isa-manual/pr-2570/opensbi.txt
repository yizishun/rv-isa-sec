PR #2570  target=opensbi  overall=bug_confirmed
Spec: Smmpm-enabled M-mode trap handlers must not perform explicit loads/stores using hardware-PM-transformed mtval values without first reversing (or accounting for) the prior PM transform, else double-masking corrupts the target physical address
Violation:
  OpenSBI M-mode trap handler reads mtval (already PM-transformed by hardware
  per pm_csr_hw_apply from the trapping privilege mode's PM settings), then
  uses this value for explicit memory accesses while Smmpm is enabled —
  hardware applies M-mode's PM transformation a second time on the already-
  transformed address (double-masking), yielding a wrong physical address.
Consequence: data_corruption
Pattern:
  csr_read(CSR_MTVAL) followed by explicit load/store (lw/ld/sw/sd) within
  M-mode trap handler when Smmpm may be enabled; also M-mode misaligned access
  emulation using mtval without clearing PM transformation before constituent
  aligned accesses
------------------------------------------------------------

[potential_risk] lib/sbi/sbi_unpriv.c:21-46  DEFINE_UNPRIVILEGED_LOAD_FUNCTION
  All unprivileged load functions (sbi_load_u8/u16/u32/u64/s8/s16/s32/ulong)
  set MPRV before performing an explicit data load. Per norm:pm_mprv_spvp
  (zpm.adoc:135), MPRV causes the pointer masking settings of the effective
  privilege mode to be applied. This is mechanically correct for single-PM
  application when the input address is untransformed — but these functions
  have no way to know whether their caller passed a PM-transformed or
  untransformed address. The vulnerability is in the callers (misaligned
  emulators, access fault emulators) that pass mtval as the address.
  | "csrrs %[mstatus], " STR(CSR_MSTATUS) ", %[mprv]\n"  // MPRV set
  | #insn " %[ret], %[addr]\n"  // explicit load → PM applies

[potential_risk] lib/sbi/sbi_trap_ldst.c:69-73  sbi_trap_emulate_load
  Instruction fetch for load emulation uses sbi_get_insn(regs->mepc, &uptrap),
  which sets MPRV+MXR and performs an explicit lhu data load on mepc. Per
  norm:pm_not_apply_implicit (zpm.adoc:67), PM does NOT apply to instruction
  fetches, but this uses an explicit data load (lhu) which IS subject to PM.
  If mepc happens to have tag bits set in the PM region (unlikely for
  instruction addresses but possible), the instruction would be read from the
  wrong physical address. Also note that sbi_get_insn sets MXR (zpm.adoc:135:
  when MXR is in effect, PM does not apply), which mitigates this in the
  current code, but sbi_load_u8/sbi_store_u8 do NOT set MXR.
  | insn = sbi_get_insn(regs->mepc, &uptrap);
  | // sbi_get_insn uses MPRV|lhu — explicit data load on mepc, PM applies
  | // But MXR is also set → PM does NOT apply per norm:pm_mxr_exception

[potential_risk] lib/sbi/sbi_fwft.c:237-262  fwft_set_pmlen
  fwft_set_pmlen configures menvcfg.PMM (for Smnpm — pointer masking for
  S-mode/next-lower mode). This is the ONLY code path in OpenSBI that touches
  pointer masking configuration, and it has ZERO integration with the trap
  handling code. When this is called to enable PM (e.g., PMLEN=7 or 16), the
  trap handlers in sbi_trap_ldst.c have no awareness that addresses in mtval
  may now be PM-transformed. The misaligned/access fault emulators will
  silently double-apply PM. Additionally, this function only controls
  menvcfg.PMM (Smnpm), not mseccfg.PMM (Smmpm) — so even if OpenSBI disables
  PM for lower modes, the hardware could have Smmpm enabled independently via
  mseccfg.
  | prev = csr_read_clear(CSR_MENVCFG, ENVCFG_PMM);
  | csr_set(CSR_MENVCFG, pmm);
  | // No notification to trap handlers; no PM-awareness flag set

[potential_risk] lib/sbi/sbi_trap_v_ldst.c:196-212  sbi_misaligned_v_ld_emulator
  Vector misaligned load emulator computes the element address from register
  state (base + vstart*stride) rather than from mtval, which correctly avoids
  the double-PM problem on the address source. However, it passes the computed
  address to sbi_load_u8 which sets MPRV, and if the register values contain
  PM tags, the address will be PM-transformed once (correct). The risk is that
  if S-mode had PM enabled and the register base has tag bits, the single PM
  application via MPRV is spec-correct — but the code has no awareness of
  whether the address is virtual or physical and does not handle the ignore-
  transform distinction (sign-extend for VA vs zero-extend for PA per
  zpm.adoc:39,53).
  | ulong addr = base + vstart * stride;
  | // ...
  | sbi_load_u8((void *)(addr + seg * len + i), &uptrap);
  | // addr from registers, not mtval — single PM via MPRV is correct
