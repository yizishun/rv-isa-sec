PR #2721  target=qemu  overall=bug_confirmed
Spec: ELEN>VLEN spec relaxation makes scalar/reduction/whole-register vector ops access register groups via EMUL=ceil(EEW/VLEN) rather than a single register; QEMU must compute EMUL dynamically instead of assuming EMUL=1, or else read/write wrong registers on ELEN>VLEN configs.
Violation: QEMU implements vector scalar move (vmv.x.s/vmv.s.x/vfmv.f.s/vfmv.s.f) or vector reduction operations (vred*.vs/vfred*.vs) or whole-register moves (vmv<nr>r.v) using the pre-relaxation semantics where scalar operands always occupy exactly one vector register (EMUL=1, ignoring ceil(EEW/VLEN)), and whole-register moves use EEW=SEW rather than EEW=min(VLEN*EMUL, SEW). When an ELEN > VLEN configuration is emulated, these operations must access vector register groups spanning ceil(EEW/VLEN) registers; using a single register would read/write only a fraction of the element bits, exposing or corrupting data from unrelated guest state.
Consequence: info_leak
Pattern: Hardcoded EMUL=1 or s->lmul=0 assumption in scalar move, reduction, or whole-register move emulation paths without computing EMUL = ceil(EEW/VLEN); also EEW computed as SEW in whole-register moves instead of min(VLEN*EMUL, SEW). Grep for vmv_x_s, vmv_s_x, vfmv_f_s, vfmv_s_f, vred, vmv[1248]r in target/riscv/ and check that s->emul derives from ceil(EEW/VLEN) rather than defaulting to 1.

[potential_risk] target/riscv/vector_helper.c:5756-5782  HELPER(vmvr_v)
  The vmvr_v helper comment states 'EEW = SEW' (line 5758) but the post-relaxation spec requires EEW = min(VLEN*EMUL, SEW) for whole-register moves.
