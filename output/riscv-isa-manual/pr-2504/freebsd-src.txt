PR #2504  target=freebsd-src  overall=bug_confirmed
Spec: bhyve guest stimecmp CSR state leaks across VM boundaries because vstimecmp is not saved/restored on VM transitions even though HENVCFG_STCE is set to enable direct VS-mode access
Violation: FreeBSD bhyve VMM sets HENVCFG_STCE to expose stimecmp to VS-mode guests but never saves/restores vstimecmp across VM transitions. When vstimecmp from a prior guest is stale and (time + htimedelta) exceeds it, hardware asserts VSTIP for the incoming guest who did not request it. Conversely, a prior guest's vstimecmp far in the future suppresses a legitimate timer interrupt the incoming guest expects. The spec mandates VSTIP = hvip.VSTIP OR vstimecmp_timer_signal, so both sources must agree; bhyve's dual-track injection (callout-driven HVIP writes AND hardware vstimecmp) creates a conflict where VSTIP can be asserted by vstimecmp after hvip.VSTIP is cleared, or vice versa.
Consequence: info_leak
Pattern: csr_write.*stimecmp|HENVCFG_STCE|vstimecmp|VTIMER.*sstc|hcounteren.*TM

[bug_confirmed] sys/riscv/vmm/vmm_riscv.c:594-597  riscv_sync_interrupts
  Dual-track VSTIP conflict: riscv_sync_interrupts() manages HVIP_VSTIP solely via the host-callout-driven interrupts_pending flag. It clears HVIP_VSTIP when interrupts_pending is 0. However, per the RISC-V spec, VSTIP = hvip.VSTIP OR vstimecmp_timer_signal. The hardware vstimecmp mechanism independently asserts VSTIP regardless of the hvip CSR bit, so clearing hvip.VSTIP does not actually suppress a pending hardware vstimecmp interrupt.
  | if (riscv_check_interrupts_pending(hypctx))
  |     hypctx->guest_csrs.hvip |= HVIP_VSTIP;
  | else
  |     hypctx->guest_csrs.hvip &= ~HVIP_VSTIP;

[bug_confirmed] sys/riscv/vmm/vmm_vtimer.c:98-119  vtimer_set_timer
  vtimer_set_timer implements a host-callout-based virtual timer (Track 1), clearing interrupts_pending (line 112) when a future timer is set, and scheduling a callout to set interrupts_pending later.
