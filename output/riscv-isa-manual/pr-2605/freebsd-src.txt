PR #2605  target=freebsd-src  overall=bug_confirmed
Spec: FreeBSD detects Sscofpmf but never manages HPM counter state — swtch.S leaks counter values across threads, scounteren stays zero blocking legitimate access, and no LCOFI handler exists, violating thread-isolation invariants when M-mode firmware has counters running
Violation: When Sscofpmf hardware is present (has_sscofpmf=1), the FreeBSD kernel never writes scounteren or mcounteren to enable HPM-counter access from S-mode, never saves/restores hpmcounter/mhpmevent state across context switches in swtch.S, and has no trap handler for the count-overflow interrupt (LCOFI) if delegated to S-mode via mideleg — counter state from M-mode firmware (OpenSBI) or prior kernel operations persists unswitched across thread boundaries, and an undelivered LCOFI interrupt may cause an unhandled-trap panic.
Consequence: info_leak
Pattern: swtch.S context-switch path missing hpmcounter/mhpmevent save/restore; no csr_write(scounteren, *) in kernel; no LCOFI trap handler registered; has_sscofpmf checked but never acted upon
------------------------------------------------------------

[bug_confirmed] sys/riscv/riscv/swtch.S:268-284  cpu_switch
  cpu_switch() saves/restores only GPRs (ra, sp, s0-s11) and optionally FPU state. No hpmcounter3–31 or mhpmevent3–31 CSR save/restore exists anywhere in the context-switch path. When M-mode firmware has configured mcounteren to grant S-mode HPM access, the 29 counter CSRs and their event-selector CSRs carry stale values from the previous thread into the next — a cross-thread information leak through performance-monitor state.

[potential_risk] sys/riscv/riscv/exception.S:41-114  save_registers
  The trap-entry save_registers macro saves all GPRs plus sepc, sstatus, stval, scause — but does not read or snapshot scounteren or any hpmcounter CSR. If the kernel ever uses HPM counters for profiling, trap entries will corrupt counter values (e.g., counting trap-handling instructions as user/kernel work). This is currently latent since hwpmc is disabled on RISC-V.

[bug_confirmed] sys/riscv/riscv/trap.c:372-376  do_trap_supervisor
  do_trap_supervisor() switch on scause has a default case that panics. If M-mode firmware sets mideleg[13] to delegate the local-counter-overflow interrupt (LCOFI) to S-mode, the kernel receives scause=0x800000000000000d (interrupt bit | 13). SCAUSE_CODE masks this to 13, which matches no case label, falls to default, and triggers panic("Unknown kernel exception") — a guaranteed denial-of-service on counter overflow.

[bug_confirmed] sys/riscv/include/intr.h:43-56  (enum definition)

[bug_confirmed] sys/riscv/include/riscvreg.h:136-175  (CSR bit definitions)

[potential_risk] sys/riscv/riscv/locore.S:230-265  (boot sequence)
  The boot sequence sets stvec and sscratch, then jumps to initriscv() → mi_startup without writing scounteren. The scounteren CSR remains at its reset value (likely 0, blocking all U-mode HPM-counter access). While this prevents user info leaks, it also means the kernel has no deliberate policy for scounteren — it passively inherits whatever M-mode left, and adds no initialization.
  | la   t0, cpu_exception_handler
  | csrw stvec, t0
  | li   t0, 0
  | csrw sscratch, t0
  | ...
  | call _C_LABEL(initriscv)
  | call _C_LABEL(mi_startup)
