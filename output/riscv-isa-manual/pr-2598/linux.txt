PR #2598  target=linux  overall=compliant
Spec: Ziccid's I-fetch ordering is per-hart; cross-hart I-D coherence still requires FENCE W,O + IPI-triggered remote FENCE.I — kernel code patches that assume Ziccid eliminates the need for cross-hart fencing would cause remote harts to execute stale instructions
Violation:
  On a Ziccid platform, the kernel relies on FENCE.I for I-D coherence after
  text patching (bpftrace, kprobes, ftrace, alternatives, module loading). If
  FENCE.I is executed on a hart other than the one that performed the store,
  and Ziccid's 'eventuality' property is relied upon without proper
  synchronization (FENCE W,O + IPI or FENCE W,W + flag + remote FENCE.I), the
  remote hart may indefinitely execute stale instructions because Ziccid
  explicitly scopes instruction-fetch ordering to the local hart — instruction
  fetches only appear in program order *per hart*, and cross-hart visibility
  of stores to instruction fetches requires explicit synchronization in
  addition to FENCE.I. The kernel's existing stop_machine()/on_each_cpu()
  FENCE.I broadcast pattern in patch_text() and flush_icache_mm() already
  handles this correctly. The vulnerable pattern would be code that performs a
  local FENCE.I after a store on one hart and expects another hart to
  eventually see the store via Ziccid's eventuality guarantee, without the
  required FENCE W,O+IPI or FENCE W,W+flag synchronization that the spec
  explicitly requires for cross-hart I-fetch visibility.
Consequence: data_corruption
Pattern:
  local_flush_icache_all\(\)|fence\.i.*(?!on_each_cpu|stop_machine|sbi_remote_
  fence_i|ipi_remote_fence_i|RISCV_FENCE.*w.*o)
