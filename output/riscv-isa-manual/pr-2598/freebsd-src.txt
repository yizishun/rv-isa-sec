PR #2598  target=freebsd-src  overall=bug_confirmed
Spec: Ziccid removes the hard FENCE.I gating invariant: stores to I-stream memory become progressively visible to the local hart's fetch stage in program order, so multi-store kernel code patches are exposed to a TOCTOU race between partial-store visibility and the final FENCE.I flush — FreeBSD's module loader and live-patching paths must ensure all stores precede a single FENCE.I without intermediary instruction fetches landing in the patched region
Violation: In the FreeBSD kernel, when a code-patching or module-loading sequence performs multiple stores to modify instruction memory and the Ziccid 'eventual visibility' property causes an instruction fetch to observe a partially-complete store chain before the final FENCE.I barrier executes — particularly on cacheable, coherent memory regions where Ziccid applies — the hart may execute half-patched instructions (e.g., a partially-written branch target, an uninitialized immediate field, or an in-progress nop-sled). FreeBSD's pmap_kenter or vtophys-based code update paths that assume FENCE.I is the sole mechanism for I-fetch visibility are unsynchronized against this eventuality.
Consequence: privilege_escape
Pattern: Multiple sequential store instructions (sb/sh/sw/sd) to a writable+executable kernel page, followed by a non-atomic FENCE.I or delayed FENCE.I, where the cumulative write crosses instruction boundaries — grep for consecutive stores to pages mapped VM_PROT_EXECUTE or consecutive stores preceding fence_i calls in machine-dependent code.
