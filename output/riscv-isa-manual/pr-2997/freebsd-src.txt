PR #2997  target=freebsd-src  overall=potential_risk
Spec: Zvt adds multi-kilobyte matrix tile state per hart that must be context-switched; FreeBSD's riscv cpu_switch/sendsig paths lack tile save/restore, leaking prior process's matrix computation results across context switches
Violation: FreeBSD kernel context-switch path (cpu_switch, savectx, set_mcontext, sendsig) saves/restores vector registers via vsetvl/vsext but does not save/restore the matrix tile state (up to 16*TE*TE bytes of architectural state per hart) or the mtype CSR (0xC23), causing tile data from the switched-out process to be readable by the switched-in process
Consequence: info_leak
Pattern: cpu_switch|savectx|restorectx|set_mcontext|get_mcontext|sendsig|sigreturn.*mtype|tile|mstatus.*MS|vtdiscard|vtmv\.t\.v|vtzero
------------------------------------------------------------

  PCB has no fields for matrix tile state (Zvt extension): no save area for tile registers (up to 16*TE*TE bytes), no slot for mtype CSR (0xC23), no XS-dirty tracking. [potential_risk] sys/riscv/riscv/swtch.S:286-305  cpu_switch
  cpu_switch checks only SSTATUS_FS (floating-point) dirty state to decide whether to save FP registers. It does not check SSTATUS_XS (extension state) or mstatus.XS, which tracks user-mode extension dirty state including vector/tile. When hardware supports Zvt, tile-dirty state would be silently lost on context switch, leaking data from the old process to the new process.

  | li t2, SSTATUS_FS_DIRTY
  | bne t3, t2, 1f  /* No, skip. */
  | li t2, ~SSTATUS_FS_MASK
  | and t3, t1, t2
  | li t2, SSTATUS_FS_CLEAN
  | or t3, t3, t2
  | sd t3, (TF_SSTATUS)(t0)

[potential_risk] sys/riscv/riscv/exec_machdep.c:245-249  set_mcontext
  set_mcontext explicitly masks SSTATUS_XS_MASK in the sstatus validation check, meaning the kernel deliberately ignores the XS (extension status) field across signal delivery.
