PR #2635  target=qemu  overall=bug_confirmed
Spec: Zvknhb implies Zvknha: QEMU must enforce that enabling Zvknhb automatically enables Zvknha, otherwise guest software checking Zvknha on a Zvknhb-advertised machine will see missing SHA-256 SEW=32 acceleration and may fall back to software paths or trap on reserved SEW encodings, breaking guest crypto stack availability assumptions.
Violation:
  QEMU advertises Zvknhb in the ISA string or device tree to the guest without
  also asserting Zvknha, or the TCG backend implements vsha2* with SEW=64
  support but fails to support SEW=32, violating the implication that Zvknhb
  includes Zvknha's full SEW=32 functionality.
Consequence: denial_of_service
Pattern:
  riscv,isa.*Zvknhb.*!Zvknha|set_misa.*Zvknhb|cfg-
  >ext_Zvknhb.*true.*ext_Zvknha.*false|prop->ext_Zvknhb.*prop->ext_Zvknha
------------------------------------------------------------
[bug_confirmed] target/riscv/cpu.c:2542-2549  ZVKNHB_IMPLIED
  The ZVKNHB_IMPLIED rule does not include Zvknha in its implied_multi_exts
  array. Per the RISC-V Vector Crypto spec (zvk.adoc:483), 'Zvknhb implies
  Zvknha', meaning enabling Zvknhb must automatically enable Zvknha. Without
  this entry, a user can configure '-cpu rv64,zvknhb=true,zvknha=false' and
  QEMU will advertise Zvknhb in the ISA string/DTB without Zvknha, violating
  the spec-mandated dependency.
  | static RISCVCPUImpliedExtsRule ZVKNHB_IMPLIED = {
  |     .ext = CPU_CFG_OFFSET(ext_zvknhb),
  |     .implied_multi_exts = {
  |         CPU_CFG_OFFSET(ext_zve64x),
  | 
  |         RISCV_IMPLIED_EXTS_RULE_END
  |     },
  | };

[potential_risk] target/riscv/tcg/tcg-cpu.c:799-804  riscv_cpu_validate_set_extensions
  The validation function checks that Zvknhb requires Zve64x but does not
  validate that Zvknha is also enabled when Zvknhb is set. While the implied-
  rules engine should handle this, there is no hard validation to catch the
  case where a user explicitly disables Zvknha while enabling Zvknhb. This is
  a secondary defense gap — the implied-rules fix (finding above) is the
  primary fix needed.
  | if ((cpu->cfg.ext_zvbc || cpu->cfg.ext_zvknhb) && !cpu->cfg.ext_zve64x) {
  |     error_setg(
  |         errp,
  |         "Zvbc and Zvknhb extensions require V or Zve64x extensions");
  |     return;
  | }

[compliant] target/riscv/insn_trans/trans_rvvk.c.inc:414-418  vsha_check_sew
  The SEW check correctly implements the Zvknhb-includes-Zvknha semantics at
  the instruction translation level: vsha2* instructions accept SEW=32 when
  either Zvknha or Zvknhb is enabled, and additionally accept SEW=64 only when
  Zvknhb is enabled. This means the TCG decode path already handles the
  implication correctly for instruction execution, even though the ISA string
  advertising does not.
  | static bool vsha_check_sew(DisasContext *s)
  | {
  |     return (s->cfg_ptr->ext_zvknha == true && s->sew == MO_32) ||
  |            (s->cfg_ptr->ext_zvknhb == true &&
  |             (s->sew == MO_32 || s->sew == MO_64));
  | }
