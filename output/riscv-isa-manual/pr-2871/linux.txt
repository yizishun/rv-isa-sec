PR #2871  target=linux  overall=compliant
Spec: PR clarifies SRET-in-M-mode (not S-mode) clears MDT/SDT and SDT-clearing is gated on Ssdbltrp; kernel returning to userspace via S-mode SRET must explicitly clear SDT or risk trapping all subsequent S-mode exceptions as unexpected double-traps
Violation:
  Kernel S-mode trap handler sets sstatus.SDT=1 (double-trap protection) then
  executes SRET to U/VS/VU, implicitly assuming the hardware will clear SDT —
  but either (a) the kernel is returning via SRET from S-mode, which is not
  covered by the spec's clearing rule (only SRET-in-M-mode clears MDT/SDT), or
  (b) Ssdbltrp is not implemented so SDT is never auto-cleared, or (c) the
  kernel returns via a path that does not go through M-mode MRET/SRET (e.g.,
  direct S-mode SRET), leaving SDT stuck at 1 and causing the next S-mode trap
  to be treated as an unexpected double trap.
Consequence: denial_of_service
Pattern:
  sstatus.*SDT|CSR.*sstatus.*SDT|__enable_double_trap|__disable_double_trap|sd
  t|SSTATUS_SDT
