PR #2503  target=freebsd-src  overall=compliant
Spec: FreeBSD kernel must never issue a bare CSR read to `seed` without a preceding write; the ISA-mandated write-before-read protocol triggers illegal-instruction trap regardless of SSEED/USEED, causing kernel panic
Violation: In the FreeBSD kernel, a direct CSR read of `seed` (csrr/csrrw reading without prior write) from S-mode raises an illegal-instruction exception regardless of mseccfg.SSEED. The Zkr extension mandates that `seed` is accessible only via a read-write CSR instruction pair (write to poll entropy, then read the result). If FreeBSD's entropy harvesting path (e.g., a naive randomdev or DTRACE probe) issues a bare csrr to seed CSR at address 0x015, the CPU traps. In RISC-V S-mode FreeBSD with medeleg delegating illegal-instruction exceptions to S-mode, this reaches the kernel trap handler as an unhandled illegal-instruction fault, causing a kernel panic.
Consequence: denial_of_service
Pattern: csrr[[:space:]]+.*0x015|CSR_SEED|asm.*"csrr.*seed|"csrrw.*seed.*zero

[compliant] sys/riscv/include/riscvreg.h:232-274  csr_read/csr_write macros

No caller in the FreeBSD RISC-V kernel passes the seed CSR address (0x015). Grep for '0x015' across sys/riscv/ returned zero results.
  | __asm __volatile("csrr %0, " #csr : "=r" (val));

[compliant] sys/riscv/riscv/exception.S:96-139  cpu_exception_handler
  Exception handler only accesses standard supervisor CSRs (sscratch, sepc, sstatus, stval, scause). No access to the seed CSR at 0x015. The trap path correctly handles illegal-instruction exceptions delegated from M-mode via medeleg, so a hypothetical userspace access to seed CSR would be caught as SIGILL rather than panicking the kernel.
  | csrr t0, sscratch
