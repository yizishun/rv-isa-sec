PR #2162  target=qemu  overall=bug_confirmed
Spec: QEMU applies ror32 before SubBytes (old spec order) and uses full AES round with ShiftRows, but the corrected SAIL spec does SubBytes first then rotate without ShiftRows — all rnum values produce diverging cipher output, corrupting guest key schedule generation
Violation: QEMU's aes64ks1i helper applies ror32 BEFORE SubBytes and uses the full AES round function (aesenc_SB_SR_AK with ShiftRows) when the corrected spec mandates SubBytes-first-then-rotate with no ShiftRows. For rnum == 0xA, QEMU skips rotation and uses XOR with zero-valued round key, but still applies ShiftRows, while the corrected spec requires only aes_subword_fwd with neither rotation nor rcon XOR. Additionally, trans_aes64ks1i rejects rnum > 0xA as illegal, but the spec now defines valid (zero-valued) rcon entries for 0xB-0xF, changing the illegal-instruction boundary.
Consequence: data_corruption
Pattern: ror32.*temp.*8.*aesenc_SB_SR_AK|aes64ks1i.*imm\s*>\s*0xA|round_consts\[enc_rnum\].*aes64ks1i
------------------------------------------------------------

  ShiftRows incorrectly applied: aesenc_SB_SR_AK (SubBytes+ShiftRows+AddRoundKey) is used at line 158, but the corrected spec requires only SubBytes (aes_subword_fwd) with no ShiftRows.
