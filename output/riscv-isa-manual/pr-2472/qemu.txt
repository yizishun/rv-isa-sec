PR #2472  target=qemu  overall=bug_confirmed
Spec: TOR PMP address computation in pmp_update_rule_addr() uses target_ulong arithmetic that truncates 34-bit physical addresses to 32 bits on RV32, causing TOR entries for high memory to silently match wrong address ranges or become no-ops
Violation: In QEMU RV32 TCG or KVM mode, when pmpaddr CSR values are used in TOR (Top of Range) matching via pmp_update_rule_addr(), the arithmetic `sa = prev_addr << 2` and `ea = (this_addr << 2) - 1u` is computed in target_ulong (uint32_t on RV32) before promotion to hwaddr (uint64_t). When physical address width exceeds 32 bits (e.g., RV32 with 34-bit PAs), a pmpaddr value exceeding 0x3FFFFFFF causes the left shift to overflow 32 bits silently. The resulting sa/ea wrap modulo 4 GiB, causing the PMP entry to match a completely wrong low-memory region or match nothing (when sa > ea), leaving the intended high-physical-memory range completely unprotected by PMP.
Consequence: privilege_escape
Pattern: target_ulong.*<<\s*2.*hwaddr|prev_addr\s*<<\s*2|this_addr\s*<<\s*2|PM_AMATCH_TOR.*<<
------------------------------------------------------------
[bug_confirmed] target/riscv/pmp.c:246-258  pmp_update_rule_addr
  TOR PMP address computation uses target_ulong (uint32_t on RV32) for prev_addr<<2 and this_addr<<2 before promotion to hwaddr (uint64_t). On RV32 with physical address width > 32 bits, any pmpaddr value >= 0x40000000 causes silent 32-bit wraparound, producing wrong sa/ea. The intended high-physical-memory region (above 4 GiB) is left completely unprotected — a privilege_escape vulnerability.
  | sa = prev_addr << 2; /* shift up from [xx:0] to [xx+2:2] */
  | ea = (this_addr << 2) - 1u;

[bug_confirmed] target/riscv/pmp.c:260-262  pmp_update_rule_addr
  NA4 PMP address computation has the same target_ulong overflow bug: `sa = this_addr << 2` wraps on RV32 when this_addr >= 0x40000000, producing a wrong start address for the naturally-aligned 4-byte region.
  | sa = this_addr << 2; /* shift up from [xx:0] to [xx+2:2] */
  | ea = (sa + 4u) - 1u;

[compliant] target/riscv/pmp.c:265-266  pmp_update_rule_addr
  NAPOT path correctly avoids the overflow: pmp_decode_napot(this_addr, ...) takes hwaddr as the first parameter, so this_addr is promoted to uint64_t via the function-call parameter passing before any shift occurs.
  | case PMP_AMATCH_NAPOT:
  |     pmp_decode_napot(this_addr, &sa, &ea);

[bug_confirmed] target/riscv/pmp.c:229-233  pmp_update_rule_addr
  Root cause: prev_addr and this_addr are declared as target_ulong (uint32_t on RV32) despite being used exclusively in arithmetic that produces hwaddr (uint64_t) values. The implicit C integer promotion rules do not widen the shift result because the operands determine the type of the intermediate result.
  | target_ulong this_addr = env->pmp_state.pmp[pmp_index].addr_reg;
  | target_ulong prev_addr = 0u;
  | hwaddr sa = 0u;
  | hwaddr ea = 0u;
