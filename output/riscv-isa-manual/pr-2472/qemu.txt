PR #2472  target=qemu  overall=bug_confirmed
Spec: RV32 TOR PMP << 2 overflow truncates physical addresses >= 4 GiB, aliasing PMP protections into low memory and defeating access control
Violation:
  On RV32 QEMU (TARGET_LONG_BITS=32), pmp_update_rule_addr() at pmp.c:256-257
  computes sa = prev_addr << 2 and ea = (this_addr << 2) - 1u, where
  prev_addr/this_addr are 32-bit target_ulong but sa/ea are 64-bit hwaddr. The
  << 2 is evaluated in 32-bit arithmetic before assignment. For pmpaddr values
  representing physical addresses above 4 GiB (pmpaddr >= 0x40000000, i.e.
  pa[33:32] != 00), the shift overflows 32 bits, truncating the high address
  bits. The PMP range aliases into low 4 GiB space or becomes empty (sa > ea),
  violating the spec requirement that TOR PMP correctly addresses up to
  2^XLEN+2.
Consequence: privilege_escape
Pattern:
  pmp_update_rule_addr.*<< 2|target_ulong.*<< 2.*hwaddr
------------------------------------------------------------

[potential_risk] target/riscv/pmp.c:624-657  pmpaddr_csr_write

  matching the 32-bit CSR register width. This is architecturally correct (the
  CSR is 32 bits wide on RV32) and the read-masking logic for OFF/TOR/NAPOT
  modes is correct. However, the write path at line 603 stores the raw
  target_ulong value without range validation. While the spec defines pmpaddr
  as WARL, QEMU does not enforce the WARL constraint that high bits beyond the
  physical address width should be read-only zero. This is not a security bug
  per se (the pmpaddr register is architecturally 32-bit), but means guest
  software could observe inconsistent behavior if it writes values with upper
  bits set and expects them to be masked.
