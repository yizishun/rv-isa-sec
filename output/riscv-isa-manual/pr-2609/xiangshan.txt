PR #2609  target=xiangshan  overall=potential_risk
Spec: pmpcfg truncated to 8-bit PMPConfig with no E field at MXLEN-1; mseccfg lacks MSSE bit; PMP checker silently interprets shadow-stack-encoded entries (E=1 XWR=010) as standard execute-only entries—enabling instruction fetch from regions that spec mandates as shadow-stack-only, a hardware privilege escalation path
Violation: XiangShan implements pmpcfg as an 8-bit PMPConfig (l, c, atomic, a[2], x, w, r) with no E field at bit MXLEN-1. The mseccfg CSR lacks the MSSE field entirely. When software writes mseccfg.MSSE=1 expecting M-mode shadow-stack enable, the write is silently dropped (field doesn't exist in the RTL CSR bundle at MachineLevel.scala:319-327). When software configures a PMP entry with pmpcfg[MXLEN-1]=1 (E=1) and XWR=010 (M-mode shadow stack) via either direct CSR write or the indirection miselect/mireg2 path, the hardware truncates pmpcfg to 8 bits—the E bit is discarded, and the entry is interpreted as a standard PMP entry with XWR=010 (execute-only), silently granting execute permission to a region that should be a shadow-stack-only memory zone. The mireg2-6 CSRs are ZeroFieldBundle stubs (CSRIND.scala:17-40) that always read zero, rendering the Smpmpind indirect PMP access path non-functional—reads return 0 instead of actual pmpcfg data, and writes are discarded.
Consequence: privilege_escape
Pattern: sextMask &= ~(~(0 until 8).map(BP => (0 until numCSRs).map(csr => csr.pmpcfg.cfg.bits.get(BP) != spec_E_field_BP)).foldLeft(true.B)(_ || _)); OR search for pmpcfg width < MXLEN, missing MSSE in mseccfg bundle, ZeroFieldBundle on mireg2/mireg3, PMPConfig bits restricted to 8

[potential_risk] src/main/scala/xiangshan/backend/fu/PMP.scala:41-61  class PMPConfig
  PMPConfig is an 8-bit bundle (l/c/atomic/a[2]/x/w/r) with no E field at any bit position. In the Sspmpss spec, PMP entries that encode shadow-stack memory regions require a distinguished encoding (E bit at MXLEN-1 per entry, or repurposed XWR=010 with E=1). Software writes to pmpcfg that set the E bit are truncated to 8 bits—the E bit is silently discarded—so a region intended as shadow-stack-only is interpreted as a standard PMP permission entry (bits 2:0 = XWR). For XWR=010 with E=1 (intended M-mode shadow-stack), the RTL interprets r=0, w=1, x=0 which it sanitizes to r=0, w=0 (W := W & R), yielding a no-permission region rather than a shadow-stack-protected region. This means shadow-stack memory is silently unprotected.

[potential_risk] src/main/scala/xiangshan/backend/fu/PMP.scala:403-412  trait PMPCheckMethod / pmp_check
  The pmp_check method performs a simple permission check: ld = isRead && !r, st = (isWrite||isAmo) && !w, instr = isExec && !x. There is no awareness of shadow-stack memory semantics—no check for 'this is a shadow-stack region, only shadow-stack instructions may access it, and only with dual read+write permission'. If the E field and XWR=010 encoding were added to PMPConfig but the checker was not updated, shadow-stack regions would be treated as 'write-only' (r=0, w=1, x=0), granting write but denying read/execute, which is the opposite of what shadow-stack semantics require (read+write for ss-push/pop, fault on normal loads/stores).
