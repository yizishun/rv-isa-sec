PR #2569  target=qemu  overall=bug_confirmed
Spec: QEMU LR/SC reservation tracking ignores device DMA writes — SC can succeed after an intervening device write to the reservation set, violating the normative sc_device_write_failure requirement that SC must fail if a non-hart device wrote the LR-accessed bytes between LR and SC
Violation: In QEMU TCG multi-hart (MTTCG) emulation, when a DMA-capable device (e.g., virtio-blk, NIC) performs a memory write through the IOMMU or directly to guest RAM that falls within a hart's LR reservation set, QEMU does not invalidate that hart's reservation. The subsequent SC can succeed despite the intervening device write, because gen_sc() relies solely on TCG's tcg_gen_atomic_cmpxchg_tl() for conflict detection — which only observes host-coherent store traffic from other vCPU threads, not emulated device DMA writes that go through QEMU's address_space_write / cpu_physical_memory_write path.
Consequence: data_corruption
Pattern: target/riscv/insn_trans/trans_rva.c.inc gen_sc using tcg_gen_atomic_cmpxchg_tl without device-write reservation invalidation hook; cpu_physical_memory_write and address_space_write not wired to clear load_res on any hart; absence of notifier on MemoryRegion write ops to invalidate per-hart reservations
------------------------------------------------------------
[bug_confirmed] target/riscv/insn_trans/trans_rva.c.inc:72-81  gen_sc
  gen_sc() checks reservation validity solely via a local comparison of 'load_res' against the SC address (line 72), then executes tcg_gen_atomic_cmpxchg_tl(). The address-match check succeeds because device DMA writes never clear load_res. The cmpxchg data-match catches simple overwrites (value changed → cmp fails), but is vulnerable to the ABA problem: if a DMA write changes the value from A→B and a second DMA write restores B→A between the LR and SC, the cmpxchg succeeds, violating the RISC-V spec requirement that 'a store by another hart or other device to any byte in the range of the reservation set must be observed and must cause the reservation to be invalidated.'

[bug_confirmed] system/physmem.c:3270-3278  flatview_write_continue_step
  The RAM fast-path of flatview_write_continue_step() services device DMA writes via direct memmove() + invalidate_and_set_dirty(), without any call to clear per-hart load_res reservations on any CPU. Neither cpu_physical_memory_write() nor address_space_write() provides a hook or notifier that allows the RISC-V backend to invalidate reservations when a device writes to guest RAM. Compare: there is no RISC-V equivalent of ARM's arm_clear_exclusive(), and even if there were, it is not called from this write path.
