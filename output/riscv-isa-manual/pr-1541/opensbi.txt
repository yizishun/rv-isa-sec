PR #1541  target=opensbi  overall=potential_risk
Spec: Memory-mapped MSIP writes are not guaranteed immediately visible in mip.MSIP; OpenSBI IPI send-and-check paths risk stale-read races without a fence or polling loop
Violation: OpenSBI writes a hart's memory-mapped MSIP register (e.g., via CLINT/ACLINT MMIO) to send an IPI, then immediately reads mip.MSIP via CSR instruction to confirm delivery — the read may return a stale value because the spec only guarantees eventual (not immediate) reflection from the MMIO register to mip.MSIP, causing the firmware to falsely conclude the IPI was not delivered and retry or take a wrong control-flow decision.
Consequence: race_condition
Pattern: MMIO write to CLINT/ACLINT MSIP offset (base+0x0000 or similar), immediately followed by csrr/csrsi/csrci on mip without an intervening fence.w.w.o (fence w,w) or delay/poll loop checking mip.MSIP

[potential_risk] lib/sbi/sbi_ipi.c:47-96  sbi_ipi_send
  sbi_ipi_send() uses __atomic_fetch_or with __ATOMIC_RELAXED on the remote hart's ipi_type scratch field to decide whether to call sbi_ipi_raw_send(). This is inter-hart shared-memory communication without release/acquire semantics. While not the specific MMIO→CSR race described in the spec, the relaxed atomic combined with the wmb() in sbi_ipi_raw_send() (fence ow,ow = I/O-only write ordering) does not form a full release-acquire pair. The wmb() only orders MMIO stores; it does NOT guarantee that the scratch ipi_type store is visible to the remote hart before the MSIP MMIO write arrives. If the remote hart's MSIP interrupt fires before the ipi_type scratch store is visible, sbi_ipi_process() would read ipi_type=0 and drop the IPI.
