PR #1541  target=qemu  overall=potential_risk
Spec: Memory-mapped MSIP is now defined as 32-bit register with bits 31:1 hardwired zero and eventual mip reflection; QEMU read path must not leak internal mip state through upper bits, and KVM must ensure eventual consistency
Violation: QEMU's ACLINT SWI read handler (riscv_aclint_swi_read) returns `(env->mip & MIP_MSIP) > 0` to emulate the memory-mapped MSIP register, deriving the value directly from the hart's internal mip CSR state. If the read path is refactored to expose more than bit 0 (e.g., returning raw `env->mip & MIP_MSIP` without boolean reduction, or returning the full 32-bit mip slice), bits 31:1 would expose internal interrupt-pending state rather than reading as hardwired zero. Additionally, the spec's relaxed timing guarantee ('eventually, but not necessarily immediately') means KVM-accelerated multi-hart setups where MSIP writes go through hardware CLINT while mip reads are trapped by QEMU could observe stale mip.MSIP indefinitely, violating the eventual-reflect guarantee.
Consequence: info_leak
Pattern: riscv_aclint_swi_read|env->mip.*MIP_MSIP|aclint-swi.*read|MSIP.*register.*read
------------------------------------------------------------

[potential_risk] hw/intc/riscv_aclint.c:1036-1039  riscv_cpu_set_irq (caller context)
  In KVM-accelerated setups, the ACLINT SWI write path raises MSIP via qemu_irq_raise, which calls riscv_cpu_set_irq -> kvm_riscv_set_irq(cpu, IRQ_M_SOFT, level). KVM injects the interrupt into hardware mip; QEMU's env->mip is NOT synchronously updated. When the ACLINT SWI read handler later reads env->mip (line 431), it may observe stale mip.MSIP state because the KVM path writes to hardware mip without mirroring back to env->mip. The ACLINT spec allows 'eventually, but not necessarily immediately' timing, so this is a spec-relaxed behavior rather than a hard bug, but it could cause guest-observable delays in observing MSIP writes.
  | if (kvm_enabled()) {
  |     kvm_riscv_set_irq(cpu, irq, level);
  | } else {
  |     riscv_cpu_update_mip(env, 1 << irq, BOOL_TO_MASK(level));
  | }

[compliant] hw/riscv/riscv-iommu.c:753-757  riscv_iommu_validate_device_ctx
  The PR change adds a validation check: when GATP is BARE (no second-level address translation), MSIPTP mode must be OFF. This prevents an IOMMU device context from being configured with MSI page-table-based translation when there is no G-stage translation to apply — avoiding undefined/misconfigured MSI routing. Note: 'MSIPTP' here is 'MSI Page Table Pointer' (IOMMU interrupt remapping), completely unrelated to ACLINT's memory-mapped MSIP (Machine Software Interrupt Pending) register. This is a correct security-hardening addition per the RISC-V IOMMU architecture spec.
