PR #2091  target=qemu  overall=bug_confirmed
Spec: Zalasr load-acquire decode patterns accept any rs2 value via @atom_st wildcard, but the spec encoding diagram requires rs2=0 — reserved encodings silently execute instead of trapping
Violation: When a guest executes a Zalasr load-acquire instruction (funct5=00110) with a non-zero rs2 field, QEMU's insn32.decode pattern '00110 . . ..... ..... <width> ..... 0101111 @atom_st' matches any rs2 value due to the wildcard '.....', and the gen_load_acquire trans function never validates that rs2==0. The spec encoding diagram explicitly constrains rs2 to 0 (attr: ['5', '0']). QEMU silently executes these reserved encodings as valid load-acquire instructions instead of raising an illegal instruction exception.
Consequence: function_loss
Pattern: Zalasr load-acquire decode @atom_st wildcard rs2 not validated against spec encoding constraint rs2=0
------------------------------------------------------------
[potential_risk] target/riscv/insn32.decode:76-76  (decode pattern)
  The @atom_st pattern uses '%rs2' (variable) with no constraint, while @atom_ld (line 75) correctly uses 'rs2=0'. Zalasr load-acquire instructions (funct5=00110) are defined via @atom_st, inheriting the unconstrained rs2 field. Per the Zalasr spec encoding diagram, load-acquire instructions must have rs2=0; non-zero rs2 values are reserved encodings that should raise illegal instruction exceptions.
  | @atom_st ..... aq:1 rl:1 ..... ........ ..... ....... &atomic %rs2      %rs1 %rd
  | (compare with:)
  | @atom_ld ..... aq:1 rl:1 ..... ........ ..... ....... &atomic rs2=0     %rs1 %rd

[bug_confirmed] target/riscv/insn32.decode:1079-1082  (decode entries)
  Zalasr load-acquire decode entries (lb_aqrl, lh_aqrl, lw_aqrl, ld_aqrl) use @atom_st which passes the rs2 field as a variable. The spec encoding diagram constrains rs2=0 (attr: ['5', '0']). The decode wildcard '.....' for rs2 matches any value, so reserved encodings with non-zero rs2 are silently decoded as valid load-acquire instructions instead of raising illegal instruction exceptions.
  | lb_aqrl  00110 . . ..... ..... 000 ..... 0101111 @atom_st
  | lh_aqrl  00110 . . ..... ..... 001 ..... 0101111 @atom_st
  | lw_aqrl  00110 . . ..... ..... 010 ..... 0101111 @atom_st
  | ld_aqrl  00110 . . ..... ..... 011 ..... 0101111 @atom_st

[bug_confirmed] target/riscv/insn_trans/trans_rvzalasr.c.inc:19-42  gen_load_acquire
  gen_load_acquire() never validates that a->rs2 == 0. It validates a->aq (mandatory acquire bit), but completely ignores the rs2 field. When the decoder passes a non-zero rs2 from a reserved encoding, the function silently executes the load-acquire as if it were a valid instruction. This is a violation condition: reserved encodings execute instead of trapping.
  | static bool gen_load_acquire(DisasContext *ctx, arg_lb_aqrl *a, MemOp memop)
  | {
  |     decode_save_opc(ctx, 0);
  |     TCGv addr = get_address(ctx, a->rs1, 0);
  |     TCGv dest = get_gpr(ctx, a->rd, EXT_NONE);
  |     /* ... no check for a->rs2 == 0 ... */

  Individual trans functions (trans_lb_aqrl, trans_lh_aqrl, trans_lw_aqrl, trans_ld_aqrl) do not validate rs2==0 before calling gen_load_acquire(). Each trans function only checks REQUIRE_ZALASR(ctx), then delegates to gen_load_acquire() which also lacks the rs2 check. Both layers fail to validate the spec-mandated encoding constraint.
