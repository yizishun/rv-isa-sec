PR #2977  target=linux  overall=compliant
Spec: Spec mandates menvcfg must exist when U-mode is implemented and menvcfgh must exist when S-mode+XLEN=32; kernel/firmware accessing these CSRs on a non-conformant hart triggers illegal-instruction trap and system crash.
Violation:
  Kernel M-mode firmware (e.g. OpenSBI) or KVM host accesses menvcfg or
  menvcfgh CSR on a non-conformant hart that supports U-mode but does not
  implement these registers, or on an RV32 hart with S-mode that omits
  menvcfgh. Access to a non-existent CSR raises an illegal-instruction
  exception in M-mode/HS-mode, crashing the firmware or hypervisor before the
  kernel can handle it.
Consequence: denial_of_service
Pattern:
  csr_read\s+menvcfg|csr_write\s+menvcfg|csr_read\s+menvcfgh|csr_write\s+menvc
  fgh; SBI_EXT_SRST or SBI_EXT_DBENC paths that indirectly read/write menvcfg
  fields (CBZE, CBCFE, CBIE, STCE, PBMTE) without checking CSR existence
------------------------------------------------------------

  Under CONFIG_RISCV_M_MODE, CSR_ENVCFG resolves to CSR_MENVCFG (0x30a). If
  the M-mode kernel runs on a hart that lacks U-mode, menvcfg does not exist
  per spec (norm:menvcfg_menvcfgh_no_U_mode), and any csr_read/csr_write via
  CSR_ENVCFG would raise an illegal-instruction exception. The XLINUXENVCFG
  guard is a synthetic extension inferred from extensions with envcfg bits
  (ZICBOZ, ZICBOM, etc.), but these extensions don't strictly require U-mode —
  a Zicboz implementation for M-mode-only is theoretically possible. No
