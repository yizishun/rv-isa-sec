PR #2539  target=freebsd-src  overall=compliant
Spec: hwpmc profiling data silently corrupted when ill-configured HPM counters return constant values instead of trapping, breaking performance monitoring integrity in FreeBSD's RISC-V port
Violation: FreeBSD kernel (e.g., hwpmc driver) reads an HPM counter (hpmcounterN) after configuring its event selector (mhpmeventN) to an unsupported or illegal event code, and relies on the read either trapping or returning a distinguishable error value, but the hardware instead silently returns a constant value (e.g., zero) indistinguishable from a valid zero count
Consequence: data_corruption
Pattern: mhpmevent[0-9]+.*write.*hpmcounter[0-9]+.*read|csr_write.*mhpmevent.*csr_read.*hpmcounter|hwpmc.*configure.*counter.*read|pmc.*setup.*hpm
------------------------------------------------------------
[compliant] sys/riscv/conf/NOTES:93-95  N/A (kernel config)
  hwpmc(4) is explicitly disabled for RISC-V via 'nodevice hwpmc' and 'nooptions HWPMC_HOOKS'. This prevents the kernel from ever entering the code paths that would write mhpmevent selectors and read hpmcounter values — the vulnerability pattern cannot manifest because the driver infrastructure does not exist.

  | nooptions 	HWPMC_HOOKS

[compliant] sys/riscv/vmm/vmm_riscv.c:634-635  vm_enter_guest (vmm_loop context)
  hcounteren is configured to expose only cycle and time (HCOUNTEREN_CY | HCOUNTEREN_TM) to the guest. hpmcounter3-31 are not exposed (hcounteren bits 3-31 remain zero), so a guest reading hpmcounter registers would trap with illegal-instruction. The mhpmevent registers are in M-mode address range (0x323-0x33F) and would also trap. The spec's vulnerability pattern (write mhpmevent, read hpmcounter, get silent zero) cannot occur within a bhyve guest either. The TODO comment acknowledges this area is under active consideration.
  | /* TODO: should we trap rdcycle / rdtime? */
  | csr_write(hcounteren, HCOUNTEREN_CY | HCOUNTEREN_TM);

[compliant] sys/riscv/riscv/trap.c:366-371  cpu_exception_handler
  Illegal instruction exceptions (including illegal CSR accesses to unimplemented HPM counters) trigger a kernel panic via 'panic('Unknown kernel exception %x ...')', not silent data corruption. Userspace illegal CSR accesses are signalled via SIGILL. There is no path where an unsupported mhpmevent write + hpmcounter read returns silently.
