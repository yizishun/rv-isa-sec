PR #2979  target=qemu  overall=potential_risk
Spec: QEMU narrow-check infrastructure assumes 2× widening; vfncvt.f.f.q requires 4× (FP32→OFP8), risking wrong EMUL register access and silent data corruption if impl falls through existing checks
Violation: QEMU implements vfncvt.f.f.q (FP32→OFP8 quad-width narrowing) reusing the existing opfv_narrow_check/vext_check_sd infrastructure, which validates only 2×LMUL source alignment (s->lmul+1) and 2×SEW source width (s->sew+1). The instruction requires 4×LMUL source alignment (s->lmul+2) and 4×SEW source width (s->sew+2), since it narrows FP32 (EMUL=4×LMUL, SEW=32) to OFP8 (EMUL=LMUL, SEW=8). Without a dedicated quad-narrow validation path, the TCG helper reads only half the intended source vector register group, operating on stale or unrelated register file data.
Consequence: data_corruption
Pattern: vfncvt.f.f.q|vfncvt.sat.f.f.q|quad.*narrow|emu[lL].*4|EMUL.*4|vnarrow.*quad|vext_check.*quad
------------------------------------------------------------
[potential_risk] target/riscv/insn_trans/trans_rvv.c.inc:526-535  vext_narrow_check_common
  This is the root validation function for all vector narrowing instructions. It validates source register alignment at s->lmul+1 (2xLMUL, line 532: require_align(vs2, s->lmul+1)) and constrains SEW to 2x width (line 531: s->sew+1 <= elen>>4). For vfncvt.f.f.q (FP32→OFP8, EMUL=4xLMUL source), this would need s->lmul+2 alignment and s->sew+2 width. No quad-narrow variant of this function exists anywhere. If vfncvt.f.f.q were added reusing this check, misaligned source register numbers (e.g., vs2=2 with LMUL=1) would incorrectly pass validation at 2x alignment but should fail at 4x alignment (requiring vs2%4==0). The TCG helper would then operate on only half the architectural source register group.
  | static bool vext_narrow_check_common(DisasContext *s, int vd, int vs2, int vm)

  |            (s->sew < MO_64) &&
  |            ((s->sew + 1) <= (s->cfg_ptr->elen >> 4)) &&
  |            require_align(vs2, s->lmul + 1) &&  /* 2xLMUL — needs lmul+2 for quad */

[compliant] target/riscv/vector_internals.h:114-121  vext_get_total_elems
  Correctly computes destination element count as (vlenb << emul) / esz where emul = ctz(esz) - ctz(sew) + lmul. For OFP8 dest (esz=1) with SEW=8 and LMUL from descriptor: emul = 0-3+lmul = lmul-3, correctly giving the destination group size. This function is used only for tail-agnostic destination masking in GEN_VEXT_V_ENV, not for source buffer validation. The source access in do_##NAME has no bounds checking. This function is compliant for its current purpose.
  | static inline uint32_t vext_get_total_elems(CPURISCVState *env, uint32_t desc,
  |                                             uint32_t esz)
  | {
  |     uint32_t sew = 1 << FIELD_EX64(env->vtype, VTYPE, VSEW);
  |     int8_t emul = ctz(esz) - ctz(sew)
  |                   + FIELD_EX64(desc, VDATA, LMUL);
  |     return (env->cfg.vlenb << MAX(emul, 0)) / esz;
  | }
