PR #2599  target=qemu  overall=compliant
Spec: QEMU must ensure ext_svnapot and PTE_N decode apply uniformly to both first_stage (VS-stage) and second_stage (G-stage/hgatp) page table walks; any first_stage gate on NAPOT handling would corrupt G-stage physical address computation and break hypervisor memory isolation
Violation: In QEMU's get_physical_address() PTW loop, if the Svnapot N-bit check (PTE_N at cpu_helper.c:1449) or the NAPOT decode logic (cpu_helper.c:1645) is inadvertently gated on first_stage==true, G-stage PTEs with the N bit set would either be incorrectly rejected as reserved (denial_of_service) or silently treated as non-NAPOT entries, computing wrong physical addresses. Additionally, if ext_svnapot==true but the G-stage hgatp-configured levels/vm differ from VS-stage satp, the leaf-PTE napot_bits validation (i != levels-1, napot_bits != 4) could trigger spurious TRANSLATE_FAIL on valid hypervisor G-stage NAPOT superpages, causing unexpected G-stage page faults injected into the guest.
Consequence: data_corruption
Pattern: search for any 'first_stage' boolean condition used as a guard around ext_svnapot, PTE_N, napot_bits, or napot_mask computation in target/riscv/cpu_helper.c get_physical_address(); also search for missing HENVCFG or hgatp-dependent gating that would prevent NAPOT decode in the two_stage && !first_stage G-stage walk path
