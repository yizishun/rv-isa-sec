PR #2659  target=linux  overall=not_implemented
Spec: Smrnmi CSRs and mnret are M-mode-only; kernel relies on firmware to correctly save/restore context in mnscratch and not corrupt mnepc across WARL remapping — any firmware bug silently corrupts kernel execution on mnret resume
Violation:
  In the Linux kernel (via SBI/SEE firmware), after mnstatus.NMIE is set to 1,
  the one-way enable latch prevents software from masking RNMIs; if the M-mode
  RNMI handler fails to properly save/restore all interrupted context through
  mnscratch, or if the mnepc WARL silently remaps a valid kernel resume PC
  into a different invalid address on a bogus handler write, the kernel
  resumes at an unintended instruction with corrupted register state.
Consequence: data_corruption
Pattern:
  mnstatus_nmie|mnepc.*write|mnscratch.*save|mnret.*return|RNMI.*handler.*cont
  ext
------------------------------------------------------------
[not_implemented] arch/riscv/:0-0  (none)
  The Smrnmi extension CSRs (mnepc, mncause, mnstatus, mnscratch) and the
  MNRET instruction are M-mode-only constructs. They are managed entirely by
  the M-mode firmware/SEE (e.g., OpenSBI). The Linux kernel runs in S-mode and
  has no code referencing any RNMI CSR, register, or handler logic. A
  comprehensive grep across arch/riscv/, include/, drivers/firmware/, and
  Documentation/ confirms zero matches for mnepc, mncause, mnstatus,
  mnscratch, MNRET, RNMI, NMIE, smrnmi, or resumable NMI. This is
  architecturally correct — S-mode software cannot access these M-mode CSRs
  and RNMI handling is the firmware's responsibility.
