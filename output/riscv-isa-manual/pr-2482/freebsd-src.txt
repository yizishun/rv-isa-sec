PR #2482  target=freebsd-src  overall=bug_confirmed
Spec: CBO instructions now explicitly require page-table/PMP permission checks: cbo.zero needs write (store fault), others need read (load fault); FreeBSD kernel S-mode usage is safe since it operates on owned kernel pages, but bhyve lacks any CBO emulation, and U-mode CBO is gated behind senvcfg bits that FreeBSD never sets — the gap is that if either is ever enabled without updating the fault-classification paths, wrong fault types would be delivered
Violation:
  bhyve VMM takes no action on VS-mode CBO instructions — it neither emulates
  the page-table permission check (cbo.zero → store page-fault,
  cbo.clean/flush/inval → load page-fault) nor injects a virtual illegal-
  instruction exception. A guest executing cbo.zero on a read-only page
  receives no store page-fault and may corrupt guest-physical memory.
  Additionally, if FreeBSD ever sets senvcfg.CBIE/CBCFE/CBZE to permit U-mode
  CBO without updating the trap handler to distinguish CBO-origin faults, a
  U-mode cbo.zero passing the fault check on a writable page but violating PMP
  write permission would be misclassified as a load access-fault instead of
  store access-fault.
Consequence: privilege_escape
Pattern:
  bhyve CBO instruction emulation gap: grepping for
  cbo\.(clean|flush|inval|zero) in vmm/ yields no results; henvcfg
  CBIE/CBCFE/CBZE bits are defined but never programmed

[potential_risk] sys/riscv/riscv/trap.c:255-262  page_fault_handler
  The page fault handler determines fault type solely from scause
  (STORE_PAGE_FAULT → VM_PROT_WRITE, LOAD_PAGE_FAULT → VM_PROT_READ). It never
  inspects stval to decode whether the faulting instruction was a CBO
  instruction. The hardware reports the correct scause for CBO faults
  (cbo.zero → STORE, cbo.clean/flush/inval → LOAD/STORE), so by coincidence
  this mapping is correct when CBO instructions are executed from S-mode.

  since senvcfg is never written), and a U-mode cbo.zero on a writable page
  faulted due to PMP write permissions, the handler would correctly report the
  fault via scause. The risk is forward-looking: if someone adds senvcfg
  configuration without adding CBO-aware checks, the existing handler has no
  defense-in-depth to catch misclassification.

[not_implemented] sys/riscv/riscv/machdep.c:557-678  initriscv

  kernel never configures senvcfg.CBZE/CBCFE/CBIE, so U-mode CBO instructions
