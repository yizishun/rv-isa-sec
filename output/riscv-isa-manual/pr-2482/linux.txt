PR #2482  target=linux  overall=potential_risk
Spec: CBO instructions are now unambiguously permission-checked: cbo.clean/flush/inval consume read permission, cbo.zero consumes write permission at both PTE and PMP levels, closing hardware-level privilege-escape vectors where implementations could silently allow cache-block operations across permission boundaries
Violation:
  In the Linux kernel, S/U-mode code (or M-mode with MPRV) executes a cache-
  block management instruction (cbo.clean, cbo.flush, cbo.inval) targeting a
  virtual address whose PTE has R=0 or whose PMP region has R=0, or executes
  cbo.zero targeting a virtual address whose PTE has W=0 or whose PMP region
  has W=0. The hardware now explicitly raises a load/store page-fault or
  access-fault where previously non-enforcement was implementation-defined,
  exposing kernel assumptions that CBO operations succeed without explicit
  permission checks.
Consequence: privilege_escape
Pattern:
  (CBO_ZERO|CBO_INVAL|CBO_CLEAN|CBO_FLUSH)\s*\(.*\) without prior PTE
  permission validation (pte_write|pte_read) on the target address; or
  userspace-accessible code path issuing CBO without PTE R/W checks

[compliant] arch/riscv/include/asm/errata_list.h:101-115  ALT_CMO_OP
  The ALT_CMO_OP macro emits CBO instructions via the RISC-V ALTERNATIVE
  framework, iterating over cache-block-aligned virtual addresses. It performs
  address alignment ((_start) & ~((_cachesize) - 1UL)) and loops by
  incrementing by _cachesize until reaching (_start + _size). No PTE
  permission validation is performed within the macro — the caller is
  responsible. This is correct architectural design: PTE enforcement is the
  hardware's responsibility; the macro is infrastructure, each call site is
  responsible for address validity.
  | #define ALT_CMO_OP(_op, _start, _size, _cachesize)

  | 	__nops(5),
  | 	"mv a0, %1\n\t"
  | 	"j 2f\n\t"
  | 	"3:\n\t"
