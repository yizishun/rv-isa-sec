PR #2729  target=xiangshan  overall=compliant
Spec: vmmacc.vv with vm=0 is explicitly reserved (must trap) while vwmmacc/vqwmmacc with vm=0 decodes to microscaling FP-accumulate forms; decoder failure to distinguish these creates type confusion between integer MAC datapath and E8M0 scale-reading microscaling datapath
Violation:
  In the XiangShan vector decode stage, when vmmacc.vv (funct6=0x38, OPIVV) is
  decoded with vm=0, the hardware fails to raise an illegal-instruction
  exception. The spec explicitly reserves vm=0 for vmmacc.vv (unlike
  vwmmacc.vv/vqwmmacc.vv where vm=0 selects the integer-input FP-accumulate
  microscaling form vfwimmacc.vv/vfqwimmacc.vv). If the decoder treats vm=0
  identically across all three integer MAC opcodes—or routes vm=0 vmmacc.vv to
  the microscaling datapath that reads v0 for paired E8M0 block-scale
  factors—the integer MAC execution unit would either (a) read v0 scale data
  instead of applying a vector mask, producing undefined computational
  results, or (b) misinterpret altfmt_A/altfmt_B as FP format selectors rather
  than signedness controls, causing type confusion between integer and FP
  datapaths.
Consequence: data_corruption
Pattern:
  OPIVV funct6 0x38 vm==0 trap check missing | vmmacc vm=0 not reserved | IME
  vm bit as sub-opcode mux error | integer MAC reads v0 as E8M0 scale
