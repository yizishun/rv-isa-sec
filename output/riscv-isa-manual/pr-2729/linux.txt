PR #2729  target=linux  overall=potential_risk
Spec: Zvvm adds 6 new bits to vtype CSR (lambda[2:0] at high bits, altfmt_A/B at bits 9-10, bs at bit 11) controlling matrix tile geometry and microscaling; kernel vtype save/restore paths must preserve these bits or userspace IME context is silently corrupted across context switches
Violation: Linux kernel saves/restores vtype CSR without preserving bits lambda[2:0] (vtype[XLEN-2:XLEN-4]), altfmt_A (vtype[9]), altfmt_B (vtype[10]), or bs (vtype[11]) across context switch, trap handling, or signal delivery, causing these Zvvm-defined fields to be clobbered to zero on any kernel entry/exit
Consequence: data_corruption
Pattern: __riscv_v_state_save|__riscv_v_state_restore|vtype_save|vtype_restore|VSETVL.*vtype|vtype_mask
------------------------------------------------------------
[potential_risk] arch/riscv/include/asm/vector.h:167-194  __vstate_csr_restore
  vtype CSR restoration uses 'vsetvl x0, %2, %1' (line 172) which per RISC-V spec only writes standard vtype fields (VSEW[5:3], VLMUL[2:0], VTA[6], VMA[7], VILL[XLEN-1]). Bits [8] through [XLEN-2], where Zvvm defines lambda[2:0] (vtype[XLEN-2:XLEN-4]), altfmt_A (vtype[9]), altfmt_B (vtype[10]), and bs (vtype[11]), are NOT written by vsetvl and get zeroed on any kernel entry/exit. No Zvvm hardware exists today so no actual data corruption occurs, but the save/restore infrastructure is architecturally incapable of preserving tile format state.
