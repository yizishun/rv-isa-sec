PR #2366  target=freebsd-src  overall=potential_risk
Spec: Spec clarification tightens STIP semantics to STCE-gated: kernel must re-validate STCE at runtime before trusting sip.STIP as read-only hardware timer indicator, else dynamic STCE clear causes silent timer-fabric corruption and stimecmp trap storms
Violation: FreeBSD kernel probes Sstc availability at boot (via ISA string or stimecmp CSR trial) and thereafter unconditionally reads sip.STIP as a hardware-reflected timer signal or writes stimecmp to set/clear timer interrupts, but menvcfg.STCE (or henvcfg.STCE under bhyve) is dynamically cleared by firmware, hypervisor, or misconfigured bhyve, causing sip.STIP to silently transition from read-only hardware reflection to execution-environment-software-injected behavior while stimecmp accesses become illegal-instruction traps — breaking the kernel's timer interrupt state machine mid-flight
Consequence: denial_of_service
Pattern: csrr.*sip.*STIP|CSR_READ.*sip.*STIP|csrw.*stimecmp|csrs.*sie.*STIE where Sstc capability is cached at boot without runtime menvcfg.STCE liveness re-validation
------------------------------------------------------------
[potential_risk] sys/riscv/riscv/identcpu.c:78-78  update_global_capabilities
  has_sstc is declared __read_frequently and set once at boot from the ISA string ('sstc' extension parse). No runtime liveness check of menvcfg.STCE exists anywhere in the kernel. If M-mode firmware dynamically clears menvcfg.STCE (e.g., due to an M-mode SW bug or a non-compliant firmware), the kernel continues to assume Sstc is available and will execute csr_write(stimecmp) instructions that become illegal-instruction traps. However, S-mode cannot read menvcfg (M-mode CSR), so the kernel has no architectural way to revalidate STCE at runtime — this is a fundamental architectural limitation, not a kernel bug.
  | bool __read_frequently has_sstc;
  | ...
  | UPDATE_CAP(has_sstc, (desc->smode_extensions & SV_SSTC) != 0);

[potential_risk] sys/riscv/riscv/timer.c:88-96  set_timecmp
  csr_write(stimecmp, timecmp) is gated solely by the boot-time-cached has_sstc flag. If menvcfg.STCE is subsequently cleared by M-mode firmware, this CSR write becomes an illegal instruction. The trap handler at trap.c:366-370 would panic the kernel ('Illegal instruction'), so the failure mode is a hard crash rather than silent timer-state-machine corruption. The backstop SBI path (sbi_set_timer) remains available but unreachable because has_sstc stays true.
  | if (has_sstc)
  |     csr_write(stimecmp, timecmp);
  | else
  |     sbi_set_timer(timecmp);

[potential_risk] sys/riscv/riscv/timer.c:140-155  riscv_timer_intr
  Similarly gated by has_sstc: the timer ISR writes csr_write(stimecmp, -1UL) to suppress the timer interrupt. Same vulnerability as set_timecmp — if menvcfg.STCE has been cleared, this traps/pancis. Importantly, FreeBSD does NOT read sip.STIP in the interrupt dispatch path; it relies on scause (hardware-reflected interrupt code 5), so the sip.STIP semantic-change half of the spec's vulnerability pattern does not apply.
  | if (has_sstc)
  |     csr_write(stimecmp, -1UL);
  | else
  |     sbi_set_timer(-1UL);

[bug_confirmed] sys/riscv/vmm/vmm_riscv.c:631-632  vmmops_run
  Blind write to henvcfg: 'csr_write(henvcfg, HENVCFG_STCE)' overwrites the entire henvcfg register with only the STCE bit set, silently clearing all other bits (PBMTE, CBZE, CBCFE, CBIE, FIOM). This breaks any concurrently configured henvcfg features. It also writes henvcfg.STCE unconditionally based on host has_sstc, without consulting the guest's view of whether Sstc should be exposed. The write should use csr_set(henvcfg, HENVCFG_STCE) or a read-modify-write to preserve other bits. Additionally, there is no check that the host menvcfg.STCE is also set — if the host M-mode cleared it, the hs-level henvcfg.STCE write may be ineffective or undefined.
  | if (has_sstc)
  |     csr_write(henvcfg, HENVCFG_STCE);

[compliant] sys/riscv/vmm/vmm_riscv.c:594-597  riscv_sync_interrupts

The guest never directly reads sip.STIP; instead bhyve injects VSTIP via hvip. This correctly virtualizes the Sstc extension for guests using the hypervisor-level CSR infrastructure.
