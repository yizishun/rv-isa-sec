PR #2364  target=qemu  overall=potential_risk
Spec: Zilsd (RV32) and RV64C share identical compressed opcode encodings for C.LD/C.SD/C.LDSP/C.SDSP but with divergent semantics (register-pair vs single xreg); QEMU TCG must dispatch based on XLEN+misa.Zilsd or silently corrupt guest register state
Violation: In QEMU TCG, when translating a 16-bit compressed load/store instruction (C.LD/C.SD/C.LDSP/C.SDSP), the translator selects the wrong expansion path based on XLEN or misa bits: on RV32 with Zilsd enabled, the instruction must load/store a 64-bit value to/from a register pair (rd', rd'+1) using two 32-bit memory accesses, but if QEMU instead expands it as an RV64C single 64-bit register load/store (or vice versa on RV64), the emulated register state silently diverges from architectural expectations
Consequence: data_corruption
Pattern: transc_c_ld|trans_c_sd|c_ldsp|c_sdsp|Zilsd.*trans|decode_compressed.*Zilsd
------------------------------------------------------------
[potential_risk] target/riscv/insn16.decode:130-141  decode_insn16 (generated) — Quadrant 0 Zclsd patterns
  Decode pattern interleaving between standard C instructions and Zclsd: on RV32 with Zclsd + F enabled (without RVC), the c_flw entry in the { } multi-pattern block matches the C.LD opcode (011 in Q0) before zclsd_ld is reached. trans_c_flw succeeds via REQUIRE_ZCF_OR_FC when F is present, causing the translator to execute a 32-bit FP load with wrong immediate decoding (uimm_cl_w instead of uimm_cl_d) instead of the Zclsd 64-bit register-pair load. The validation at tcg-cpu.c:850-861 only blocks RVC+RVF and explicit Zcf, not the Zca+RVF combination where Zca is implied by Zclsd.

  |   ld              011  ... ... .. ... 00 @cl_d
  |   c_flw           011  ... ... .. ... 00 @cl_w
  |   # *** Zclsd Extension ***
  |   zclsd_ld        011  ... ... .. ... 00 @cl_d
  | }

[potential_risk] target/riscv/tcg/tcg-cpu.c:850-861  riscv_cpu_validate_set_extensions
  Validation gap: Zclsd+RVC+F and Zclsd+Zcf are correctly blocked, but Zclsd+Zca+F (where Zca is implied by Zclsd) is not explicitly forbidden. Zclsd auto-enables Zca (line 1135), and F can be independently enabled. In this configuration, c_flw/c_fsw become valid 16-bit instructions that share opcodes with Zclsd's C.LD/C.SD — and since they appear before zclsd_* in the decode blocks, they win the pattern match, silently producing wrong instruction semantics.
