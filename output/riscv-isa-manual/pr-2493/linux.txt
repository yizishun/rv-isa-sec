PR #2493  target=linux  overall=potential_risk
Spec: Kernel code running in M-mode must verify pmpcfg writes after MML lockdown, as hardware silently ignores attempts to add executable M-mode rules without RLB, and S-mode kernels cannot verify RLB status since mseccfg is inaccessible from S-mode
Violation: In M-mode Linux (CONFIG_RISCV_M_MODE) or KVM host code, after mseccfg.MML is set to 1 without mseccfg.RLB=1, any CSR write to pmpcfg that attempts to create an executable M-mode-only rule (pmpcfg.L=1, pmpcfg.X=1) or executable locked Shared-Region rule (pmpcfg.RW=01, pmpcfg.L=1) is silently ignored by hardware. If kernel code does not read back pmpcfg to verify the write took effect, it proceeds under the false assumption that the executable region is enforced, leaving M-mode execution unprotected or incorrectly restricted.
Consequence: privilege_escape
Pattern: csr_write.*CSR_PMPCFG|write_pmpcfg|__asm__.*csrw.*pmpcfg
------------------------------------------------------------
[potential_risk] arch/riscv/kernel/head.S:239-240  _start_kernel
  Single PMPCFG write in M-mode boot path writes an unlocked L=0 RWX=111 NAPOT rule via csrw CSR_PMPCFG0. The rule written (L=0) does NOT match the spec's silent-ignore patterns (L=1+X=1 or L=1+RW=01), so the specific Smepmp MML=1 silent-discard bug is not triggered. However, the kernel has zero Smepmp awareness: no mseccfg.MML checks, no pmpcfg read-back verification, and no detection of pre-existing MML=1 state set by firmware. If firmware enables MML=1 before handoff, kernel PMP assumptions are silently violated with no diagnostic. Additionally, PMP is not re-initialized on CPU hotplug.
