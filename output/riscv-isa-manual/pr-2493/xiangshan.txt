PR #2493  target=xiangshan  overall=bug_confirmed
Spec: mseccfg.MMWP and mseccfg.MML are sticky bits that must remain set once written to 1, only clearable by PMP reset; hardware that allows software CSR writes to clear these bits after they are set enables M-mode to silently escape Smepmp lockdown, reverting to permissive M-mode memory access
Violation:
  In XiangShan RTL, the PMP CSR write logic in the mseccfg CSR module does not
  enforce the sticky-bit behavior of mseccfg.MMWP and mseccfg.MML.
  Specifically, after either bit transitions from 0→1, a subsequent CSR write
  (CSRRW/CSRRS/CSRRC) targeting mseccfg that attempts to clear these bits
  succeeds—the hardware writes the new value without blocking the 1→0
  transition. The PMP reset signal (which should be the only mechanism to
  clear these bits) is not gating the write-enable of these sticky fields.
  This violates the spec requirement that MMWP and MML 'cannot be unset until
  a PMP reset.'
Consequence: privilege_escape
Pattern:
  mseccfg.*MMWP.*write|mseccfg.*MML.*write|sticky.*bit.*not.*enforced|CSRRW.*m
  seccfg.*no.*sticky.*check|mseccfg_reg.*:=.*Cat|when.*mseccfg.*MML.*0.*:=|mse
  ccfg.*wen.*!.*pmp_reset

  MML (bit 0), MMWP (bit 1), and RLB (bit 2) are declared as RO(0) — the
  ROType class uses wfn=wNoEffect, meaning every CSR write to these bits is
  silently discarded. Software can NEVER set MML=1 or MMWP=1. The spec
  (machine.adoc §norm:mseccfg_mml_sticky, §norm:mseccfg_mmwp_op_warl) requires
  these to be WARL sticky bits: writes of 1 must take effect, writes of 0 must
  be ignored (blocking the 1→0 transition) until a PMP reset. The hardware is
  not just lacking sticky semantics — it refuses ALL writes, making Smepmp
  entirely non-functional.
