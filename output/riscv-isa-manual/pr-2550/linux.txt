PR #2550  target=linux  overall=compliant
Spec: Unconditional mseccfg access traps on harts lacking all mseccfg-field-defining extensions; the kernel must guard CSR access with extension probing (e.g., riscv_isa_extension_available for Smepmp/Smmpm) or risk an unhandled illegal instruction in context-switch, KVM, or save/restore paths.
Violation: Kernel code reads or writes CSR mseccfg/mseccfgh without first confirming that at least one extension defining mseccfg fields (Smepmp, Smmpm, Smctr, etc.) is implemented on the hart; on harts where no such extension is present, mseccfg is a reserved CSR number and access raises an illegal instruction exception.
Consequence: denial_of_service
Pattern: csr_read\s*\(\s*CSR_MSCONF|csr_write\s*\(\s*CSR_MSCONF|mseccfg|MSECCFG
------------------------------------------------------------
[compliant] arch/riscv/include/asm/csr.h:429-430  (none — header macro definition)
  CSR_MSECCFG and CSR_MSECCFGH are defined as CSR numbers 0x747/0x757 but are never referenced by any kernel C or assembly code. No csr_read/csr_write/csr_set/csr_clear or inline asm accesses these CSRs anywhere in the tree. Since the kernel never touches mseccfg, it cannot trigger an illegal-instruction exception on harts where no mseccfg-defining extension is present.
  | #define CSR_MSECCFG		0x747
  | #define CSR_MSECCFGH		0x757

[compliant] arch/riscv/include/asm/csr.h:245-249  (none — header macro definition)
  MSECCFG_PMM and MSECCFG_PMM_PMLEN_* bit macros are defined as aliases for ENVCFG_PMM bits. These are never used by any kernel code either. The aliasing to ENVCFG bits (rather than independent definitions) is unusual but harmless since no code references them.
  | #define MSECCFG_PMM			ENVCFG_PMM
  | #define MSECCFG_PMM_PMLEN_0		ENVCFG_PMM_PMLEN_0
  | #define MSECCFG_PMM_PMLEN_7		ENVCFG_PMM_PMLEN_7
  | #define MSECCFG_PMM_PMLEN_16		ENVCFG_PMM_PMLEN_16
