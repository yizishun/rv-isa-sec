PR #2572  target=qemu  overall=bug_confirmed
Spec: Whole-register vector instructions lack illegal-instruction trap on vstart>=evl (now spec-reserved), silently violating guest security assumptions and containing uint32_t wraparound in ldst_whole page-splitting arithmetic
Violation: When a whole-register vector instruction (vl1re*, vl2re*, vl4re*, vl8re*, vs1r, vs2r, vs4r, vs8r, vmv1r, vmv2r, vmv4r, vmv8r) executes with vstart >= evl (where evl = NFIELDS*VLENB>>log2_esz for ld/st or EMUL*VLENB>>sew for vmv), QEMU silently returns without raising an illegal-instruction exception. Additionally, in vext_ldst_whole(), when vstart > evl the computation 'elems = evl - env->vstart' wraps uint32_t, producing an enormous element count that probes/accesses memory at unintended guest-physical addresses.
Consequence: function_loss
Pattern: ldst_whole_trans\(\)|vext_ldst_whole\(\)|HELPER\(vmvr_v\)|GEN_VMV_WHOLE_TRANS|GEN_LDST_WHOLE_TRANS
------------------------------------------------------------
[bug_confirmed] target/riscv/vector_helper.c:834-882  vext_ldst_whole
  No validation that vstart < evl before executing whole-register load/store. When vstart >= evl, the computation 'elems = evl - env->vstart' (line 854) underflows uint32_t, producing an enormous element count (~4 billion). This wrapped elems is passed to vext_page_ldst_us(), which calls probe_pages() with the corrupted size, probing unintended guest-physical addresses. Per RISC-V spec, whole-register instructions with vstart values >= evl (=NFIELDS*VLENB>>log2_esz) are reserved and should raise an illegal-instruction exception. The missing check allows a malicious guest to probe arbitrary pages via crafted vstart values.
  | uint32_t evl = nf * max_elems;
  | ...
  | if (unlikely(env->vstart + elems >= evl)) {
  |     elems = evl - env->vstart;  /* uint32_t wrap when vstart > evl */
  | }
  | ...
  | vext_page_ldst_us(env, vd, addr, elems, 1, max_elems, log2_esz, ...);

[bug_confirmed] target/riscv/vector_helper.c:5756-5782  HELPER(vmvr_v)
  When startb >= maxsz (i.e., vstart >= EMUL*VLENB>>sew), the function silently sets vstart=0 and returns without raising an illegal-instruction exception. Per RISC-V spec, whole-register move instructions with vstart >= EMUL*VLEN/SEW are reserved and should trap. The silent return allows guest execution to continue after an illegal vstart value, which can be exploited to skip expected exception handling in security-sensitive supervisor code.
  | uint32_t startb = env->vstart * sewb;
  | ...
  | if (startb >= maxsz) {
  |     env->vstart = 0;
  |     return;   /* illegal-instruction exception NOT raised */
  | }

[potential_risk] target/riscv/insn_trans/trans_rvv.c.inc:1181-1237  ldst_whole_trans
  The translator dispatches to the inline TCG fast path when s->vstart_eq_zero at translation time. If vstart is later modified (e.g., by CSR write or trap return) between TB generation and execution, the instruction executes via the inline path with a non-zero vstart, bypassing the helper entirely. The inline path uses atomic pairs (MO_ATOM_IFALIGN_PAIR) and increments vstart from zero, which could corrupt vector register state and produce incorrect memory access patterns when vstart is actually non-zero at execution.
  | bool use_helper_fn = !s->vstart_eq_zero;
  | if (!use_helper_fn) {
  |     /* inline TCG: assumes vstart==0, uses MO_ATOM_IFALIGN_PAIR */
  |     for (int i = 0; i < size; i += 8) { ... }
  | }

[compliant] target/riscv/csr.c:1001-1013  write_vstart
  vstart CSR write correctly masks the value to lg2(VLEN*8) bits, preventing writes of vstart values beyond the maximum element index. Migration state includes vstart (machine.c:148). However, the CSR write does not validate whether the new vstart value is legal for the current instruction context (e.g., vstart >= evl for whole-register instructions), which is expected since validation occurs at instruction execution time, not at CSR write time.
