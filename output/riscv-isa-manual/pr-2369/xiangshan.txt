PR #2369  target=xiangshan  overall=not_implemented
Spec: Missing vd/vs2 register overlap trap on vghsh.vs/vgmul.vs allows scalar subkey corruption during GHASH, breaking GCM authentication and enabling forged ciphertext acceptance
Violation:
  In XiangShan RTL, when the vector execution unit processes vghsh.vs or
  vgmul.vs instructions, if the hardware does not check and trap on the
  condition where the vd register group overlaps the vs2 scalar element group
  (spec norm:vghsh-vs_vdovlpvs2_rsv and norm:vgmul-vs_vdovlpvs2_rsv), the
  scalar subkey H held in vs2 can be overwritten by partial result writes to
  vd before all element group iterations consume H. This creates a write-
  after-read hazard where later element groups use a corrupted hash subkey,
  producing incorrect GCM/GMAC authentication tags. The overlap check must
  consider VLEN-dependent EMUL: for VLEN >= 128, vs2 is a single register; for
  VLEN < 128, vs2 is a register group spanning ceil(128/VLEN) registers. The
  decoder or issue logic must raise an illegal-instruction exception when
  overlap is detected, per the spec's 'reserved encoding' classification.
Consequence: privilege_escape
Pattern:
  vd.*vs2.*overlap|vdovlp|register.*overlap.*check|illegal.*instruction.*vghsh
  .*vs|illegal.*instruction.*vgmul.*vs|scalar.*element.*group.*overlap|vs2.*vd
  .*hazard

  vghsh.vs and vgmul.vs are NOT implemented in XiangShan RTL. The instructions
  file defines only Zvbb bit-patterns (VANDN_VV through VWSLL_VX). No Zvkg or
  Zvkgs BitPat objects exist. The only vector crypto extension implemented is
  Zvbb. vghsh.vv and vgmul.vv are also not implemented. Furthermore, the
  RISC-V specification (zvk.adoc lines 2631-2636, 2752-2757) explicitly states
  that .vs forms of vghsh and vgmul are NOT part of the current specification
  — they are listed as hypothetical 'future extension' possibilities in non-
  normative NOTE blocks. The generic .vs overlap constraint table (zvk.adoc
  lines 331-346) enumerates the instructions subject to vd/vs2 overlap checks
  and neither vghsh nor vgmul appear in that table. The normative rule tags
  cited in the security spec (norm:vghsh-vs_vdovlpvs2_rsv, norm:vgmul-
  vs_vdovlpvs2_rsv) do not exist in the current specification.

[potential_risk] src/main/scala/xiangshan/backend/decode/VecExceptionGen.scala:276-277  VecExceptionGen
  The notAllowOverlapInst exclusion list in VecExceptionGen does not include
  vghsh or vgmul. If these instructions were added in the future (either .vv
  or hypothetical .vs forms), the existing overlap-checking infrastructure
  would silently permit vd/vs2 overlap because vs2Constraint1 (EEW equality
  for non-mask instructions) would evaluate to true for these EEW=32
  instructions, and the absence from notAllowOverlapInst means vs2AllowOverlap
  would be true. This is a defense-in-depth gap: the overlap detection logic
  has no forward-compatible safeguard for Zvkgs instructions that inherently
  require non-overlapping vd and vs2.
