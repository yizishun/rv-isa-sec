PR #2369  target=qemu  overall=not_implemented
Spec: Zvkgs adds .vs variants of vghsh/vgmul where vs2 is a scalar element group broadcast to all vd element groups; QEMU must enforce the vd/vs2 non-overlap constraint or the scalar key is corrupted during in-place updates
Violation:
  QEMU executes vghsh.vs or vgmul.vs without checking that the vd register
  group overlaps the vs2 scalar element group. In the .vs form, vs2 holds a
  single 128-bit scalar element group (the hash subkey H or multiplicand)
  broadcast across all element groups of vd. If vd overlaps vs2, the in-place
  read-modify-write of vd corrupts the scalar key material before it is
  applied to all element groups, producing incorrect GHASH results.
Consequence: data_corruption
Pattern:
  trans_vghsh_vs|trans_vgmul_vs|gen_vghsh|gen_vgmul|vext_vv_rmw|vcrypto_vs_ove
  rlap|require_noover_vd_vs2

  which adds vgmul.vs (the .vs scalar element group form), is not implemented.
  No vgmul.vs encoding exists in insn32.decode, no trans_vgmul_vs function
  exists, no ext_zvkgs config flag exists, and no HELPER(vgmul_vs) exists. The
  vgmul.vv form reads vs2 per-element-group (vs2[i*2+0], vs2[i*2+1]) and does
  not require the .vs-specific vd-vs2 overlap check. The spec itself notes at
  zvk.adoc:2752-2757 that .vs variants are described as a 'future extension'.
  Since the .vs instructions do not exist in QEMU, the vulnerability described
  in the security spec (vd overlapping vs2 scalar element group in .vs form)
  cannot occur.

[not_implemented] target/riscv/vcrypto_helper.c:795-833  HELPER(vghsh_vv)
  This helper implements the .vv form correctly: it reads vs2 per-element-
  group at line 808 (vs2[i*2+0], vs2[i*2+1]), so each 128-bit element group
  gets its own copy of the hash subkey H. The .vs form (Zvkgs) would require a
  different helper that reads vs2 only once at indices [0] and [1] and
  broadcasts that single scalar element group across all vd element groups. No
  such HELPER(vghsh_vs) exists. The existing HELPER(vghsh_vv) correctly
  implements the Zvkg .vv specification (zvk.adoc:2638-2675).
