PR #2597  target=linux  overall=bug_confirmed
Spec: Kernel must gate Zicfiss enablement on Zaamo presence; shadow stack memory updates that are non-atomic on Zaamo-less hardware can race, silently corrupting return addresses and defeating the CFI protection that Zicfiss is meant to provide.
Violation: Linux kernel enables Zicfiss shadow stack for a task (via hwprobe, prctl, or ELF aux vector) on hardware that advertises Zicfiss but lacks Zaamo atomic operations, or KVM exposes Zicfiss to a guest without also exposing Zaamo, causing shadow stack push/pop operations to use non-atomic memory accesses that race with concurrent stores on the same cache line.
Consequence: race_condition
Pattern: Zicfiss without Zaamo in ISA string / hwprobe / DT / ACPI detection logic, or SSP/SSPUSH/SSPOPCHK context-switch paths that assume atomic shadow stack updates but are compiled for a kernel running on Zicfiss-without-Zaamo hardware
------------------------------------------------------------
[bug_confirmed] arch/riscv/kernel/cpufeature.c:310-318  riscv_cfiss_validate
  Zicfiss validate callback ignores the isa_bitmap parameter—it does not check for RISCV_ISA_EXT_ZAAMO. On hardware that advertises Zicfiss in the ISA string but lacks Zaamo (and lacks 'A' which implies Zaamo), the kernel will still enumerate Zicfiss as present, enabling shadow stacks whose ssamoswap.d instructions will issue non-atomic memory accesses. This creates a race condition where a concurrent store on the same cache line can corrupt the shadow-stack token.
  | static int riscv_cfiss_validate(const struct riscv_isa_ext_data *data,
  |                 const unsigned long *isa_bitmap)
  | {
  |     if (!IS_ENABLED(CONFIG_RISCV_USER_CFI) ||
  |         (riscv_nousercfi & CMDLINE_DISABLE_RISCV_USERCFI_BCFI))
  |         return -EINVAL;
  |     return 0;
  | }
