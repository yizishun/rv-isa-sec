PR #2561  target=linux  overall=compliant
Spec: mseccfg changed from optional (trap on access) to conditionally-existent with reserved fallback (read-zero/write-ignored); kernel must check extension presence (misa/DT) before interpreting mseccfg fields, because reserved reads returning 0 are indistinguishable from 'all security features off'
Violation:
  In the Linux kernel, when code reads or writes CSR_MSECCFG (0x747) /
  CSR_MSECCFGH (0x757) on hardware where no mseccfg-field-adding extension
  (Smmpm, Smepmp, Zkr, etc.) is implemented, the access silently succeeds
  (reads return 0, writes are ignored) under the new 'reserved' semantics,
  whereas the old 'optional' semantics would have caused an illegal-
  instruction trap. Kernel code that probes mseccfg via csr_read and branches
  on the absence of a trap to infer that PMM/MML/MMWP fields are operational
  will falsely conclude these security features exist.
Consequence: function_loss
Pattern:
  csr_read\(CSR_MSECCFG\)|csr_write\(CSR_MSECCFG|CSR_MSECCFG|CSR_MSECCFGH
