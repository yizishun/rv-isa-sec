PR #2561  target=xiangshan  overall=compliant
Spec: mseccfg existence is now conditional on implemented extensions: if no extension adds a field to mseccfg, the CSR is reserved and access must trap; incorrect decode gating causes either spurious CSR accessibility (privilege_escape) or blocked security configuration
Violation:
  In XiangShan RTL, if the mseccfg CSR is implemented as a permanently-
  accessible read/write register (even returning zero) regardless of whether
  any extension adding mseccfg fields is implemented. Per the updated spec,
  mseccfg is 'reserved' when no extension that adds a field to it is
  implemented — meaning CSR access instructions (CSRRW/CSRRS/CSRRC) targeting
  mseccfg must raise an illegal instruction exception in this case. A hardware
  implementation that always decodes mseccfg as a valid CSR address
  (0x747/0x757) without gating on the presence of at least one mseccfg-using
  extension (e.g., Smepmp, Smmtt, Sspmp) violates this spec. Conversely, if an
  extension such as Smepmp IS implemented but the RTL fails to make mseccfg
  accessible (e.g., the CSR decode masks it as unimplemented), required
  security configuration fields become unreachable.
Consequence: privilege_escape
Pattern:
  mseccfg CSR address decode without extension-presence gating; CSR(0x747) or
  CSR(0x757) read/write path in Chisel CSRModule without conditional on
  implementedExtensions; mseccfg registered as always-accessible in CSR map;
  illegal instruction exception logic does not include mseccfg=reserved case
