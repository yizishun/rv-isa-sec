PR #2731  target=xiangshan  overall=not_implemented
Spec: lambda[2:0]=0b000 is architecturally invalid/dynamic and must raise Illegal_Instruction; silent acceptance causes tile geometry parameters (K_eff, MUL_C) to be undefined, leading to register file index miscalculation and data corruption across arbitrary vector registers
Violation:
  In XiangShan RTL, when vtype.lambda[2:0] = 0b000 (invalid/dynamic encoding),
  if the hardware does not raise an illegal-instruction exception on any Zvvm
  matrix multiply-accumulate or tile load/store instruction that reads
  vtype.lambda, the decode_gemm_geometry SAIL function returns
  Illegal_Instruction for this encoding, but a hardware implementation that
  silently interprets 0b000 as any valid lambda value (e.g., λ=1) would
  execute with incorrect tile geometry: K_eff, MUL_C, M_tile, N_tile, and
  register group boundaries are all derived from lambda. This causes the
  matrix operation to read from and write to wrong vector register indices,
  spanning register groups incorrectly, leading to arbitrary register file
  data corruption across architectural vector registers. Similarly, if
  lambda[2:0] decodes to λ=0 (division by zero in MUL_C = VLEN/(SEW×λ²) or
  M_tile = VLEN/(SEW×λ)), the hardware could enter undefined index
  calculations producing out-of-bounds register file accesses, potentially
  leaking data from or corrupting registers outside the architecturally
  specified operand groups.
Consequence: data_corruption
Pattern:
  vtype.*lambda|decode_vlambda|lambda.*0b000|Illegal_Instruction.*lambda|MUL_C
  .*VLEN.*lambda|gemm_geom.*lambda|WARL.*lambda
