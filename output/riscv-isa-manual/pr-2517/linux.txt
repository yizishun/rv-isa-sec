PR #2517  target=linux  overall=compliant
Spec: mstatus.TW does not gate U-mode WFI trapping: kernel must always deliver SIGILL to user-space on WFI regardless of TW, or KVM must always inject illegal-instruction into guest VU-mode.
Violation:
  Kernel trap handler for illegal-instruction exceptions in U-mode checks
  mstatus.TW before deciding whether a U-mode WFI trap is legitimate. With the
  clarified spec, TW is irrelevant for U-mode WFI: the trap always fires. Code
  that treats U-mode WFI differently based on TW=0 (e.g., resuming execution
  as if WFI were a no-op, because TW=0 previously suggested S-mode could
  'permit' U-mode WFI) would incorrectly suppress a mandatory signal (SIGILL)
  to the offending user process, or in KVM, incorrectly forward WFI to a guest
  VU-mode vCPU instead of injecting an illegal-instruction exception into the
  guest.
Consequence: privilege_escape
Pattern:
  mstatus.*TW.*WFI|WFI.*TW.*U-
  mode|TW=0.*illegal_instruction.*WFI|WFI.*seccomp|WFI.*SIGILL

  kvm_halt. It does not inspect hstatus.VTW or mstatus.TW—the decision to
  reach this emulation path is made by hardware, which traps VU-mode WFI as
  virtual-instruction exception (§norm:H_virtinst_vu_wfi_tw0) and VS-mode WFI

[compliant] arch/riscv/include/asm/csr.h:1-200  
  The RISC-V CSR header defines HSTATUS_VTW for KVM's VTW control but does NOT
  define SR_TW for mstatus.TW. This absence is itself evidence that the kernel
  does not and should not be inspecting mstatus.TW in software—the TW/WFI trap
  decision is a hardware mechanism. The kernel does not need a software TW
  constant because it never performs a TW-based decision on U-mode illegal
  instruction traps.
