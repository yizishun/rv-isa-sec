PR #2568  target=qemu  overall=compliant
Spec: QEMU terminates VM on critical-error via cpu_abort() but spec now leaves counter/timer updates UNSPECIFIED during this state; a future per-hart halt implementation that keeps counters running would leak critical-error timing information through shared timer/perf-counter CSRs accessible to other harts
Violation:
  QEMU models critical-error state via cpu_abort() at
  target/riscv/cpu_helper.c:2478, terminating the entire VM. Multi-hart
  systems lose all harts (not just the faulting one), and before termination,
  QEMU's timer device (CLINT/ACLINT mtime) and PMU counters may have already
  advanced beyond the point where the critical-error was detected, since the
  abort is reached only after counter read paths in the trap delivery sequence
  have executed. If QEMU later replaces cpu_abort() with a per-hart halt while
  leaving the timer device running, performance counters and timers would
  continue updating during the critical-error halt—a behavior the spec now
  explicitly labels UNSPECIFIED, creating a side channel where observing hart
  B's time/counter CSRs reveals that hart A entered critical-error and how
  long it has been halted.
Consequence: info_leak
Pattern:
  cpu_abort.*double.trap|critical.error.*mtime|scountinhibit.*NMIE|mcountinhib
  it.*halt
