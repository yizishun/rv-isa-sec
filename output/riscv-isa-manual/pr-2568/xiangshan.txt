PR #2568  target=xiangshan  overall=potential_risk
Spec: Performance counters and timer (mtime) may continue updating after critical-error entry because their freeze logic is not gated by the critical-error signal, creating a timing side channel observable post-reset and violating the architectural expectation that no architectural state changes in critical-error state
Violation:
  In XiangShan RTL, when the hart enters critical-error state (unexpected trap
  with !Smrnmi or mnstatus.NMIE==0), the CSR module asserts critical-error and
  ceases execution, but performance counters (mcycle/minstret/mhpmevent*) and
  the mtime timer in the CLINT/ACLINT module do NOT receive the critical-error
  stall signal. Specifically, mcycle and minstret in the CSR file may continue
  incrementing because their clock-gating condition only checks for CSR-
  counter-enable writes and COUNTINHIBIT bits, not the critical-error signal.
  The mtime register in the platform timer module is independently clocked and
  has no critical-error input at all, so it unconditionally continues
  counting. This means the counter/timer freeze behavior is inconsistent: some
  counters may stop due to pipeline stall propagation while others continue,
  and this inconsistency is determined by the microarchitectural signal
  routing topology rather than any architectural intent.
Consequence: function_loss
Pattern:
  critical_error.*counter|counter.*critical_error|mcycle.*inhibit.*critical|mi
  nstret.*critical|mtime.*critical_error|COUNTINHIBIT.*critical|csr_write.*MIP
  .*STIP.*critical|timer.*update.*critical_error
