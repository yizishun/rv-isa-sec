PR #2755  target=freebsd-src  overall=bug_confirmed
Spec: Spec now clarifies STCE=1 is required for STIP to reflect stimecmp; FreeBSD kernel has no menvcfg visibility and silently loses all timer interrupts if M-mode firmware omits STCE delegation
Violation: FreeBSD S-mode kernel runs on hardware with Sstc extension but M-mode firmware left menvcfg.STCE=0; the kernel's stimecmp writes (timer.c:93, vmm_riscv.c:632 relying on HENVCFG_STCE) never produce timer interrupts because STCE gates the comparator-to-STIP signal path, while the kernel unconditionally assumes stimecmp works when has_sstc is true and has no mechanism to detect missing M-mode STCE delegation
Consequence: denial_of_service
Pattern: has_sstc\b.*\bcsr_write\s*\(\s*stimecmp
------------------------------------------------------------
[bug_confirmed] sys/riscv/riscv/timer.c:88-96  set_timecmp
  Direct stimecmp CSR write gated solely by has_sstc (ISA-string flag) with no check of menvcfg.STCE delegation. If M-mode firmware leaves menvcfg.STCE=0, the stimecmp write is a silent no-op: the comparator-to-STIP signal path remains gated and timer interrupts never fire, causing system-wide denial of service (scheduler ticks, callouts, and all timer-dependent subsystems halt). No fallback to sbi_set_timer() is possible because the kernel has no mechanism to detect this condition.
  | if (has_sstc)
  | 		csr_write(stimecmp, timecmp);
  | 	else
  | 		sbi_set_timer(timecmp);

[bug_confirmed] sys/riscv/riscv/timer.c:139-155  riscv_timer_intr
  ISR writes stimecmp = -1UL when has_sstc is true, same menvcfg.STCE blind spot as set_timecmp. Under missing STCE delegation, this write fails to clear the timer condition properly, and the ISR itself would never have been entered (since the initial stimecmp write in set_timecmp produced no interrupt).
  | if (has_sstc)
  | 		csr_write(stimecmp, -1UL);
  | 	else
  | 		sbi_set_timer(-1UL);

[potential_risk] sys/riscv/riscv/identcpu.c:464-468  update_cpu_caps
  has_sstc is set from smode_extensions (ISA string 'sstc' substring) without any M-mode STCE delegation probe. This flag gates all stimecmp and henvcfg.STCE code paths, but ISA-string Sstc presence is necessary but not sufficient — menvcfg.STCE must also be set by M-mode firmware. The kernel never validates this precondition.
  | UPDATE_CAP(has_sstc, (desc->smode_extensions & SV_SSTC) != 0);

[potential_risk] sys/riscv/vmm/vmm_riscv.c:631-632  vmmops_vcpu_run
  Writes HENVCFG_STCE to henvcfg for guest VS-mode when has_sstc is true. This is the hypervisor-level STCE for the guest, distinct from menvcfg.STCE for the host. However, the host kernel's own stimecmp path has the same missing-STCE-delegation vulnerability, and vmmops_getcap (line 932) advertises VM_CAP_SSTC to bhyve userspace based on has_sstc without verifying the full STCE enablement chain.
  | if (has_sstc)
  | 		csr_write(henvcfg, HENVCFG_STCE);

[potential_risk] sys/riscv/vmm/vmm_riscv.c:931-934  vmmops_getcap
  Advertises VM_CAP_SSTC to bhyve userspace based solely on has_sstc. If menvcfg.STCE=0, the host kernel's own timer interrupts are already broken, and advertising Sstc capability to userspace is misleading.
  | case VM_CAP_SSTC:
  | 		*retval = has_sstc;
  | 		ret = 0;
