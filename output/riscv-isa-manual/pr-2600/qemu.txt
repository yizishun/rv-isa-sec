PR #2600  target=qemu  overall=potential_risk
Spec: mseccfg.MML sticky-bit not enforced on CSR write, allowing guest to bypass Smepmp M-mode lockdown and escalate to M-mode access on S/U-mode-only PMP regions
Violation: In QEMU TCG, when a guest CSR write to mseccfg attempts to clear the MML bit while MML=1 and the Smepmp extension is implemented, if the WARL sticky-bit logic permits the write to succeed (clearing MML to 0) without a full PMP reset, the emulation violates the normative rule that MML is a sticky bit that 'once set cannot be unset until a PMP reset'.
Consequence: privilege_escape
Pattern: write_mseccfg.*mml|mseccfg.*MML.*sticky|pmp_reset.*mml|warl.*mml|mseccfg_write.*clear|s->mseccfg.*&=.*~MSEECFG_MML

  Sticky-bit logic for MML and MMWP is correctly implemented. Line 688 'val |= (env->mseccfg & mask)' ORs the current MML/MMWP bits back into val, so any write attempting to clear MML from 1→0 has MML forced back to 1. [potential_risk] target/riscv/pmp.c:677-683  mseccfg_csr_write
  RLB write-enable check only considers entries with explicit PMP_LOCK bit (via pmp_is_locked()). Under MML=1, PMP entries configured as Shared-Region (encodings 12-14) are implicitly locked per the Smepmp spec even without the LOCK bit. The spec requires RLB to be unwritable when ANY entry is locked (explicitly or implicitly). This allows RLB to be incorrectly set to 1 when MML=1 and implicitly-locked Shared-Region entries exist, potentially weakening PMP enforcement by making locked entries writable.

  |             }
  |         }
  |     }
