PR #2400  target=linux  overall=compliant
Spec: Changing menvcfg.ADUE or henvcfg.ADUE without subsequent TLB invalidation leaves stale TLB entries with the old A/D-bit-update policy (hardware vs. software), causing the kernel to either miss required page faults for accessed/dirty tracking or receive unexpected faults, leading to silent loss of PTE A/D state, broken page aging, and potential memory corruption
Violation: In the Linux kernel, any code path that writes a new value to menvcfg.ADUE or henvcfg.ADUE without immediately executing the required TLB fence (SFENCE.VMA with rs1=x0, rs2=x0 for menvcfg; HFENCE.VVMA with rs1=x0, rs2=x0 or HFENCE.GVMA with rs1=x0, rs2=x0 for henvcfg, depending on scope) violates this spec. The most dangerous instance is KVM guest world-switch code that changes henvcfg.ADUE between guests with different Svadu/Svade configurations but omits the HFENCE.VVMA before writing the new vsatp.
Consequence: data_corruption
Pattern: (csr_write|__riscv_xchg_csr)\(CSR_MENVCFG|write_henvcfg|kvm_riscv_vcpu_.*switch|__cpu_setup.*menvcfg
