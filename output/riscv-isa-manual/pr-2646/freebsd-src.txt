PR #2646  target=freebsd-src  overall=compliant
Spec: FreeBSD kernel must guard every ssp CSR access with an explicit menvcfg.SSE liveness check; the menvcfg→henvcfg→senvcfg read-only-zero cascade means M-mode firmware can silently disable shadow stacks, turning ssp accesses into illegal-instruction exceptions that crash context-switch and signal-delivery paths
Violation: In the FreeBSD kernel running in S-mode on Zicfiss hardware, code in cpu_switch (sys/riscv/riscv/swtch.S), sendsig/sigreturn (sys/riscv/riscv/exec_machdep.c), or set_mcontext/get_mcontext paths accesses the ssp CSR without first reading menvcfg to test the SSE bit. When M-mode firmware (e.g., OpenSBI) boots with menvcfg.SSE=0—globally disabling shadow stacks—the ssp access raises an illegal-instruction exception (#norm:zicfiss_m_menvcfg-sse). These kernel paths do not expect CSR-access exceptions; the unhandled trap either panics the host or silently skips save/restore, leaking or zeroing per-thread shadow stack state. In bhyve, a host that sets henvcfg.SSE=0 after this PR forces guest senvcfg.SSE to read-only zero; the simplified VU-mode check now depends solely on senvcfg.SSE (#norm:zicfiss_vu_senvcfg-sse), so guest VU-mode ssp accesses raise a virtual-instruction exception that bhyve's vmmops_exception stub (returning ENOSYS) cannot handle, corrupting guest userspace shadow stacks. Additionally, because ssp CSR access is no longer contingent on S-mode being implemented, a FreeBSD kernel that gates ssp usage on S-mode presence rather than on menvcfg.SSE will incorrectly assume availability.
Consequence: data_corruption
Pattern: csr_read|csr_write|csr_swap inline asm referencing "ssp" in sys/riscv/riscv/swtch.S (cpu_switch), sys/riscv/riscv/exec_machdep.c (set_mcontext, get_mcontext, sendsig, sigreturn), sys/riscv/vmm/vmm_riscv.c (vmmops_vcpu_save_csrs, vmmops_vcpu_restore_csrs) without a logically-preceding CSR read of menvcfg to test SSE bit, and without a trap wrapper guarding the ssp access
