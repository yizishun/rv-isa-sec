PR #2494  target=freebsd-src  overall=potential_risk
Spec: bhyve must fence GVMA on henvcfg.PMM transitions when PMLEN < GPA width, and must mirror senvcfg.PMM→hstatus.HUPMM before HLV/HSV in U-mode, else guest memory accesses resolve to wrong physical pages causing cross-VM info leak
Violation: In FreeBSD's bhype hypervisor, when henvcfg.PMM is changed from/to a value where (XLEN-PMLEN) < GPA width (PMLEN=7 with hgatp.MODE=sv57x4, or PMLEN=16 with hgatp.MODE=sv48x4/sv57x4) without subsequently executing HFENCE.GVMA(x0), stale TLB entries may map masked GPAs to wrong supervisor physical addresses. Additionally, if bhyve invokes HLV.*/HSV.* in U-mode without first copying the guest's senvcfg.PMM to hstatus.HUPMM, pointer masking will be applied at the wrong privilege level, causing loads/stores to target incorrect guest physical addresses.
Consequence: info_leak
Pattern: henvcfg.*PMM|hstatus.*HUPMM|HFENCE\.GVMA|HLV\.|HSV\.|vsatp.*BARE|hgatp|pointer_mask

[potential_risk] sys/riscv/include/riscvreg.h:125-134  
  No HSTATUS_HUPMM bit is defined. The RISC-V privileged spec requires hstatus.HUPMM to be set from the guest's senvcfg.PMM when a hypervisor executes HLV.*/HSV.* instructions in U-mode, so pointer masking is applied at the correct privilege level. Currently FreeBSD bhyve executes HLV.* (hlvx.hu at vmm_riscv.c:296) from HS-mode, not U-mode, so this is not immediately exploitable. However, the missing definition means any U-mode HLV usage would apply pointer masking with the wrong privilege context.
