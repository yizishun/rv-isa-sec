PR #2494  target=linux  overall=bug_confirmed
Spec: KVM must issue HFENCE.GVMA(rs1=x0) on henvcfg.PMM changes when hgatp uses x4 modes and vsatp.MODE=Bare, else GPA masking causes TLB-alias data corruption across guest pages
Violation: In the KVM hypervisor (arch/riscv/kvm), when henvcfg.PMM is changed for a guest with hgatp.MODE in {sv48x4, sv57x4} and vsatp.MODE=Bare, without a subsequent HFENCE.GVMA with rs1=x0, stale TLB entries may alias guest-physical addresses differing only in the top 2 masked bits to the same supervisor-physical page.
Consequence: data_corruption
Pattern: henvcfg.*PMM|hgatp.*MODE.*sv57x4|hgatp.*MODE.*sv48x4|vsatp.*MODE.*Bare|HFENCE\.GVMA|kvm_arch_vcpu_load|kvm_arch_vcpu_put|kvm_riscv_vcpu_switch

  When guest changes henvcfg.PMM via SBI FWFT SET (non-one_reg_access path), csr_write(CSR_HENVCFG, ...) directly modifies hardware without a subsequent HFENCE.GVMA. If vsatp.MODE=Bare and hgatp.MODE is sv48x4 or sv57x4, stale G-stage TLB entries may alias guest-physical addresses differing only in the top masked bits to the same supervisor-physical page, causing data corruption. The RISC-V privileged spec requires TLB invalidation after changing translation-relevant CSRs.

[potential_risk] arch/riscv/kvm/vcpu_sbi_fwft.c:132-136  try_to_set_pmm
  During initialization, try_to_set_pmm() directly sets and clears PMM on the hardware CSR to probe PMLEN support. The csr_read_clear restores PMM to 0 after the probe, but no HFENCE.GVMA is issued between the set and clear, nor after the final clear. If the host CPU has residual G-stage TLB state from a previous guest, the transient PMM enable/disable could briefly create the aliasing condition. However, this runs during VCPU init before the guest actually executes, so the practical risk is low.
  | csr_set(CSR_HENVCFG, value);
  | return (csr_read_clear(CSR_HENVCFG, ENVCFG_PMM) & ENVCFG_PMM) == value;
