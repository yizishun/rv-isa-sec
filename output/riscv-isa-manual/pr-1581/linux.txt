PR #1581  target=linux  overall=potential_risk
Spec: CSRRS/CSRRC read-modify-write can corrupt underlying state of 'reads-as' bits (e.g., pmpaddr grain bits) when kernel modifies unrelated bits in the same CSR — KVM emulation and csr_read_set/clear macros are the primary exposure surface
Violation: In the Linux kernel, KVM emulation of CSRRS/CSRRC (vcpu_insn.c:162-168) or any kernel code using csr_read_set/csr_read_clear macros (csr.h:575-598) on a CSR containing bits whose architectural read value differs from the underlying stored value (e.g., pmpaddr[n][G-1] reads as 0 but stores 1 due to grain matching): the read-modify-write cycle reads the 'read-as' value, applies rs1's set/clear mask, then writes back — silently overwriting the underlying value of the 'reads-as' bits even though rs1 did not target them.
Consequence: data_corruption
Pattern: csr_read_set|csr_read_clear on CSRs with WRITE-synthesized or grain-masked bits that differ from underlying storage; KVM CSRRS/CSRRC emulation doing read-then-write on CSRs with 'reads as' semantics
------------------------------------------------------------

The CSRRS decode sets new_val=-1UL (line 164) and CSRRC sets new_val=0 (line 168). For CSRs not in the in-kernel csr_funcs[] table (which includes pmpaddr, pmpcfg, and most non-AIA/non-PMU CSRs), the kernel exits to user-space with KVM_EXIT_RISCV_CSR, delegating the actual read-modify-write to the VMM. If the VMM (e.g., QEMU) reads the 'read-as' architectural value and performs the RMW on that, the underlying storage bits will be silently corrupted. The in-kernel AIA handlers (aia_rmw_iprio, imsic_rmw) are safe because they operate on kernel-maintained swfile state, not actual hardware CSRs. The PMU handler rejects writes (wr_mask != 0 → illegal trap). No in-kernel safeguard exists to prevent or warn about CSRRS/CSRRC on CSRs known to have divergent read-vs-stored semantics.

[potential_risk] arch/riscv/include/asm/csr.h:575-599  
  csr_read_set/csr_read_clear macros expand to CSRRS/CSRRC hardware instructions, which perform an atomic read-modify-write cycle. When used on a CSR with 'reads as' semantics (e.g., pmpaddr[n][G-1] where grain-masked bits read as 0 but underlying storage is 1), the hardware reads the architectural 'read-as' value (0), applies the set/clear mask, and writes back — overwriting the underlying stored value of the 'reads-as' bits to 0 even when rs1 did not target those bits. For CSRRS with bit_i=0 in rs1: CSR[bit_i] = read_as(0) | 0 = 0, corrupting the underlying 1. All five current call sites (irqflags.h:33 STATUS.SR_IE, process.c:402 ENVCFG.PMM, vcpu_sbi_fwft.c:135 HENVCFG.PMM, vector.h:154,184 STATUS.SR_FS_DIRTY) are safe because STATUS/ENVCFG/HENVCFG do not have 'reads as' semantics. However, the macros carry no documentation warning and no compile-time or runtime guard against misuse on CSRs with 'reads as' bits, making them a latent footgun for future kernel code.
  | #define csr_read_set(csr, val) ({ \
  |     unsigned long __v = (unsigned long)(val); \
  |     __asm__ __volatile__ ("csrrs %0, " __ASM_STR(csr) ", %1" \
  |         : "=r" (__v) : "rK" (__v) : "memory"); \
  |     __v; })
