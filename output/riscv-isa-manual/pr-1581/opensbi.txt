PR #1581  target=opensbi  overall=compliant
Spec: CSRRS/CSRRC read-modify-write on pmpaddr CSRs silently corrupts NAPOT 'reads as' bits (e.g., G-1) because the read phase returns the architectural read value (0) rather than the underlying hardware value (1), breaking PMP memory isolation enforced by OpenSBI
Violation:
  OpenSBI (M-mode) or S-mode code uses CSRRS/CSRRC (or CSRRSI/CSRRCI) read-
  modify-write instructions on pmpaddr CSRs to modify a subset of bits while
  the CSR is configured in NAPOT mode. During the read phase, the G-1 bit (and
  possibly other 'reads as' bits) returns 0 instead of its underlying value of
  1, and the write-back phase then overwrites those bits with 0, silently
  corrupting the NAPOT address encoding.
Consequence: data_corruption
Pattern:
  csr_read_set | csr_read_clear | CSRRS | CSRRC on CSR_PMPADDR with non-x0 rd
  and non-x0 rs1 while pmpaddr holds NAPOT encoding — any read-modify-write to
  a subfield of pmpaddr destroys the trailing-ones NAPOT pattern when 'reads
  as' bits differ from underlying bits

[compliant] lib/sbi/riscv_asm.c:383-434  pmp_get
  pmp_get() is read-only: it reads both pmpcfg and pmpaddr with csr_read_num()
  (plain csrr) and does not write back. The NAPOT decoding (ctz(~addr))
  correctly handles the 'reads as ones' behavior because when the CSR is read,
  the hardware returns the 'reads as ones' bits as 1s, which is the correct
  NAPOT encoding for decoding.
  | addr = csr_read_num(pmpaddr_csr);
  | t1   = ctz(~addr);
  | addr = (addr & ~((1UL << t1) - 1)) << PMP_SHIFT;
