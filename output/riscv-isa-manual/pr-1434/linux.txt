PR #1434  target=linux  overall=bug_confirmed
Spec: PMP faults from misaligned/wide stores or decomposed CMOs may leave partially-visible writes in protected regions; kernel must not assume PMP faults are atomic with zero side effects
Violation:
  Kernel code writes to memory via misaligned stores or stores wider than XLEN
  (e.g., FSD on RV32D) that straddle a PMP boundary, or issues CBO
  instructions crossing PMP region boundaries, and assumes that a PMP access-
  fault exception means no bytes were modified in the protected region.
Consequence: data_corruption
Pattern:
  misaligned.*store.*pmp|pmp.*partial.*write|FSD.*RV32.*pmp|cbo\.zero.*pmp.*bo
  undary|store.*wider.*XLEN.*pmp|assume.*pmp.*fault.*atomic

[bug_confirmed] arch/riscv/kernel/traps_misaligned.c:333-425  handle_scalar_misaligned_store
  On RV32, when emulating an FSD (8-byte FP store) instruction that triggered
  a misaligned trap, the handler calls copy_to_user() at line 416 to write all
  8 bytes in a single call. Since XLEN=32, copy_to_user() decomposes this into
  two 32-bit word writes. If the misaligned address straddles a page or PMP
  boundary such that the second 32-bit write faults, the first 32-bit write
  has already been committed to memory. The handler returns -1 on any
  copy_to_user() failure, and the caller (do_trap_misaligned at
  traps.c:230-232) signals SIGBUS — without any mechanism to detect or undo
  the partial write. This means bytes are written into the protected/faulting
  region despite the exception. This is the exact vulnerability pattern
  described by the RISC-V spec at machine.adoc:3571-3574.

[potential_risk] arch/riscv/kernel/traps_misaligned.c:310-319  handle_scalar_misaligned_load
  On RV32 with FLD (8-byte FP load, len=8), copy_from_user() reads 8 bytes
  decomposed into two 32-bit reads. If the second read faults, copy_from_user
  returns an error, and the handler returns -1. While a load doesn't corrupt
  protected memory (it only reads), the partial read may have observable side-
  effects: the first 4 bytes are consumed but the instruction is retried or
  the process is killed. More critically, if the watched memory has MMIO side-
  effects on read (e.g., a FIFO), the partial read consumes data that is lost
  when the instruction fails. This is lower severity because it does not write
  into a protected region, but it is the same pattern.

[potential_risk] arch/riscv/lib/clear_page.S:20-73  clear_page
  clear_page() uses CBO.ZERO instructions operating on cache-block-sized
  regions (typically 64 bytes). Per the RISC-V CMO spec (cmo.adoc:327-328), if
  a CBO instruction's cache block spans two PMP regions with different
  permissions, the behavior is UNSPECIFIED. The kernel does not check whether
  the target page straddles a PMP boundary before issuing CBO.ZERO. In the
  kernel's own PMP configuration (head.S:237-240), PMP0 grants universal R/W/X
  access, so this is not triggerable by the kernel's PMP setup alone. However,
  with firmware-managed PMP where M-mode restricts kernel S-mode access to
  certain physical regions, a page allocation that spans a PMP boundary could
  cause UNSPECIFIED behavior — potentially zeroing memory in a protected
  region.

[compliant] arch/riscv/kernel/head.S:229-242  _start_kernel
  The kernel boot sequence in M-mode configures PMP0 as NAPOT covering the
  full address space with R/W/X permissions, then never reconfigures PMP at
  runtime. This L=0 entry grants M-mode universal access and S/U-mode
  universal access. This is the correct behavior for a kernel that delegates
  PMP management to M-mode firmware (e.g., OpenSBI). The kernel does not
  attempt runtime PMP manipulation, which avoids introducing PMP-related bugs
  in kernel context-switch or hotplug paths.
  | la a0, .Lpmp_done
  | csrw CSR_TVEC, a0
  | li a0, -1
  | csrw CSR_PMPADDR0, a0
  | li a0, (PMP_A_NAPOT | PMP_R | PMP_W | PMP_X)
  | csrw CSR_PMPCFG0, a0
