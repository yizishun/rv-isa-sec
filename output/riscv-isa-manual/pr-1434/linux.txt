PR #1434  target=linux  overall=compliant
Spec: PMP explicitly decomposes wide/misaligned stores into per-memory-operation checks — partial writes become visible across PMP boundaries before the fault, violating any kernel invariant that treats PMP store-checks as all-or-nothing
Violation: Kernel code in M-mode (or S/U-mode via PMP) executes a misaligned store, an XLEN-wider store (e.g., FSD on RV32D), or a Zicboz CBO.ZERO whose decomposed memory-operations span a PMP region boundary — one memory operation writes into a PMP-allowed region and becomes architecturally visible, while another memory operation in a disallowed region triggers an access-fault. The kernel cannot assume the store is atomic with respect to PMP checking; partial writes commit in allowed regions before the fault fires
Consequence: data_corruption
Pattern: store instruction (SD/FSD/CBO.ZERO or memcpy/copy_to_user/__put_user) whose byte range [addr, addr+len) crosses a PMP region boundary defined by pmpaddr[] registers; search M-mode trap handlers, context-switch save/restore, KVM vCPU world-switch paths, and any code writing near PMP-configured guard pages

[potential_risk] arch/riscv/kernel/traps_misaligned.c:446-452  handle_misaligned_store
  Misaligned store emulation by the kernel decomposes a single architectural store into multiple byte/word writes via the scalar misaligned handler. If the original misaligned store spans a PMP region boundary (configured by M-mode firmware), the kernel's software emulation could cause partial writes: some bytes land in an allowed PMP region while others trigger a fault. The kernel has no visibility into M-mode PMP configuration and cannot detect or prevent this. However, this risk is fundamentally M-mode firmware's concern -- the kernel correctly emulates the misaligned access at the virtual address level and relies on M-mode to enforce PMP at the physical level.
  | int handle_misaligned_store(struct pt_regs *regs)
  | {
  |     if (IS_ENABLED(CONFIG_RISCV_SCALAR_MISALIGNED))
  |         return handle_scalar_misaligned_store(regs);
  |     return -1;
  | }

[potential_risk] arch/riscv/lib/clear_page.S:20-73  clear_page
  CBO.ZERO on a page whose underlying physical memory spans a PMP region boundary: each CBO.ZERO instruction is decomposed by hardware into per-byte (or per-sub-block) memory operations. If the cache block straddles a PMP boundary (e.g., a 64-byte CBO block where bytes [0,32) are allowed but bytes [32,64) are disallowed), the allowed portion becomes architecturally visible while the disallowed portion triggers an access-fault. In practice, clear_page operates on kernel buddy-allocated pages that are page-aligned, and PMP regions are unlikely to be configured at sub-page granularity within kernel heap. The risk is theoretical unless M-mode firmware configures PMP guard pages within kernel-allocated pages.
