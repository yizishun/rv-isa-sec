PR #1434  target=opensbi  overall=potential_risk
Spec: Decomposed memory operations (misaligned stores, wide stores, CMOs) are independently PMP-checked per operation, not per instruction — OpenSBI's PMP configuration must ensure region boundaries are aligned to the largest possible memory operation size, or a single instruction can partially bypass write protections via successful sub-operations
Violation:
  OpenSBI configures adjacent PMP regions with differing R/W/X permissions
  where the boundary between them is not aligned to the maximum memory
  operation size (cache block size for CMOs, or XLEN for wide stores like FSD
  on RV32). A misaligned store, wide store, or decomposed CMO (e.g., cbo.zero)
  that spans the boundary will have each constituent memory operation
  independently PMP-checked, allowing a partial write to succeed in a region
  that OpenSBI intended to be write-protected, even as the other half faults.
Consequence: privilege_escape
Pattern:
  PMP region boundary that separates different R/W/X permissions but is not
  aligned to max(cache_block_size, XLEN_bytes); adjacent PMP entries with
  differing R/W/X bits where pmpaddr boundary could be crossed by a single
  decomposed memory operation; CBO handler or PMP setup code that assumes the
  access-fault is all-or-nothing per instruction rather than per memory
  operation; missing SFENCE.VMA after PMP reconfiguration that could leave
  stale PMP cache entries across decomposed operations

[compliant] lib/sbi/riscv_asm.c:333-381  pmp_set
  CSR write ordering is correct: pmpaddr CSR is written first (line 377), then
  pmpcfg CSR (line 378). The pmpcfg write is the committing write that enables
  the PMP entry (sets A field to NAPOT/NA4). Before the pmpcfg write, the old
  pmpcfg value either has A=OFF (entry disabled, no match) or the previous
  configuration. Writing pmpaddr first then pmpcfg ensures the entry
  atomically becomes valid with the correct address range and permissions at
  the point of the final CSR write. The reverse ordering (pmpcfg first) would
  be dangerous because the new permissions would briefly apply to the old
  address range. This is the recommended approach.
  | /* write csrs */
  | csr_write_num(pmpaddr_csr, pmpaddr);
  | csr_write_num(pmpcfg_csr, pmpcfg);
  | 
  | return 0;
