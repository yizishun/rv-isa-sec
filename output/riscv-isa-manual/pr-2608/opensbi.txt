PR #2608  target=opensbi  overall=compliant
Spec: OpenSBI's HSM resume path fails to restore mstateen0-3 after non-retentive suspend, causing S-mode to lose access to all state controlled by these CSRs (sstateen, hstateen, IMSIC, AIA, context/environment config CSRs), violating the expectation that M-mode firmware transparently preserves hart state across suspend/resume cycles.
Violation: In OpenSBI's HSM non-retentive suspend/resume flow (lib/sbi/sbi_hsm.c), the per-hart struct sbi_hsm_data saves MIE, MIP, MEDELEG, MIDELEG, and MENVCFG but does NOT save or restore mstateen0-3. Per the spec (norm:mstateen_zero_initialization), hardware resets all writable mstateen bits to zero on reset. After a deep suspend where the hart loses CSR state, mstateen0-3 come back as all-zero, losing bit 63 (STATEN) which controls access to sstateen/hstateen CSRs, and all other extension-enable bits (CONTEXT, IMSIC, AIA, ENVCFG, etc.) that OpenSBI originally set in mstatus_init(). Resume does not re-call mstatus_init(), so mstateen remains zeroed.
Consequence: function_loss
Pattern: HSM suspend/resume save/restore lists in sbi_hsm_data struct (and corresponding __sbi_hsm_hart_suspend/__sbi_hsm_hart_resume helpers) that include M-mode CSRs like menvcfg but omit mstateen0-3 CSR save/restore fields, or any resume path that fails to reinitialize mstateen after a non-retentive suspend where CSR state was lost
