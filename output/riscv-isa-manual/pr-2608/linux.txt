PR #2608  target=linux  overall=compliant
Spec: Kernel enabling sstateen bits without context-switching the corresponding extension registers creates cross-process covert channels through ISA extension state
Violation:
  Kernel writes to sstateen CSRs to permit user-mode access to extension state
  (e.g., JVT, FCSR-under-Zfinx, custom state via C bit), but the kernel's
  __switch_to context-switch path does not save/restore the actual
  architectural state controlled by those bits, allowing one user thread to
  set state and another to observe it
Consequence: info_leak
Pattern:
  csr_write.*sstateen|csr_set.*sstateen|__switch_to.*sstateen|SZSTATEEN|save_s
  tateen|restore_stateen
------------------------------------------------------------

[potential_risk] arch/riscv/include/asm/csr.h:233-243  SMSTATEEN0 bit definitions
  The kernel only defines hstateen0/mstateen0 bits for supervisor-and-above-
  level state (bit 58-63: AIA_IMSIC, AIA, AIA_ISEL, HSENVCFG, SSTATEEN0).
  Missing are the user-facing sstateen0 bit definitions: bit 0 (C — custom
  state), bit 1 (FCSR — Zfinx fcsr), and bit 2 (JVT — Zcmt jvt). The kernel
  currently has no Zcmt or Zfinx support (confirmed: no 'jvt', 'zcmt', 'zfinx'
  references in arch/riscv/), so this is a latent gap. If a future
  implementation adds Zcmt/Zfinx and M-mode firmware sets corresponding
  mstateen0 bits, the kernel would lack the symbolic definitions to detect or
  control this state.
  | /* Smstateen bits */
