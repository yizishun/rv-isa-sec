PR #111  target=freebsd-src  overall=bug_confirmed
Spec: Svukte (Address-Independent Fault Latency) missing from FreeBSD/riscv enables KASLR-defeating timing side channel via U-mode probing of S-mode address space through pmap fault latency measurement
Violation:
  In the FreeBSD/riscv kernel, if the Svukte extension is not implemented or
  enabled, the pmap page-fault handler (riscv/pmap.c) resolves U-mode-to-S-
  mode address accesses with timing that varies by target address — e.g., a
  fault to an unmapped kernel address may resolve faster (invalid PTE) than a
  fault to a valid kernel PTE that requires TLB fill or table walk. A
  userspace attacker can probe the supervisor address range, measure fault
  latencies via rdtime, and infer the kernel's virtual address layout (KASLR
  bypass), text segment boundaries, or heap structure.
Consequence: info_leak
Pattern:
  riscv/pmap.c page-fault handler path from U-mode accesses that does not
  enforce constant-time fault resolution; absence of Svukte CSR checks or
  menvcfg.CBZE/menvcfg.CBCFE configuration in locore.S or identcpu.c;
  pmap_fault() or trap_pfault() returning to userland without Svukte-
  guaranteed constant-latency semantics
------------------------------------------------------------

[bug_confirmed] sys/riscv/riscv/trap.c:230-264  page_fault_handler
  page_fault_handler() processes U-mode page faults to kernel addresses (va >=
  VM_MIN_KERNEL_ADDRESS) through the full fault resolution pipeline. The
  VIRT_IS_VALID() macro at line 231 treats any address in the kernel virtual
  range (>= 0xffffffc000000000) as 'valid', allowing the fault to proceed into
  pmap_fault() at line 264 rather than being immediately rejected. This means
  a U-mode attacker can probe the entire kernel virtual address space and

[bug_confirmed] sys/riscv/include/pmap.h:126-128  VIRT_IS_VALID
  VIRT_IS_VALID() macro treats any address >= VM_MIN_KERNEL_ADDRESS
  (0xffffffc000000000) as a 'valid' address for fault processing, even when
  the fault originated from U-mode. This is the gate that enables the KASLR-
  probing side channel: it allows U-mode faults to kernel addresses to enter
  the timing-variable pmap_fault() code path. Only the non-canonical hole
  between user space and kernel space is rejected immediately. The macro
  should explicitly reject kernel-range addresses when the faulting context is
  U-mode, or Svukte constant-time semantics should be enforced.

[not_implemented] sys/riscv/riscv/locore.S:65-391  _alt_start/_start
  The RISC-V boot assembly does not configure menvcfg at all. Only stvec
  (lines 212, 232, 369, 387), satp (lines 220, 375), and sscratch (lines 236,
  391) are written during boot. No CSR write to menvcfg exists anywhere in the
  kernel source under sys/. The menvcfg register (CSR 0x30A) is never read,
  written, or configured. This means menvcfg.CBZE, menvcfg.CBCFE, and any
  Svukte-related control bits remain at hardware reset defaults (typically 0,
  disabled). Even if firmware (OpenSBI) configures some menvcfg bits, the
  kernel has no visibility into or control over the configuration.

[potential_risk] sys/riscv/riscv/trap.c:425-428  do_trap_user
  do_trap_user() dispatches all U-mode page faults (instruction, load, store)
  to page_fault_handler() with usermode=1 without first checking whether the
  faulting address (stval) targets kernel virtual space. The faulting address
  is only checked later inside page_fault_handler() via VIRT_IS_VALID(). An
  early rejection of kernel-address faults at this dispatch point would
  prevent the timing-variable pmap_fault() walk entirely, but would still need
  constant-time rejection to avoid leaking the address-range boundary.
