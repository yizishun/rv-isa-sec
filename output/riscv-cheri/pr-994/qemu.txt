PR #994  target=qemu  overall=compliant
Spec: PR #994 moves SENTRY and CBLD from optional Zysentry/Zybld extensions into the mandatory CHERI base ISA — QEMU must now always implement these instructions and their unconditional JALR sentry-unseal/return-seal side-effects when CHERI is enabled, or guest CFI is silently broken
Violation: QEMU implements the CHERI base ISA (Zcheri) but treats SENTRY (YSENTRY) and CBLD (YBLD) as optional extension-gated instructions, or gates JALR sentry unseal/seal behavior on a separate Zysentry/Zybld extension property. If QEMU's CHERI enablement check does not unconditionally decode and execute SENTRY and CBLD when the CHERI base ISA is present, guest software relying on ambient sentry sealing/unsealing in JALR will silently execute with degraded control-flow integrity — JALR will not unseal sentry capabilities before installing into PCC, nor seal return pointers as sentries. Conversely, if QEMU implemented the old hook-based JALR behavior but removes the extension gate without adding the unconditional sentry logic, JALR incorrectly handles non-sentry sealed capabilities (e.g., from Zyseal) by clearing their tag instead of preserving them.
Consequence: privilege_escape
Pattern: check for CHERI extension enablement (e.g., cpu->cfg.ext_cheri or similar) that does not also unconditionally enable SENTRY/CBLD decode; JALR translation logic that checks for a separate Zysentry/Zybld property before applying sentry unseal/seal; capability type 1 (sentry) treated as undefined or falling through to default/error paths
