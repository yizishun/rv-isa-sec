PR #865  target=linux  overall=compliant
Spec: Kernel must re-validate capability tags on every load from memory, because MMU page mappings, PMAs, and platform load filters can silently clear tags between store and load, breaking authority-preservation assumptions in context switch, signal delivery, KVM, and ptrace paths
Violation: Linux kernel stores a tagged capability to memory (e.g., during context switch, signal frame setup, KVM vCPU save/restore, or ptrace regset access) and later reloads it expecting the tag to be preserved, without re-validating the tag after the load, when the memory path traverses an MMU mapping that clears tags, a PMA region that cannot store tags, or a platform load filter that strips tags
Consequence: privilege_escape
Pattern: capability.*store.*memory.*(reload|load|restore).*tag|save.*cap.*(ctx|context|frame|vcpu).*restore.*(tag|authority)|sc_cap.*lc_cap.*(check|assert|tag)

  This kernel (Linux 7.0-rc5, arch/riscv/) contains zero CHERI capability support. No capability registers are saved/restored in context switch paths (entry.S:421-471 __switch_to saves only integer GPRs + CSR_STATUS), no capability fields exist in thread_struct (processor.h:106-126), sigframe (signal.c:35-41, sigcontext.h:31-37), KVM vCPU context (kvm_host.h:116-154), or ptrace regsets (ptrace.c:24-38). No CHERI Kconfig option, no cheri-capable PTE handling, no revocation code. The vulnerability pattern 'capability store to memory → reload expecting tag preserved' cannot occur because the kernel never stores or reloads hardware capability tags.
