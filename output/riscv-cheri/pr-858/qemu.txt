PR #858  target=qemu  overall=compliant
Spec: CHERIoT JALR sentry semantics require atomic xstatus.xIE update and return-capability sealing based on prior-instruction retirement state; missing or reorderable emulation of this atomic side-effect in QEMU TCG enables untrusted guest code to escalate interrupt posture and bypass structured interrupt control
Violation: QEMU's emulation of JALR_CHERI for CHERIoT (Zycheriot) does not atomically update xstatus.xIE and seal the return capability in a single unbreakable step, OR writes xstatus.xIE using the wrong sentry type semantics (e.g., fd/bd sentries fail to clear xIE), OR seals the return capability based on post-retirement xIE rather than the prior instruction's retirement xIE
Consequence: privilege_escape
Pattern: jalr.*sentry|xstatus.*[Mm]IE.*cheriot|sentry_ot_[fb][de]|seal_return.*jalr|cheriot.*xIE|zycheriot.*mstatus
------------------------------------------------------------
[compliant] target/riscv/insn_trans/trans_rvi.c.inc:141-180  trans_jalr
  QEMU upstream has no CHERI/CHERIoT (Zycheriot) implementation. The trans_jalr function implements only standard RISC-V JALR: it computes target_pc = rs1 + imm, sets bit 0 to zero, writes return address to rd, and jumps. There are no capability checks, no sentry type decoding, no xstatus.xIE side-effects, and no return-capability sealing. This is NOT a bug — the CHERI/CHERIoT ISA extensions are simply unimplemented in mainline QEMU. The SMCTR/SSCTR control-transfer recording and Zicfilp forward-edge CFI are the only CFI-related JALR extensions present. The CHERIoT spec (rvy-cheriot-isa-priv.adoc:86-95) requiring JALR_CHERI to atomically update xstatus.xIE based on sentry type and seal the return capability with the prior instruction's retirement xIE is not applicable to this codebase.

[compliant] target/riscv/csr.c:1-1  N/A (no CHERI CSRs)
  QEMU has no CHERI-related CSR implementations (mtidc, mscratchc, mepcc, pcc, etc.). The CHERIoT spec (rvy-cheriot-isa-priv.adoc:39-49) redefines mtidc and mscratch reset values to hold root-rw-cap and sealing-root capability values respectively, and adds CSR legalization requiring pcc, mtvec, mepc to clear tag if sealed or lacking X-permission. None of these CSRs exist in this codebase, so there is no emulation bug.

[compliant] target/riscv/cpu_helper.c:542-547  riscv_cpu_do_interrupt
  The interrupt enable checks in cpu_helper.c use standard RISC-V MSTATUS_MIE/MSTATUS_SIE fields. In a CHERIoT system, the JALR_CHERI instruction must atomically update xstatus.xIE at retirement based on sentry type, and the return capability sealing must use the prior instruction's xIE. Since CHERIoT is unimplemented, these standard checks do not interact with any sentry-based interrupt control flow, and there is no vulnerability from missing xIE side-effects on capability-mediated control transfers.
