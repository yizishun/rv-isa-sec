PR #867  target=linux  overall=potential_risk
Spec: sstatus.CRGE is a new per-context opt-in bit that toggles PTE.CRW/CD/CRG into a 3-bit capability-access field; if the kernel does not save/restore it on context switch or fails to virtualize vsstatus.CRGE in KVM, the hardware will reinterpret the same PTE bits under different semantics per thread, causing silent PTE.CD dirty-tracking corruption (Svadu) or spurious capability-store traps (Svade) on pages created by CRGE-unaware code.
Violation: Linux kernel context switch, KVM vCPU switch, signal delivery (sigreturn), or ptrace (PTRACE_SETREGSET) fails to save/restore sstatus.CRGE, causing a process or VM to observe CRGE enable/disable state from a different security context, or the kernel sets CRGE=1 without zero-initializing PTE.CD and PTE.CRG bits in all user page tables, causing hardware to trigger unexpected store exceptions or silently set PTE.CD via Svadu hardware dirty tracking on pages whose PTE was configured under the pre-Svucrg PTE.CRW-only semantics.
Consequence: data_corruption
Pattern: sstatus.*save|sstatus.*restore|__switch_to|switch_to|sstatus_val|SR_|STATUS_|csr_write.*sstatus|csr_read.*sstatus|kvm_riscv_vcpu_switch|__fpsimd_save|do_signal|restore_sigcontext|ptrace_setsigmask

[potential_risk] arch/riscv/kernel/entry.S:441-451  __switch_to
  Context switch saves full sstatus into thread.sum (line 442-443), but on restore masks to SR_SUM only (line 450: 'and s0, s0, s1') and uses csrs (set-bits only, line 451) rather than csrw. This means: (a) any CRGE/UCRG bit stored in the saved value is discarded by the AND mask, and (b) csrs only sets bits without clearing, so a previous task's CRGE=1 state leaks into the next task. A task expecting CRGE=0 would run with CRGE=1, causing hardware to interpret PTE.CD/CRG bits under Svucrg semantics on page tables configured under pre-Svucrg PTE.CRW-only semantics.
  | csrr  s0, CSR_STATUS
  | REG_S s0, TASK_THREAD_SUM_RA(a3)
  | ...
  | REG_L s0,  TASK_THREAD_SUM_RA(a4)
  | li    s1,  SR_SUM
  | and   s0,  s0, s1
  | csrs  CSR_STATUS, s0

[potential_risk] arch/riscv/include/uapi/asm/ptrace.h:24-57  user_regs_struct
  user_regs_struct defines 31 GPRs (pc through t6) but omits sstatus. This is the UAPI structure used by signal frames, ptrace, and core dumps. The struct comment (line 21) states it 'must form a prefix of struct pt_regs', but pt_regs->status sits after t6 at offset 32*sizeof(long). Adding sstatus to user_regs_struct would break UAPI, so an extension-header mechanism (like the existing RISCV_V_MAGIC/RISCV_ZICFISS_MAGIC chain) is needed for CRGE.
