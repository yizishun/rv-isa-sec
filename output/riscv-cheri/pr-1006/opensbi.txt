PR #1006  target=opensbi  overall=bug_confirmed
Spec: Removal of the 'no active elements → no CHERI exceptions' rule means S-mode vector instructions with vl=0 or all elements masked can now trap to OpenSBI, creating a DoS vector if M-mode trap handlers lack a path for this previously impossible trap condition
Violation: OpenSBI M-mode trap handler receives a CHERI capability exception from an S-mode vector load/store instruction (e.g., vle, vse) that has zero active elements (vl=0, vstart≥vl, or all mask bits clear). The spec previously guaranteed that vector instructions with no active elements would not raise CHERI exceptions, so OpenSBI's trap handler may assume such traps are impossible and lack a handler path—causing an unrecoverable fault or infinite trap loop when the removed guarantee allows these exceptions to fire.
Consequence: denial_of_service
Pattern: sbi_trap_handler.*vector|handle_vector_exception|vector.*CHERI|vle.*trap|vse.*trap|vl.*0.*exception|inactive.*element.*trap|CSR_VSTART|CSR_VL
------------------------------------------------------------

[potential_risk] firmware/fw_base.S:673-690  _trap_handler
  The assembly trap entry via TRAP_SAVE_INFO (line 680) saves mcause, mtval, and optionally mtval2/mtinst, but does NOT save any CHERI-specific trap CSRs (meventcause, mepcc, mtdc, mcapidx). On a CHERI capability exception, these CSRs hold critical fault metadata (the authorizing capability, bounds check failure details, tag state) that is lost if not explicitly saved before the C handler runs. Even if a CHERI handler were added to sbi_trap_handler(), it would lack complete fault context.
