PR #996  target=linux  overall=potential_risk
Spec: Removal of sstatus.YE enable bit makes Svyrg 4-bit PTE Y-field subdivision always-on; kernel must initialize all Y sub-fields (YR/YW/YD) in every PTE or risk spurious capability load/store faults and silent tag stripping
Violation: Kernel PTE initialization code writes the Y field as a single YRW enable bit (e.g., setting only bit 3 and leaving bits 2:0 as zero or stale) without explicitly initializing the YR/YW/YD sub-fields. With YE removed, the 4-bit Svyrg subdivision is always active: YR=0 causes all capability loads from the page to trap with the new CHERI PTE-LD fault, YW=0 causes all capability stores with valid tags to trap with the CHERI PTE-ST fault. A kernel that previously depended on YE=0 to make Y[2:0] reserved/don't-care will now inject spurious capability faults on affected pages, or silently strip capability tags on load if YR=0.
Consequence: denial_of_service
Pattern: PTE_Y_FIELD.*(=|\|).*[^_]YRW|pte_val_t.*\by\b.*<<.*3|_PAGE_Y.*<<.*3|__PAGE_Y|_PAGE_CAP|pte_y.*bit.*[^2-0]|sstatus.*YE|SR_YE|MSTATUS_YE

[compliant] arch/riscv/include/asm/pgtable-bits.h:9-77  (global PTE bit definitions)
  No CHERI Svyrg Y-field PTE code exists in this kernel tree. The PTE bit layout defines only standard RISC-V bits (V,R,W,X,U,G,A,D,SOFT) with no _PAGE_Y, _PAGE_CAP, _PAGE_YR, _PAGE_YW, _PAGE_YD, or _PAGE_YRG definitions. Bits 58-55 (the RV64Y field defined by the CHERI spec) are treated as reserved/unused by this kernel. Since the kernel writes zero to reserved PTE bits, all four Y sub-fields (YR,YRG,YW,YD) would be 0, which on CHERI hardware with Svyrg enabled would cause capability load/store faults. However, this kernel has no CHERI support (no CONFIG_CHERI, no sstatus.YRGE handling), so M-mode firmware would leave YRGE=0, keeping the baseline YE-only mode where bits 2:0 are reserved/don't-care.

[potential_risk] arch/riscv/include/asm/csr.h:1-0  (global CSR bit definitions)
  No sstatus.YRGE, sstatus.SYRG, or sstatus.UYRG bit definitions exist in csr.h. If a future patch adds Svyrg PTE defaults without also adding YRGE enable-bit management, there would be no way to disable the sub-field subdivision. The PR review comment ('Don't we need to keep the enable bit?') is directly relevant: without YRGE as an opt-out, future CHERI extensions would have no mechanism to revert to baseline YE-only behavior when bits 2:0 are reserved in the PTE. However, since no CHERI code exists at all, this is currently a forward-looking concern only.
