PR #219  target=xiangshan  overall=compliant
Spec: The spec clarification narrows stval address writing to only breakpoint exceptions 'defined to write an address'; hardware that unconditionally writes PC/vaddr to stval for all breakpoint triggers (including icount/etrigger/itrigger) leaks internal control-flow state to supervisor mode through a CSR that should not carry that information
Violation:
  In XiangShan RTL, when a breakpoint exception is taken due to a debug
  trigger type that is NOT defined by the Sdtrig specification to write an
  address to tval/stval (e.g., icount/type=3 triggers, etrigger/type=4,
  itrigger/type=5, or textra32/textra64-only triggers), the CSR module
  unconditionally writes the faulting PC or a virtual address into stval
  instead of leaving it unmodified or writing 0.
Consequence: info_leak
Pattern:
  CSR trap-entry write logic for stval on breakpoint exception path that does
  not gate on trigger type before writing address — search for unconditional
  stval assignment in Breakpoint/breakpoint exception case of trap dispatch,
  e.g., when (exceptionType === Breakpoint) stval := pc or vaddr without
  checking trigger.type or trigger.action semantics from Sdtrig
