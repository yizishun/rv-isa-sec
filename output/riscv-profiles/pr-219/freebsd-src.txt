PR #219  target=freebsd-src  overall=bug_confirmed
Spec: Sstvala narrowed: stval not guaranteed valid for all breakpoint sources; FreeBSD currently uses sepc for SIGTRAP delivery (safe), but bhyve unconditionally saves stval on guest breakpoint exits which could propagate stale CSR state to VMM userland
Violation:
  Kernel code (in trap handler or vmm) reads stval on SCAUSE_BREAKPOINT and
  treats it as a valid address, when the hardware breakpoint source (e.g.,
  certain Sdtrig trigger types) is not defined by the ISA to write an address
  to stval — the CSR may hold stale data from a prior exception
Consequence: info_leak
Pattern:
  SCAUSE_BREAKPOINT.*tf_stval|case
  SCAUSE_BREAKPOINT.*stval|breakpoint.*csr_read.*stval
------------------------------------------------------------
[bug_confirmed] sys/riscv/vmm/vmm_riscv.c:699-701  vmmops_run
  stval CSR is unconditionally captured from hardware (csr_read(stval)) on
  every VM exit and stored into vm_exit.stval, regardless of scause type. For
  SCAUSE_BREAKPOINT (delegated at line 148 via hedeleg), the breakpoint falls
  through to the 'default' case in riscv_handle_world_switch (line 515-519),
  which sets exitcode=VM_EXITCODE_BOGUS. The full vm_exit struct — including
  the captured stval — is copyout'd to userspace via vmm_dev_machdep.c:85
  (case VM_RUN). Per the RISC-V privileged spec, stval is NOT guaranteed to
  contain a valid/architecturally-defined value for all breakpoint exception
  types; ebreak and certain Sdtrig trigger types may leave stale CSR data in
  stval. This unconditionally exposes potentially stale hardware CSR state to
  the bhyve userspace process, constituting a kernel information leak.
  | vme->scause = csr_read(scause);
  | vme->sepc = csr_read(sepc);
  | vme->stval = csr_read(stval);

[potential_risk] sys/riscv/vmm/vmm_riscv.c:146-148  vmmops_delegate
  SCAUSE_BREAKPOINT is delegated from M-mode to HS-mode via hedeleg (bit 3).
  This is the precondition that routes guest breakpoint exceptions through the
  VMM trap path where stval is unconditionally captured and exposed.
  Delegation itself is architecturally correct for a hypervisor, but combined
  with the unconditional stval capture at line 701, it enables the info-leak.
  | hedeleg  = (1UL << SCAUSE_INST_MISALIGNED);
  | hedeleg |= (1UL << SCAUSE_ILLEGAL_INSTRUCTION);
  | hedeleg |= (1UL << SCAUSE_BREAKPOINT);

[compliant] sys/riscv/riscv/exception.S:110-111  cpu_exception_handler_user / save_regs
