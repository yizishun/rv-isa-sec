PR #219  target=qemu  overall=compliant
Spec: Sstvala narrowed: stval must only be written for breakpoint exceptions whose trigger type is defined to provide an address — unconditionally writing stval for all non-ebreak breakpoints is now a spec violation that leaks potentially uninitialized or incorrectly-scoped virtual addresses to supervisor/hypervisor mode
Violation:
  QEMU writes a faulting virtual address to stval (or vstval/htval) for a
  breakpoint exception triggered by a debug trigger type that is NOT defined
  by the RISC-V debug spec to provide an address to stval. The old spec text
  unconditionally required stval to be written for all breakpoint exceptions
  except ebreak/c.ebreak; the clarified text restricts stval writes to only
  those breakpoint exception types where the privileged/debug architecture
  explicitly defines that an address shall be written. If QEMU's trigger
  implementation (e.g. mcontrol6 with execute match, icount, itrigger,
  etrigger) unconditionally populates stval with a virtual address for every
  breakpoint exception regardless of trigger type, it violates this clarified
  normative requirement.
Consequence: info_leak
Pattern:
  riscv_cpu_do_interrupt.*stval.*breakpoint|BREAKPOINT.*stval|write_stval.*bre
  akpoint|trigger.*stval|mcontrol.*stval|itrigger.*stval
