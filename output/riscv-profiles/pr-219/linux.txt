PR #219  target=linux  overall=potential_risk
Spec: Sstvala no longer guarantees stval is written for all non-ebreak breakpoint exceptions; kernel code that unconditionally reads stval in breakpoint handlers may leak stale register state to userspace via si_addr or ptrace
Violation: Linux kernel trap handler reads CSR_STVAL on a breakpoint exception from a debug trigger (Sdtrig) that is not defined to write an address to stval, then uses the stale/garbage value as a faulting address for signal delivery (si_addr), ptrace exposure, or KVM guest injection
Consequence: info_leak
Pattern: csr_read.*STVAL.*breakpoint|handle_breakpoint.*stval|do_trap_breakpoint.*stval|siginfo.*si_addr.*breakpoint|kvm_riscv_vcpu_trap.*stval
------------------------------------------------------------
[potential_risk] arch/riscv/kernel/entry.S:186-192  handle_exception
  CSR_TVAL (stval) is read and stored into regs->badaddr unconditionally for ALL exception types, including breakpoints where Sdtrig debug triggers may not write a defined value to stval per the Sstvala specification. The stale/undefined value in regs->badaddr is then exposed through ptrace regset (ptrace.c:483), KGDB register dump (kgdb.c:203), and __show_regs() (process.c:99). While this does not constitute a kernel info_leak (the hardware typically leaves stval at 0 or a prior benign value, not sensitive kernel data), it violates the specification that breakpoint stval is architecturally undefined.
  | csrr s3, CSR_TVAL
  | csrr s4, CSR_CAUSE
  | csrr s5, CSR_SCRATCH
  | REG_S s0, PT_SP(sp)
  | REG_S s3, PT_BADADDR(sp)

[compliant] arch/riscv/kernel/traps.c:283-305  handle_break
  handle_break() correctly uses regs->epc (the instruction address) as si_addr when delivering SIGTRAP/TRAP_BRKPT to userspace, not regs->badaddr (stval). This avoids the Sstvala violation: stval is not consumed as a faulting address for breakpoint signal delivery.
  | if (user_mode(regs))
  |     force_sig_fault(SIGTRAP, TRAP_BRKPT, (void __user *)regs->epc);

[compliant] arch/riscv/kvm/vcpu_exit.c:242-245  kvm_riscv_vcpu_exit
  KVM breakpoint handling uses KVM_EXIT_DEBUG to exit to userspace (VMM) without calling vcpu_redirect(). This correctly avoids injecting trap->stval into the guest's VSTVAL CSR, so the guest never sees the undefined stval from a debug-trigger breakpoint.
  | case EXC_BREAKPOINT:
  |     run->exit_reason = KVM_EXIT_DEBUG;
  |     ret = 0;
  |     break;

[potential_risk] arch/riscv/kvm/vcpu.c:855-858  kvm_arch_vcpu_put
  csr_read(CSR_STVAL) is called unconditionally before kvm_riscv_vcpu_exit() dispatch. For EXC_BREAKPOINT, trap->stval holds the architecturally undefined value. Though the breakpoint case does not use trap->stval for guest injection, the value is logged via kvm_err() on any subsequent error path (vcpu_exit.c:257-258) and is present on the kernel stack. A future code change adding stval-dependent logic after the EXC_BREAKPOINT case could inadvertently consume this undefined value.
  | trap->sepc = gcntx->sepc;
  | trap->scause = csr_read(CSR_SCAUSE);
  | trap->stval = csr_read(CSR_STVAL);

[potential_risk] arch/riscv/kernel/ptrace.c:483-483  ptrace_regs_offset_table
  regs->badaddr (populated from CSR_TVAL/stval in entry.S) is registered in the ptrace general-purpose regset. A debugger reading registers via PTRACE_GETREGS on a task stopped at a breakpoint may observe undefined stval as badaddr. The practical risk is low (value is typically 0, not a kernel pointer), but this is a specification compliance gap.
  | REG_OFFSET_NAME(badaddr),

[potential_risk] arch/riscv/kernel/kgdb.c:203-203  dbg_reg_def
  The KGDB register definition exposes regs->badaddr (stval) via the GDB remote protocol. When kgdb stops at a compiled breakpoint (ebreak) or handles a hardware breakpoint via Sdtrig, the exposed badaddr value corresponds to undefined stval. Same low-impact specification compliance gap as the ptrace path.
  | {DBG_REG_BADADDR, GDB_SIZEOF_REG, offsetof(struct pt_regs, badaddr)},

[compliant] arch/riscv/kvm/vcpu.c:591-592  kvm_arch_vcpu_load
  VSTVAL is saved/restored across VCPU load/put as part of normal guest CSR context switching. This path handles the guest's own VSTVAL value (not a host-sourced stval), so it is unrelated to the host-side breakpoint stval ambiguity. Compliant.
  | nacl_csr_write(nsh, CSR_VSCAUSE, csr->vscause);
  | nacl_csr_write(nsh, CSR_VSTVAL, csr->vstval);
