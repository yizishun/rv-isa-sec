PR #118  target=xiangshan  overall=compliant
Spec: Implementing Smstateen without Ssstateen hides state-enable access control from S/HS-mode software, creating a privilege control gap where M-mode can silently disable extensions without supervisor visibility
Violation:
  XiangShan RTL implements Smstateen CSRs (mstateen0-3) but does NOT implement
  Ssstateen registers (sstateen0-3, hstateen0-3). This occurs when the Chisel
  CSR module instantiates mstateen read/write logic with state-enable bit
  fields but omits the corresponding sstateen and hstateen CSR definitions and
  address decode entries, violating the implication that Smstateen requires
  Ssstateen registers to be visible at supervisor and hypervisor levels.
Consequence: privilege_escape
Pattern:
  mstateen.*StateEnable|customStateEn|Mapping.*sstateen.*MissingCSR|sstateen0.
  *NOT.*defined|hstateen0.*unimplemented|stateEnableField.*mstatus

[potential_risk] src/main/scala/xiangshan/backend/fu/NewCSR/StateEnBundle.scala:15-25  Hstateen0Bundle (field definitions)
  Hstateen0Bundle writable fields (SE0 at bit 63, ENVCFG at bit 62, CSRIND at
  bit 60, AIA at bit 59, IMSIC at bit 58, CONTEXT at bit 57) are declared RW
  without .withReset(). In CSRModule.scala:24, the reg is created as
  Reg(bundle) rather than RegInit(bundle, bundle.init) when needReset is
  false. This means hstateen0-3 register values at reset are undefined
  (uninitialized flops). While the spec (smstateen.adoc:154-155) places the
  burden of hstateen/sstateen initialization on M-mode software, undefined
  reset values could transiently enable privileged state access (e.g. SE0=1
  allowing VS-mode to access sstateen CSRs) if software reads hstateen before
  writing it. The masking by mstateen (which resets to 0) limits but does not
  fully mitigate this — the raw reg value could be observed via CSR read
  before a write happens.
