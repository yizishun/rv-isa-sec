PR #210  target=linux  overall=potential_risk
Spec: Kernel must atomically save/restore all CHERI capability register file on context switch and scrub on Zyhybrid RVY-to-RV64I transitions, or capability metadata leaks between processes
Violation: Kernel does not save/restore all CHERI capability register state (capability data, bounds, permissions, tags, CIFC level metadata from uycfg) during context switch between userspace processes, or under Zyhybrid, fails to scrub capability registers when switching from a CHERI (RVY64I) process to a non-CHERI (RV64I) process, exposing capability state across the security boundary
Consequence: info_leak
Pattern: __switch_to|switch_to|context_switch|switch_mm|capability.*save|capability.*restore|caphybrid|chybrid|SAVE_CAP|RESTORE_CAP|uycfg
------------------------------------------------------------

[potential_risk] arch/riscv/kernel/entry.S:421-471  __switch_to
  __switch_to saves/restores only callee-saved GPRs (ra, sp, s0-s11) and SUM status bit. No CHERI capability registers (CLEN-bit-wide cap regs, UYCFG, or any RVY-specific CSRs) are saved or restored. On CHERI hardware, capability tags/bounds/metadata would leak across process boundaries.

  | 	/* ... only callee-saved GPRs, no CHERI cap regs ... */

[potential_risk] arch/riscv/include/asm/switch_to.h:113-126  switch_to
  switch_to() macro calls __switch_to_fpu, __switch_to_vector, and __switch_to_envcfg, but has no capability-state save/restore callout. The Zyhybrid 'scrub on CHERI->non-CHERI transition' requirement has no corresponding implementation. If a CHERI (RVY64I) process context-switches to a non-CHERI (RV64I) process on Zyhybrid hardware, capability register state persists uncleaned.
